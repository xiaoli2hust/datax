## 1. 原始版本结论

原始版本已经覆盖了产品、UI、架构、数据、API、开发、Agent、GitHub、测试和运维等主题名称，因此适合表达“项目想做什么”。

它尚未回答：

- V1 到底包含什么、不包含什么。
- 用户在正常、失败、无权限、重复提交和系统重启时看到什么。
- 数据实体有哪些字段、关系、约束、版本和保留策略。
- API 的请求、响应、错误、分页、幂等和并发语义。
- DataX 由谁启动、如何取消、如何限制资源、宕机后如何对账。
- 密码如何保存、何时解密、日志如何脱敏、谁能执行。
- AI 的工具权限、审批、隐私、降级和评测。
- 用什么真实证据证明不是 Demo。

因此，原始文件名中的“最终版”表示一次内容版本，不代表已经形成可实施的工程合同。

## 3. 发现的主要冲突

- “企业级”与单节点/无 HA/无恢复契约之间没有边界。
- 产品列出工作流、AI、告警等模块，但 V1 开发计划没有说明是否实现。
- 架构列出多个服务，部署又只有一个 backend，未决定模块化单体还是微服务。
- DataX 被描述成 Runtime 服务，却没有 Worker、队列和进程生命周期。
- UI 有告警和 AI 入口，测试/验收没有对应闭环。
- API 要求权限和审计，但没有角色矩阵、审计结构或错误语义。
- 原始 ZIP 中文文件名元数据在部分解压工具中显示乱码，影响跨平台使用。

## 4. 本次修订采用的处理

### 4.1 冻结 V1

V1 收敛为：

- 单组织、多项目、四角色。
- MySQL 8/PostgreSQL 15 认证矩阵。
- 离线批、单表、直连字段、`insert-only`、手动执行。
- 不可变 JobVersion、受控 Worker、日志、状态和审计。
- 单节点 Docker Compose，明确非 HA。

调度、DAG、告警、插件市场、CDC、自由 SQL 和 AI 移到后续版本。

### 4.2 建立工程合同

- PRD 使用需求 ID、业务规则、用户故事和验收。
- UI 覆盖页面、字段、校验、加载/空/错误/权限/危险状态。
- 数据模型定义字段、关系、索引、生命周期和迁移。
- API 同时提供自然语言契约和 OpenAPI。
- JobSpec、Plugin Manifest、AuditEvent 使用 JSON Schema。
- 执行状态机、租约、幂等、取消、超时和崩溃对账被明确。
- 凭据、日志、网络、进程、备份和升级安全有具体控制。
- Agent 被限定为 V2 草稿/建议能力，保留无 AI 的完整手工路径。
- 测试区分单元、契约、集成、真实 DataX E2E、恢复和生产验收。
- 长任务 Prompt 加入阶段停靠、阻塞报告和不可伪装要求。

### 4.3 建立治理

- 根目录 `AGENTS.md` 约束人类和编码 Agent。
- ADR 记录范围、架构和执行安全决策。
- GitHub Issue/PR 模板要求需求追踪与真实证据。
- 依赖、Runtime、插件、许可证和摘要进入供应链门禁。

## 7. 结论

原始“最终版”不是完整工程需求，只是一套覆盖面较广的目录提纲。本次修订将它提升为 **V1 实施与验收基线**；它可以指导开发，但不能在代码、真实 DataX 链路和发布门禁尚未完成时被用来宣称产品已经完成。
