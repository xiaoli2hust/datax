## 1. 原始版本结论

原始版本已经覆盖了产品、UI、架构、数据、API、开发、Agent、GitHub、测试和运维等主题名称，因此适合表达“项目想做什么”。

它尚未回答：

- V1 到底包含什么、不包含什么。
- 用户在正常、失败、无权限、重复提交和系统重启时看到什么。
- 数据实体有哪些字段、关系、约束、版本和保留策略。
- API 的请求、响应、错误、分页、幂等和并发语义。
- DataX 由谁启动、如何取消、如何限制资源、宕机后如何对账。
- 密码如何保存、何时解密、日志如何脱敏、谁能执行。
- AI 的工具权限、审批、隐私、降级和评测。
- 用什么真实证据证明不是 Demo。

因此，原始文件名中的“最终版”表示一次内容版本，不代表已经形成可实施的工程合同。

## 3. 发现的主要冲突

- “企业级”与单节点/无 HA/无恢复契约之间没有边界。
- 产品列出工作流、AI、告警等模块，但 V1 开发计划没有说明是否实现。
- 架构列出多个服务，部署又只有一个 backend，未决定模块化单体还是微服务。
- DataX 被描述成 Runtime 服务，却没有 Worker、队列和进程生命周期。
- UI 有告警和 AI 入口，测试/验收没有对应闭环。
- API 要求权限和审计，但没有角色矩阵、审计结构或错误语义。
- 原始 ZIP 中文文件名元数据在部分解压工具中显示乱码，影响跨平台使用。

## 4. 本次修订采用的处理

### 4.1 冻结 V1

V1 收敛为：

- 单组织、多项目、四角色。
- MySQL 8/PostgreSQL 15 认证矩阵。
- 离线批、单表、直连字段、`insert-only`、手动执行。
- 不可变 JobVersion、受控 Worker、日志、状态和审计。
- 当时只冻结为单节点 Docker Compose、非 HA，尚未定义 Windows 安装器、Launcher、
  宿主依赖、端口与卸载数据边界；该交付描述已被 V1.2 取代。

调度、DAG、告警、插件市场、CDC、自由 SQL 和 AI 移到后续版本。

### 4.2 建立工程合同

- PRD 使用需求 ID、业务规则、用户故事和验收。
- UI 覆盖页面、字段、校验、加载/空/错误/权限/危险状态。
- 数据模型定义字段、关系、索引、生命周期和迁移。
- API 同时提供自然语言契约和 OpenAPI。
- JobSpec、Plugin Manifest、AuditEvent 使用 JSON Schema。
- 执行状态机、租约、幂等、取消、超时和崩溃对账被明确。
- 凭据、日志、网络、进程、备份和升级安全有具体控制。
- Agent 被限定为 V2 草稿/建议能力，保留无 AI 的完整手工路径。
- 测试区分单元、契约、集成、真实 DataX E2E、恢复和生产验收。
- 长任务 Prompt 加入阶段停靠、阻塞报告和不可伪装要求。

### 4.3 建立治理

- 根目录 `AGENTS.md` 约束人类和编码 Agent。
- ADR 记录范围、架构和执行安全决策。
- GitHub Issue/PR 模板要求需求追踪与真实证据。
- 依赖、Runtime、插件、许可证和摘要进入供应链门禁。

原始“最终版”不是完整工程需求，只是一套覆盖面较广的目录提纲。第一次修订将它提升为可评审的工程设计基线，但后续第一性原理复审发现：文档虽然回答了“组件和流程是什么”，仍未充分回答“用户最终得到什么可证明的数据结果”。

## 8. 第二次第一性原理复审

第二次复审从五个不可省略的问题出发：

1. 产品承诺的数据结果是什么，而不只是进程做了什么。
2. 同一个已发布版本是否绑定相同的非秘密连接配置和运行事实。
3. 能移动数据的人是否只可使用明确授权的源、目标和路径。
4. 失败、取消、失联和恢复后再次执行是否可能扩大数据损害。
5. 发布门禁是否能由独立 oracle 和机器证据客观计算。

复审发现的关键缺口：

- 原规则是“目标预存在 + 全量读取 + insert-only + 允许不经门禁创建新 Execution”，实际属于全量追加，不能称为可重复同步。
- DataX 退出码为 0 被用作 `SUCCEEDED`，但并不证明目标数据正确。
- JobVersion 没有固定不可变 DatasourceRevision，相同版本可能解析到不同 host、database 或 username。
- Developer 创建端点并与 Operator 角色组合后可能形成未经批准的数据外传路径。
- Worker 租约与 PID/PGID 不足以阻止失租进程继续写状态或目标数据。
- 测试要求逐行规范化哈希，却未定义 NULL、Unicode、Decimal、时区、重复行和多重集规则。
- 需求矩阵缺少需求优先级且业务规则区间发生错位，发布门禁不可计算。
- Redis 在单节点 V1 中只承担可重建唤醒，却增加了必需依赖和恢复面。

## 9. 第二次修订采用的决策

- V1 正式定位为 **安全的一次性离线全量复制**，不支持非空目标追加、周期重复运行或隐式增量。
- Operator 必须确认源端从运行前检查开始到独立 oracle 完成始终静默；Operator/DBA
  必须提交 `statement_version='1.0'`、有限 `valid_until` 的目标外部独占声明，承诺从
  Worker 最后一次目标空表观察到 oracle 目标一致性读事务完成期间没有平台外 DML/DDL。
  声明具有 `ACTIVE/REVOKED/EXPIRED` 生命周期；获知破坏后经专用接口撤回/报告并写
  `TARGET_EXCLUSIVITY_REVOKED` 审计。平台目标锁不能替代该运维前提，平台也无法技术证明
  所有瞬时、未报告或已回滚的外部写从未发生。
- 发布只验证目标表存在、安全画像合格且具备可核验能力；目标是否为空由 Worker 在每次运行前实测并保存本次 Execution 的空表证据。
- API 创建 `QUEUED` 时在同一事务原子创建 `TargetCopyLock=RESERVED`；同一
  TargetNamespace 的部分唯一索引覆盖 `RESERVED/ACTIVE/RECOVERY_REQUIRED`，避免第二个
  排队意图绕过互斥。
- V1 脏数据容忍固定为 `record_count=0`、`percentage=0`；任一脏记录都不能成为业务成功。
- DataX 退出 0 后先进入 `VERIFYING`；独立 `verification-oracle.v1` 必须在目标端同一
  一致性读事务中计算行数和多重集摘要；仅当目标声明仍 `ACTIVE`、未撤回未过期且目标
  快照完成时间不晚于 `valid_until`，通过后才能进入 `SUCCEEDED`。
- 分离 `process_state`、`data_effect`、`verification_state`；`CONFIRMED` 表示影响已被
  测得且可为 0 行，oracle 未启动时为 `NOT_STARTED`，已启动但无法可靠判断时才为
  `INCONCLUSIVE`。
- 已领取执行失败、超时、取消或 `LOST` 后，恢复后再次执行必须先提交处置确认，并由独立 RecoveryProbe 生成空表证据；未领取取消不创建恢复门禁。
- 领取事务提交前失败必须整体回滚，不产生 Attempt/fence，也不把已有 `RESERVED` 预留
  转换为 `ACTIVE`；Execution 保持从未领取的 `QUEUED` 并继续持有预留。领取事务一旦
  提交，任何非唯一成功结果都不得自动回到 `QUEUED` 或复用 Attempt。
- JobVersion 固定不可变源/目标 DatasourceRevision、EndpointPolicyRevision、物理表身份和
  TransferPolicy `scope_hash`；实际 CredentialSecretEnvelope 与连接证据在运行时单独固定。
- Admin 管理端点、数据源用途和源到目标策略；网络出口执行与连接探测使用相同策略。
- PostgreSQL 同时承担事实队列；Worker 使用原子领取、目标锁和单调 fencing epoch。
- 日志统一定义为“脱敏后的原序日志”，所有截断都有机器可见证据。
- 需求追踪逐条记录优先级、唯一测试 ID、oracle、证据和结果。
- `PRD-FR-JOB-010` 冻结为 `POST-V1`，V1 不实现或展示既有 DataX JSON 迁移入口。

## 10. 第二次修订的历史结论

第二次修订形成了 V1.1 安全一次性全量复制候选语义，但其“干净主机 + Compose”仍没有
回答最终用户如何在 Windows 上安装、启动、恢复和卸载，因此不再作为当前交付基线。

## 11. 第三次复审：Windows 本地工作站交付

第三次复审回到“一个没有 Linux 服务器的 Windows 用户，如何可靠得到可使用产品”这一
结果，发现旧基线仍缺少：

- 唯一认证宿主、安装包格式、Launcher 行为、桌面入口和默认 URL。
- Docker Desktop/WSL2/虚拟化缺失、许可责任和组织策略被阻断时的真实失败路径。
- Windows 与 Linux 容器之间的程序、配置、数据、密钥、备份和卸载边界。
- 固定端口冲突、IPv4/IPv6/LAN 暴露、Windows 路径/ACL/DLL 劫持和供应链签名控制。
- Windows 重启、睡眠/恢复、Docker Desktop restart、`wsl --shutdown` 后的 fence/
  目标锁/在途执行对账。
- 干净 Windows 11 VM 的安装、卸载保留数据、重装、四方向真实 DataX 和备份恢复证据。

V1.2 因此作出以下冻结：

- 唯一发布认证宿主为 Windows 11 x64 本地工作站。Windows on Arm、Windows 10/
  Server、macOS、原生 Linux 宿主和远程共享服务器不在发布矩阵。
- 发布物是已签名 `DataX-Enterprise-Studio-Setup-<version>-x64.exe` 和已签名
  `launcher.exe`。Setup 安装程序与桌面快捷方式；Launcher 做前置检查、幂等编排、
  readiness、对账和默认浏览器打开。
- Docker Desktop + WSL2 由用户或组织自行安装并承担适用许可。安装器只检测并链接官方
  指引，不静默安装/启用、不改固件或组织策略、不代接受或规避许可。
- API、Worker、PostgreSQL、DataX/JDK 固定在 Linux 容器。只有 Web 映射
  `127.0.0.1:17860`；API/Worker/PostgreSQL 无宿主端口，不创建 LAN 入站规则。
- PostgreSQL、脱敏日志、不含秘密的 oracle 工作区使用 `des-postgres-data`、
  `des-log-data`、`des-workspace-data` named volumes，不用 Windows bind mount；含密 Job、
  未脱敏 Runtime 临时文件和 DataX 进程工作目录只进入 Worker tmpfs。卸载默认保留这些
  卷；DATA/SECRETS 备份由用户选择程序目录外的两个独立本地位置，显式删除数据必须单独
  二次确认。
- `PRD-FR-WS-001` 和 `ACC-PRD-014` 分别由 `E2E-WIN-001`、`E2E-WIN-002` 在干净
  Windows 11 x64 VM 验收。要求签名/哈希/SBOM、依赖失败、端口/磁盘、loopback/LAN、
  Windows/睡眠/Docker/WSL 恢复、卸载/重装、四方向真实 DataX 和异机备份恢复全部通过。
- macOS/Linux 构建、Windows runner 编译、EXE/镜像存在或既有安装冒烟不构成 Windows E4。

## 12. 当前结论

当前文档目标是 **V1.2 Windows 本地工作站实施候选基线**，规范化需求 catalog 为
81 项（31 FR + 22 BR + 14 NFR + 14 ACC；80 V1-MUST + 1 POST-V1）。Discovery Gate
仍要求 8–12 名目标用户访谈、至少 20 个脱敏真实任务样本，以及 3 个设计伙伴合计不少于
10 个真实一次性复制任务。按 ADR-0007，所有者已授权风险自担的工程候选实现；这不形成
Discovery 证据，企业试点、公开发布和 V1 完成声明仍保持 `BLOCKED`。

Discovery Gate 之后，还必须通过跨文档/机器契约一致性、真实
MySQL → PostgreSQL walking skeleton，以及干净 Windows 11 x64 VM 上
`E2E-WIN-001/002`、四方向真实 DataX、签名/哈希/SBOM、安装/卸载保留、重启/睡眠/
Docker/WSL 对账和备份恢复。任一 V1-MUST 为 `FAILED/BLOCKED/NOT_RUN` 都不能称为
V1 企业试点完成；文档本身不证明代码、Windows 制品、真实链路或生产环境已经完成。
