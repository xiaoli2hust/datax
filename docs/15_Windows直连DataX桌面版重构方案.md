# Windows 直连 DataX 桌面版重构方案

## 1. 一句话说明目标

用户需要的是运行在 **Windows 电脑**上的 DataX 桌面工具：在窗口中配置任务，应用在本机启动随包的
Java/DataX 进程，DataX 将数据从源数据库直接读出并写入目标数据库。

```text
源数据库  ──网络/JDBC──>  Windows 桌面应用中的 DataX 进程  ──网络/JDBC──>  目标数据库
                                      │
                                      └── 桌面 UI、任务配置、受限日志和执行记录
```

“经过 Windows 电脑”指数据在 DataX 进程的网络连接和内存缓冲中流动，不等于把源表或目标表
完整保存到 Windows 硬盘。Windows 电脑必须能够同时访问源数据库和目标数据库；它不承担数据库
服务器，也不部署 Linux 服务。

## 2. 为什么要重构

当前工程候选是另一种产品：浏览器 UI + FastAPI + Worker + 本地 PostgreSQL + Docker Desktop/
WSL2 Compose 控制面。它为多角色、审计、任务队列、恢复、容器网络和发布证据而设计，因而产生
本地 Docker 卷、服务数据库、容量门槛和复杂发布治理。

这不等于 DataX 自身需要在本机保存业务数据。对于“一人/一台 Windows 电脑控制 DataX”的目标，
该控制面是过度设计，应以更小的原生桌面运行时替代。

| 关注点 | 当前 V1.2 工程候选 | 本重构目标 |
|---|---|---|
| 用户入口 | 桌面 Launcher 打开本机浏览器 | Windows 原生桌面窗口 |
| DataX 运行位置 | Docker/WSL2 Linux Worker | Windows 本机受控子进程 |
| 本地服务 | FastAPI、Worker、PostgreSQL、反向代理、egress guard | 无常驻服务、无 HTTP API、无本地 PostgreSQL |
| 本地持久化 | PostgreSQL、Docker named volume、日志和工作区 | 小型任务/执行元数据、凭据引用、受限日志和每次临时文件 |
| 运行前置 | Docker Desktop + WSL2 | 随包 JRE + DataX；Windows 和到两端数据库的网络可达性 |
| 交付形态 | `Setup.exe` + 浏览器 + 容器栈 | `Setup.exe` + 单个桌面应用目录；不承诺字面“单文件含全部运行时” |

## 3. 目标边界

### 3.1 必须交付

1. Windows 11 x64 的 `Setup.exe`、开始菜单和桌面快捷方式；双击后直接打开桌面窗口。
2. 随包、受清单保护的 JRE 与 DataX Runtime；版本、文件摘要、许可证和插件集合可查看。
3. 数据源连接配置、任务创建/导入/导出、运行/取消、实时脱敏日志、历史记录和失败说明。
4. 通过 JDBC/对应 DataX 插件从可达的源数据库复制到可达的目标数据库；不把完整业务表落盘到
   Windows 本机。
5. 每次运行使用独立工作目录、参数数组启动、无 shell 字符串拼接；敏感临时 DataX JSON 在
   进程退出、取消或下次启动清理。
6. 默认一次只允许一个 DataX 执行；崩溃或强制结束后显示“结果未知/可能部分写入”，绝不自动
   重跑或伪报成功。

### 3.2 明确不交付

- Docker Desktop、WSL2、FastAPI、Web 浏览器、HTTP 监听端口、本地 PostgreSQL、Redis 或外部
  Linux 服务器。
- 把源数据库或目标数据库完整备份/复制到 Windows 本地。
- 多人协作、远程登录、HA、调度、DAG、CDC、云端控制台或伪造的 AI 功能。
- 在没有真实 Windows 和真实对应外部系统验证时，声称某个 DataX 插件“稳定支持”。

## 4. 本机究竟保存什么

本重构不是“零字节本地存储”；任何桌面应用都必须保存自身程序和用户配置。它的约束是
**不建立本地业务数据存储端**：

| 本地对象 | 是否保存 | 规则 |
|---|---|---|
| DataX/JRE/应用程序 | 是 | 安装包随包提供，版本与 SHA-256 进入发行清单 |
| 任务名称、连接类型、映射、运行历史 | 是 | 使用嵌入式 SQLite 或版本化本地文件；没有单独数据库服务，不保存源/目标表数据 |
| 数据库密码/Token | 是，但不写明文任务文件 | 使用 Windows Credential Manager 或 DPAPI 加密存储；界面、日志、导出和 Git 中不得出现明文 |
| 完整 DataX Job JSON | 仅在编辑/运行所需范围保存 | 有秘密的运行副本只写入 ACL 受限临时目录；进程结束后删除，启动时清理遗留副本 |
| 日志和诊断 | 是，且有上限 | 只存脱敏日志；用户可导出，超出上限提示/截断并记录原因 |
| 源表/目标表完整副本 | 否 | DataX 流式读取并写入远端数据库；不得把它伪装成本地备份产品 |

不再设定“200 GiB”或“40 GiB”这种与控制面混淆的全局启动门槛。安装器只检查实际安装包、
JRE/DataX、受限日志与本次临时工作区所需的空间；最终数值须以打包后的真实体积和 Windows
实测确定，并在安装前明确展示。

## 5. 拟定技术架构

### 5.1 桌面壳与本地事实

推荐沿用现有 Vue/TypeScript 前端资产，并采用 **Tauri 2 + Rust** 作为桌面壳：Rust 负责
Windows 单实例、受控进程树、Windows Credential/DPAPI 调用、文件 ACL、日志流和安装器边界；
Vue 负责任务、日志和结果 UI。最终技术选择必须在 ADR-0016 固化，不能仅因本方案推荐就开始
实现。

本地事实源为嵌入式元数据文件（优先 SQLite）而非本地 PostgreSQL 服务。它至少记录任务版本、
不可逆运行 ID、配置摘要、Runtime 摘要、开始/结束时间、进程结果和可选核验结果。单实例 mutex
+ 单执行锁取代当前 PostgreSQL 队列和 fencing；锁丢失、应用崩溃或进程身份无法证明时，执行记录
进入 `UNKNOWN`/`RECOVERY_REQUIRED`，不自动继续写入。

### 5.2 运行时与数据流

```text
DataX Studio.exe
  ├─ 受签名/哈希保护的 JRE
  ├─ 受签名/哈希保护的 DataX Runtime + 插件目录
  ├─ Windows Credential Manager / DPAPI 凭据引用
  ├─ 本地 SQLite 元数据、脱敏日志和临时 Job JSON
  └─ datax.py / Java 子进程（参数数组、独立工作目录、可取消进程树）
          ├─ JDBC/插件连接：源数据库
          └─ JDBC/插件连接：目标数据库
```

没有本机 HTTP 端口，也没有浏览器反向代理。数据源端点、TLS、DNS 重解析、超时和出口范围必须在
桌面进程中做同一套检查；不能因为去掉容器就放宽凭据、路径、命令注入或网络安全控制。

### 5.3 执行结果的诚实表达

DataX 返回码 `0` 只能表示进程成功结束。桌面版至少分别显示：

- **进程结果**：完成、失败、取消、超时、崩溃；
- **数据影响**：未开始、可能部分写入、DataX 报告完成；
- **核验结果**：未执行、通过、失败、不确定。

对 MySQL/PostgreSQL 等能够使用独立 oracle 的场景，可选执行独立计数/摘要核验。对没有通用
oracle 的 DataX 插件，必须明确显示“未独立核验”，不能把日志、行数或退出码包装成数据正确性。

## 6. “DataX 所有功能”的可交付口径

“所有功能”分为两个层次，不能混为一谈：

1. **运行入口覆盖**：桌面应用提供高级模式，可导入、编辑、校验并执行 DataX 原生 Job JSON，
   因而不会被四个数据库向导限制。常用数据库可以有图形向导，但不为每个插件先制作专属页面。
2. **真实兼容与再分发覆盖**：每个插件/驱动仍要证明可合法随包、能在 Windows/JRE/DataX 组合中
   启动，并且在对应真实系统上完成测试。某些上游模块依赖专有 JDBC 驱动、云账号或 Linux 特性；
   未验证项必须显示为“需用户提供驱动/未验证/不支持”，不能仅因源码存在就显示“已完成”。

高级 JSON 模式可以包含上游 DataX 的高级参数，但应在运行前展示风险提示（例如会执行 SQL、脚本
Transformer 或覆盖目标数据的配置）。它不绕过操作系统权限、凭据保护、临时文件清理、真实运行
结果和插件兼容性记录。

## 7. 重构路径：不在旧架构上硬拆

现有工程约 12.7 万行，主要价值在 DataX 上游镜像、许可证/SBOM 资料、测试夹具、安装器经验和
部分 Vue 页面；FastAPI、Compose、Docker Launcher、本地 PostgreSQL、egress guard、Worker
队列和对应恢复链不应逐个“改成桌面版”。建议采用并行、可回滚路径：

1. **冻结旧企业控制面**：保留当前提交和文档作为 `legacy-enterprise-candidate` 证据，不删除历史、
   不伪称它已成为桌面版。
2. **先裁决 ADR-0016**：明确替代哪些现有 ADR、单实例/崩溃语义、凭据机制、运行时捆绑、插件
   许可、升级/卸载与 Windows 验收；同步修改 `AGENTS.md` 才允许新实现开始。
3. **新建 desktop-direct 垂直切片**：不复用 FastAPI/Compose 业务运行路径。初期只复用可审计的
   DataX 上游、许可证和必要前端组件。
4. **最后再处置旧代码**：新桌面版通过真实 Windows 与真实数据库验收后，才决定旧控制面是归档、
   独立分支保留还是删除；不得在尚无替代物时破坏现有文件。

## 8. 分阶段交付与工作量

以下是单名开发者的**有效开发量**，不是日历承诺；签名证书、Windows 验收机、真实数据库和
第三方驱动由使用者提供的速度会影响总周期。

| 阶段 | 交付物 | 估算 |
|---|---|---:|
| R0：裁决与文档 | ADR-0016、AGENTS/PRD/架构/安全/测试/追踪矩阵的同步基线；旧契约的废弃表 | 2–3 人日 |
| R1：桌面壳 | Tauri/Vue 单窗口、单实例、设置目录、最小任务列表和无端口运行 | 2–3 人日 |
| R2：DataX Runner | JRE/DataX 清单校验、生成 Job JSON、受控启动/取消、实时脱敏日志、崩溃恢复显示 | 4–6 人日 |
| R3：配置与凭据 | 数据源表单、Credential Manager/DPAPI、任务版本、导入/导出、高级 JSON 模式 | 3–5 人日 |
| R4：Windows 交付 | Setup、签名/哈希、升级/卸载、日志/临时文件清理、离线启动 | 3–5 人日 |
| R5：真实验证 | MySQL↔PostgreSQL 实测、失败/取消/部分写入、至少一类高级插件和干净 Windows 验收 | 3–5 人日 |

基础可用版合计约 **15–24 人日**。如果要求“每个 DataX 插件都拥有专用图形表单”，工作量将按
插件族扩张到数月；本方案用“常用向导 + 原生 JSON 高级模式”避免这个陷阱。

## 9. 验收口径

| 级别 | 证据 | 不能冒充的结论 |
|---|---|---|
| L0 | 文档、ADR、静态设计审查 | 不能说明程序可运行 |
| L1 | 单元测试、Runner 进程测试、安装器构建 | 不能说明 Windows 安装或真实数据库复制通过 |
| L2 | 干净 Windows 11 x64 上实际安装、启动、升级、卸载和无端口验证 | 不能说明所有插件/数据库方向已通过 |
| L3 | Windows 桌面版对真实源/目标数据库运行 DataX，并以独立 oracle 或明确的未核验状态交付结果 | 才能说明对应方向/插件的真实闭环 |

最低验收集：

- `Setup.exe` 在干净 Windows 11 x64 实际安装、启动、修复、卸载；无需 Docker/WSL2，且没有
  本机 HTTP 监听端口。
- 安装包、JRE、DataX 核心和每个随包插件均有版本、SHA-256、许可证和签名/来源记录。
- 真实 MySQL → PostgreSQL、PostgreSQL → MySQL 至少各一条成功链和一条失败/取消链；部分写入
  或崩溃不得显示成功或自动重试。
- 数据库密码、连接串、完整 Job JSON 与原始日志不出现在 UI、诊断包、测试快照、命令行或 Git。
- 进程、临时 Job JSON 与敏感目录在成功、失败、取消和下次启动时均按规则清理。
- “所有 DataX 功能”页面逐项显示：随包、需要外部驱动、已在真实系统验证、未验证或不支持；没有
  真实证据的项不得显示为稳定可用。

## 10. 必须同步的文档与契约

当 ADR-0016 被接受时，以下文件必须同一轮同步，不能先改代码再慢慢补文档：

| 类别 | 需要处理的对象 |
|---|---|
| 强制工程规则 | `AGENTS.md`：移除 Docker/WSL2、FastAPI/Worker/PostgreSQL/Compose 不可漂移条款，换成桌面进程、凭据、临时文件和 Windows 验收规则 |
| 产品与架构 | `README.md`、`00_`、`01_`、`02_`、`03_`、`06_`、`10_`、`11_`、`14_`、`docs/security/THREAT_MODEL.md` |
| 数据/API | `04_`、`05_`、`docs/contracts/openapi.yaml`；将 HTTP API/服务数据库契约替换为桌面命令/IPC、本地元数据、凭据引用和 DataX Job 校验契约 |
| 发布与验收 | `08_`、`09_`、`12_`、Windows 安装器/发布工作流、Windows E4 profile；将 Docker/Compose 证据替换为 JRE/DataX bundle、Windows 安装和真实 DB 证据 |
| 既有 ADR | ADR-0002、0006、0008、0013、0015 需明确被替代或限定；ADR-0001、0003、0004、0005、0007、0009、0010、0011、0012、0014 需逐条重新裁决适用性 |
| 机器契约 | runtime-generation、Compose、系统备份、Phase-A、OpenAPI 等不得静默删除；在 `docs/contracts/README.md` 和追踪矩阵中标明 `SUPERSEDED`、保留历史或迁移路径。新增桌面执行清单、本地设置/凭据引用、DataX Job 校验、Windows bundle manifest 契约 |

## 11. 下一步的唯一正确顺序

1. 将本方案的核心决策写成 **ADR-0016** 并由所有者接受；列出每个被替代 ADR 的处理方式。
2. 先同步 `AGENTS.md`、PRD、架构、威胁模型、测试和契约，消除“当前规则要求 Docker、新实现
   不使用 Docker”的冲突。
3. 建立最小 desktop-direct 纵向切片：桌面窗口 → 内置 DataX → 真实测试数据库 → 诚实结果。
4. 在干净 Windows 11 x64 验证 Setup，再按插件族扩展；任何未验证插件保持未认证状态。

在第 1–2 步完成前，继续为当前 Docker/PostgreSQL 企业控制面开发新功能会与用户目标背离；
直接删除旧代码也会破坏可回滚性。这个方案的价值是先把目标、边界、工作量和证据说清楚，再开始
正确的实现。
