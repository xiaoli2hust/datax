# ADR-0012：本机入口准入与审计就绪有界核验

- 状态：Accepted
- 日期：2026-08-02
- 决策者：仓库所有者
- 关联：`docs/03_技术架构设计.md`、`docs/04_数据库与领域模型设计.md`、
  `docs/05_API接口与前后端契约.md`、`docs/09_测试与验收标准.md`、
  `docs/security/THREAT_MODEL.md`

## 背景

`/auth/login` 和 `/health/ready` 都经过唯一的 Windows loopback Web 入口，但“只能从本机访问”
不等于“调用成本有界”。攻击者或失控的本机进程可并发提交不存在的邮箱，从而触发数据库
会话、组织行锁、Argon2id dummy verify 和失败审计；也可反复调用 readiness，使每次请求
全表解析、RFC8785 规范化并重算所有审计事件哈希。前者会饿死正常登录，后者会占用 API 的
小连接池并使健康检查本身成为拒绝服务放大器。

V1 是单台 Windows 本地工作站，固定 Compose 只部署一个 API 容器和一个 Uvicorn 进程；它
不是 HA 或多 API 实例产品。该前提必须显式成为控制边界，不能被 `--workers`、Compose scale、
额外 API 入口或旁路代理静默破坏。

## 决策

### 1. 登录是先准入、后认证

- 中间件顺序固定为 `request_id → TrustedHost → Origin → login admission → router`。非法
  Host/Origin 不消耗登录准入配额；被拒绝的登录不得构造依赖、懒加载 AuthService、打开
  数据库会话、运行 Argon2id 或写 AuditEvent。
- 准入是单 API 进程内的全局、账号无关 token bucket（默认 burst=5、5 次/分钟）加一个
  非阻塞的验证并发槽。它不保存邮箱、密码、IP、User-Agent 或浏览器身份；loopback 请求
  没有足以安全区分这些主体的可信身份，按这些字段分桶会引入绕过和枚举面。
- 任何准入拒绝一律返回
  `429 AUTH_LOGIN_ADMISSION_LIMITED`、`Retry-After: 60`、Problem JSON、`X-Request-Id` 和
  `Cache-Control: no-store`，不设置 Cookie 或 `WWW-Authenticate`。固定等待值不泄露“并发满”
  或“令牌不足”的内部差别。
- 429 是尚未进入认证决策的入站拒绝，不是错误密码：不改失败计数/锁定状态、不创建 session、
  不验密码、不写 AuditEvent。获准并实际执行认证的成功/失败仍按原规则审计。
- 前端绝不自动重放登录，也不保留密码；429 只显示受限 `Retry-After` 的人工重试提示，用户
  必须重新输入密码再提交。
- API 容器固定内存、CPU、PID 和文件描述符上限，限制获准请求之外的资源放大。

### 2. 审计链 readiness 采用持久水位线，而非每请求全量重放

- 新表 `audit_chain_watermarks` 每组织保存同事务写入的 `head_*`、已验证
  `verified_*`、最近完整重放 `full_replay_*`、`integrity_status`、失败定位和
  `mutation_epoch`。三组 sequence/hash 均要求 `0 ⇔ NULL` 且
  `full <= verified <= head`。
- 所有 AuditEvent writer 先锁 Organization，再检查真实 audit tail 与 watermark head 一致，
  并在同一业务事务写入新 Event、推进 `head_*` 和 epoch。已有非空链缺水位线、尾部不一致或
  CAS 失败均回滚；首次向空链追加时在同一事务创建 `PENDING` 水位线。迁移只回填 head 并标记
  `PENDING`，不会把历史静默提升为 `PASSED`。
- 正常 `/health/ready` 只读取组织、watermark 与每组织索引 tail。只有
  `PASSED`、`verified==head`、真实 tail==head 且完整重放尚未过期，才返回 audit component
  `UP`；缺失、孤儿、格式错误、尾不一致、过期、PENDING 或 FAILED 一律 `DOWN/503`。
- 每 API 进程以非阻塞 singleflight 执行重放；完整重放最多每 60 秒一次，最大 30 秒，
  PostgreSQL 使用 `REPEATABLE READ` 与 transaction-local statement timeout。新事件且已有
  新鲜完整证明时只从 `verified+1` 做 suffix replay；完成结果必须以 `head_*+mutation_epoch`
  CAS 发布。扫描期间追加或重启不会错误标记最新 head 为已验证。内容错误导致 `FAILED`
  sticky，后续追加不能把历史篡改洗成 PASS。
- readiness 结果最多缓存 1 秒；已有计算在进行时，其他调用直接
  `READINESS_CHECK_IN_PROGRESS/DOWN`，不排队等候。完整 replay 无论成功、篡改失败还是
  timeout，均在本 API 进程内保留下一次尝试时间；窗口内返回
  `AUDIT_CHAIN_FULL_REPLAY_THROTTLED/DOWN`，不把失败重放变成连续 30 秒扫描。缓存、
  singleflight 与该 cadence 只在本 ADR 固定的单 API 进程部署中有效；持久 watermark/CAS
  才承担重启后的正确性。

## 后果与限制

- 受同一 Windows 用户控制的本机进程可短时消耗共享登录桶；Docker 控制权本身是
  管理员等价边界。API 重启会清空内存准入、1 秒缓存和完整 replay cadence，但不会丢失
  watermark；重启本身属于 Docker 管理员等价操作，不能被当作无权限调用方的绕过结论。
- 不得为提高吞吐量使用 Uvicorn workers、Compose `--scale api`、额外 API 容器或新的
  API 入站路径。若将来需要多进程/HA，必须先以新 ADR 设计共享、围栏的 admission 和
  replay lease，并更新威胁模型、Compose、测试与发布证据。
- 同库水位线能把应用旁路、尾部漂移和历史篡改变成 fail-closed readiness，但不能证明拥有
  数据库管理员权限的攻击者没有同时改写 AuditEvent、水位线和数据库触发器。数据库外
  WORM/签名锚点仍是独立发布门禁。
- 在正常 Docker health poll（5 秒）下，历史中间行篡改最迟在旧 full proof 过期、下一次
  poll 发起完整重放并在 30 秒预算内完成后暴露；其保守上限为约 96 秒（60+5+30+1）。在
  没有健康请求或数据库不可用时，系统不声称持续检测，且不会用过期 proof 报告 `UP`。

## 必需验证

1. 429 必须早于依赖、数据库、Argon2id、失败计数和审计，非法 Host 不得消耗配额；已获准
   的错误密码仍保留原 401/锁定/审计语义。
2. 登录 429 的 Problem/header/no-cookie/no-audit 合同与前端人工重试行为必须回归。
3. 新迁移必须前进、回退，并只回填 `PENDING` head；所有六个审计 writer 需同事务更新
   watermark。
4. readiness 正常路径不得读取 `audit_events.event_json` 或全表重放；缺 state、tail 漂移、
   旧行篡改、过期 full proof、CAS 竞争、超时和并发调用必须失败关闭。
5. PostgreSQL 集成和最终 Windows E4 仍是不同证据层级；源码/SQLite 回归不得宣称 E3/E4。
