# ADR-0015：Windows 本机容量准入与工作负载包络分离

- 状态：Accepted
- 日期：2026-08-03

## 背景

产品运行在用户的 Windows 11 本地工作站，Docker Desktop/WSL2 的虚拟磁盘可能不在
`%LOCALAPPDATA%` 所在盘。此前工程候选把大表复制、30 天日志保留、数据库、工作区与安全
余量合并得到的 200 GiB 推荐预算，直接作为每个已认证 Docker 产品卷的启动拒绝条件。这混淆了
“现在能否安全启动”与“能否承诺大表容量档”，并会让普通本地控制台因未预留 200 GiB 而无法启动。

同时，只检查安装目录盘会在 Docker VHD 位于另一盘时误放行；放宽启动门槛也不能取消运行中的
日志/工作区水位和磁盘耗尽保护。

## 决策

1. 容量事实分为两个层次，不能互相替代：

   - **最低启动水位**：Launcher 继续检查 `%LOCALAPPDATA%` 的 Launcher 配置、secret 与本地
     备份元数据所在卷；受认证的 Docker `local`、无 options 产品卷由固定、只读的 `statvfs`
     probe 检查。两个检查在各自执行时必须至少有 **40 GiB 当前可用空间**；任一失败、未知或
     协议异常都在 Compose/业务数据库启动前失败关闭。
   - **工作负载包络**：200 GiB 是大表复制加 30 天日志保留的推荐验收容量，而非安装或普通
     启动门槛。只有在该容量、相应组合负载和 E3/E4 实测均满足时，才可承诺该档的吞吐、日志
     保留与队列 SLO。

2. Docker probe 对三个产品卷分别读取 `statvfs`，以发现不常见的不同底层文件系统；它检查的是
   每个文件系统的当前剩余空间，不会预留空间。Docker Desktop 的三个 `local` named volume 通常
   位于同一文件系统，所以这不是 `3 × 40 GiB` 或 120 GiB 的要求。

3. 启动水位不是运行时容量承诺。Worker 仍以 `effective_free`、日志预算、活动工作区预留和
   绿/黄/红 waterline 控制新执行：黄色停止普通新准入，红色停止新领取并使 readiness 失败。
   无法满足预估空间的执行必须保持阻断或失败关闭，不能因已经启动而绕过水位。

4. 本机导出的 DATA/SECRETS 备份与 Docker VHD 同盘时不能计作灾难恢复；备份空间在导出前仍须
   单独按实际预估大小检查。该 ADR 不改变 Docker Desktop/WSL2 前置依赖、DataX Linux 容器、
   named-volume 数据生命周期或仅 `127.0.0.1:17860` 的网络边界。

## 后果

- 一般 Windows 本地使用不再因为 200 GiB 推荐档被启动器硬阻断；用户仍必须在 Docker 数据盘与
  Launcher 数据盘保有 40 GiB 当前可用空间。
- 200 GiB 预算仍保留为大表验收与容量规划依据，不能被 40 GiB 启动通过、源码测试或 Docker
  容器存在替代。
- Windows E4 必须分别覆盖 40 GiB 临界、异盘 Docker VHD、运行中耗尽、日志/工作区 waterline，
  以及 200 GiB 大表组合档；当前工程只有源码/E1，尚无 Windows E4 结果。

## 回滚

若真实 E3/E4 显示 40 GiB 无法安全完成最低受支持启动/恢复路径，必须以新的 ADR 提高水位，并
同步修改 Launcher 常量、部署/安全文档和 Windows 场景。不得在文档中提高数值而保留较低的代码
门槛，或反过来把推荐包络重新伪装成启动硬门槛。
