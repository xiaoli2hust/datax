# ADR-0013：运行时数据库最小写权限边界

- 状态：Accepted
- 日期：2026-08-02
- 决策者：仓库所有者
- 关联：ADR-0002、ADR-0006、`docs/04_数据库与领域模型设计.md`、
  `docs/contracts/runtime-db-write-matrix.v1.json`、`docs/security/THREAT_MODEL.md`

## 背景

PostgreSQL 是 Execution、围栏、独占锁、RecoveryProbe、日志索引与审计元数据的事实源。
迁移 `20260731_0013` 虽已分开 migration owner、`datax_api` 与 `datax_worker` 登录，且禁止
两个运行角色 DDL/TEMP，但仍把当前和未来所有 public table 的
`SELECT/INSERT/UPDATE/DELETE` 一并授予两个角色。

因此 API 凭据可以绕过服务端状态机直接伪造 `SUCCEEDED`、fence、oracle、Lock 或 Probe；
Worker 凭据也可以直接改用户、项目、端点策略和凭据。仅以 ORM、路由 RBAC 或 SQLite
测试约束这些路径，不是数据库事实源的权限边界。

不能简单撤销 API 的全部 `UPDATE`：API 合法地创建初始 Execution/Lock/Event、提交取消或
独占撤回、提交 RecoveryProbe/rerun，并且产品管理面也有逐表合法写入。也不能把所有
状态写入交给无审计的超级用户函数，否则只是把通配权限转移到另一个绕过点。

## 决策

### 1. 默认拒绝，矩阵是唯一授权来源

- 迁移必须撤销 `datax_api`、`datax_worker` 对现有表和 sequence 的全表 DML，以及 migration
  owner 的 future-table default DML grant；未来表默认没有运行时 DML 权限。
- 每个运行角色的合法 `SELECT/INSERT/UPDATE/DELETE`、可更新列、可调用函数、状态前置条件和
  证明测试必须列入版本化机器契约
  `docs/contracts/runtime-db-write-matrix.v1.json`。未列入的表、列、sequence 或函数一律拒绝。
- API 的产品管理写入和执行事实写入同样必须逐表明确列入矩阵；“API 本来需要管理它”不能恢复
  通配权限。Worker 只可写经矩阵列出的执行/运行事实，不能写认证、组织、项目、端点策略、
  数据源、任务定义或凭据对象。
- 列级 `GRANT` 只解决可写字段集合；涉及状态、fence、同事务 Lock/Event、租约或恢复门禁的
  写入还必须由固定 `search_path` 的 `BEFORE`/deferred constraint trigger 或受限函数验证。
  数据库约束必须拒绝绕过 ORM 的直接 SQL。

### 2. 分两阶段收敛，不能虚报全部关闭

`FP-P1-003A` 先收敛执行事实面：

- API 只能创建初始 `QUEUED/NONE/NOT_STARTED/fence=0` Execution 及同事务 `RESERVED` Lock 和
  初始 Event；可插入取消/终止请求、受限独占撤回、RecoveryProbe/rerun 所需的初始事实。
  API 不可写 Attempt、Worker heartbeat、scheduler、fence、oracle、运行终态或成功 Event。
- Worker 可领取、围栏、运行、核验、取消收敛、RecoveryProbe 和连接证据所需的执行事实；
  每次写入仍受现有 fence/lease/状态约束，不能因数据库角色变为 Worker 而绕过它。
- API 容器的本机 lifecycle 停写只能调用一个固定
  `SECURITY DEFINER des_api_request_local_stop()`：它仅接受 `session_user=datax_api`，只允许
  单向设置 `draining=true` 与固定原因，显式设置安全 `search_path`，撤销 `PUBLIC EXECUTE`。
  SQLite 保留等价测试 fallback，不得伪称 PostgreSQL 强制。
- `queue_scheduler_state` 初始化、KEK 注册等当前由错误角色懒创建的对象必须改为 migration
  owner、显式 API 路径或受限函数；不能为了兼容旧代码重新把 scheduler/凭据表授予 Worker。

`FP-P1-003B` 再收敛审计与日志事实：将 AuditEvent 追加、AuditChainWatermark 发布/失败和
日志损坏降级改为受限函数/受控写路径，并撤销 API 对 `audit_events`、
`audit_chain_watermarks`、`execution_log_chunks`、`execution_log_gaps` 与相应 Execution
日志字段的直接 DML。003A 交付前不得把尚未收敛的 B 面误写为已保护。

### 3. 迁移与回滚纪律

- 写权限迁移只能在 owner 身份执行；`upgrade` 先撤销通配/default grant，再显式授予矩阵所列
  权限、创建/替换受限函数和 triggers，最后验证无多余 grant。不能在应用启动时 `GRANT`、
  建表或补约束。
- `downgrade` 必须恢复上一已发布 revision 的精确角色合同，并在 PostgreSQL 上执行
  `head → previous → head`；不得删除业务事实或角色。
- 每增加表/列/函数写入，必须先更新矩阵、ADR 影响分析、迁移正反向测试和 PostgreSQL
  越权反例，再更新运行代码。未更新矩阵的 schema 变更阻断合并。

## 实施状态（2026-08-02；不是 PostgreSQL 权限生效证据）

- Worker 已改为只读核验已登记的 `ACTIVE` KEK；未登记、状态/算法/指纹不匹配时不建立
  dispatcher，且不插入、轮换或锁定 `kek_key_versions`。为避免全新库在 Launcher 等待
  readiness、Worker 又等待 KEK 行时互相等待，Compose 在 migration 成功后运行一次
  `keyring-bootstrap`：它仅使用 `datax_api`、API 数据库密码、`idempotency_hmac_key` 和 KEK，
  调用既有幂等登记/指纹核验后退出。它没有 owner 密码、JWT/refresh key、出口租约能力、
  宿主端口或数据卷，并与 API/Worker 一样共享 `egress-guard` 网络命名空间；API/Worker 必须等待其成功。该实现不改变 Worker 只读边界，也不代表
  细粒度 PostgreSQL DML grant 已生效。
- `create_project` 已不再懒创建 `queue_scheduler_state`；迁移 singleton 缺失时返回
  `503 SERVICE_UNAVAILABLE`，不提交项目。该行仍必须由 migration owner 初始化。
- Execution 和 RecoveryProbe 领取已在读取 `draining` 前锁同一 `system_control` 行。未来
  `des_api_request_local_stop()` 必须取得同一行锁，才不会在 Launcher 停止预检后允许一个已读到
  旧值的领取事务提交。
- 尚未存在该 `SECURITY DEFINER` 函数、列级 grant/trigger 或 DML 撤销迁移；当前
  `datax_api` 与 `datax_worker` 仍拥有宽泛 PostgreSQL DML。上述源码回归只为 E1，不能写成
  `FP-P1-003A` 已关闭或权限已生效。

## 后果与限制

- API 或 Worker 凭据被盗时，数据库会拒绝一部分过去可直接篡改的事实；这不能阻止拥有
  migration owner/superuser 或 Docker 管理权限的攻击者。
- 触发器和函数必须最小化、固定 `search_path`、限制 `EXECUTE`、不拼接输入 SQL，并把拒绝原因
  以稳定 SQLSTATE/应用错误映射呈现；它们不是任意业务逻辑的新宿主。
- SQLite 是开发兼容层，不能验证 PostgreSQL 列级 grant、default privilege、trigger 或
  `SECURITY DEFINER` 行为。任何“数据库边界已生效”结论至少需要真实 PostgreSQL E2；
  Windows E4 和真实 DataX E3 仍为独立门禁。

## 必需验证

1. 迁移静态测试证明不存在 `ON ALL TABLES` DML 或 future default DML，矩阵、grant、函数和
   trigger 一一对应，并验证 downgrade/re-upgrade。
2. 真实 PostgreSQL 用 `datax_api` 直接 SQL 尝试改 Execution 三轴状态、fence、Attempt、
   Worker heartbeat、scheduler、项目配置和伪造成功 Event，均被权限或 trigger 拒绝；同时
   API 的合法初始创建、取消、受限撤回、RecoveryProbe/rerun 路径通过。
3. 真实 PostgreSQL 用 `datax_worker` 尝试改用户、项目、端点策略、数据源和凭据，均被拒绝；
   同时 worker heartbeat、claim/fence、运行态、oracle、RecoveryProbe 和连接证据合法路径通过。
4. lifecycle 函数拒绝非 API `session_user`、反向 draining、任意原因、PUBLIC execute 与不安全
   `search_path`；Windows/SQLite 回归只能标为 E1。
5. 003B 完成前，验收清单与台账必须明确审计/日志直接写面尚未关闭。
