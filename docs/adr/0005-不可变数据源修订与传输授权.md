# ADR-0005：不可变数据源修订与传输授权

- 状态：Accepted
- 日期：2026-07-30

## 背景

如果 `JobVersion` 只保存可变 Datasource 的 ID，同一个版本可在 host、数据库名或用户
名被修改后连接到不同系统，无法重现也无法证明数据去了哪里。仅凭项目角色允许用户
任意组合源端和目标端，还会形成“合法功能被用作数据外传通道”的 confused deputy
风险。应用层校验主机字符串也不能抵御 DNS rebinding 或绕过真实网络出口边界。

## 决策

- Datasource 是可变资源身份；每次非秘密连接配置变化都创建不可变
  `DatasourceRevision`。历史修订禁止更新和删除。
- EndpointPolicy 同样只是可变显示身份。host/CIDR/port/TLS/TTL/resolver/egress 规则
  变化必须创建不可变 `EndpointPolicyRevision`；DatasourceRevision 固定引用它，
  JobVersion 与运行快照继续固定其版本，不能跟随 current pointer。
- 每个 DatasourceRevision 在可用前绑定不可变 `PhysicalEndpointIdentity`。MySQL 使用
  经受控探针验证的 `server_uuid`，PostgreSQL 使用经批准证明的 `system_identifier`；
  无可信引擎原生身份时 fail closed。hostname、IP、证书或 revision 不同不能单独证明
  物理实例不同。
- 引擎元数据按服务器真实标识符规则解析成不可变 `TargetNamespace`：
  `PhysicalEndpointIdentity + catalog/database + schema + table + normalization_version`。
  源/目标物理表 hash 相同即拒绝；同一 TargetNamespace 的活动锁/恢复门禁跨 Datasource
  和 revision 生效。
- `JobVersion` 固定源、目标 `DatasourceRevision`、EndpointPolicyRevision、物理表身份。
  CredentialSecret/Envelope 独立版本化，Execution 在领取事务内、任何连接前固定实际
  ACTIVE secret/Envelope，允许不改变任务语义的普通凭据/KEK 轮换。
- 只有 Admin 可以创建、修改、测试、启停 Datasource，维护 EndpointPolicy、显式
  DatasourceUsageGrant 和源到目标的 TransferPolicy。
- TransferPolicy 不只批准 revision 对；其 `scope_hash` 精确覆盖源/目标
  catalog/schema/table 和排序去重的显式允许列。`ALL_COLUMNS` 也必须先展开，JobVersion
  的映射只能是 scope 子集；scope/revision/classification 变化使旧审批失效。
- Developer 只能查看和使用 Admin 已授权方向/scope 的 source/target；发布时和运行前
  都要校验使用授权、TransferPolicy scope、数据源状态与固定 EndpointPolicyRevision。
  Operator 不能通过再次执行或换 revision 绕过这些检查。
- EndpointPolicy 使用精确 FQDN/IP、端口、协议和允许 CIDR 表达。连接前由受信 DNS
  解析，规范化全部 A/AAAA 结果并逐个校验；连接必须固定到已校验 IP，同时保持 TLS
  hostname 校验。TTL 过期、CNAME/解析结果变化或任一地址越界时 fail closed。
- 连接测试、元数据、preflight、DataX、oracle 和 RecoveryProbe 各自保存不可变连接
  证据：EndpointPolicyRevision、完整解析集、selected/peer IP、TTL、resolver/egress
  版本与 evidence hash；创建数据源时的一次解析不能替代运行时证据。
- Worker 容器/主机实施默认拒绝的真实 egress enforcement；应用校验不是网络隔离的
  替代品。连接测试、元数据读取、预检、核验和 DataX 正式执行使用同一策略。
- 所有端点、数据源修订、授权、传输策略、DNS 拒绝与执行决策都产生审计事件。

## 后果

- 发布版本可证明固定连接到哪个非秘密端点/网络策略、哪张物理表和哪些允许列，同时仍
  允许安全轮换密码或只重包裹 DEK。
- 项目角色不再自动授予任意数据移动权，降低内部数据外传和横向访问风险。
- 部署必须提供可测试的 DNS pinning 与网络出口控制；没有该能力时试点发布门禁为
  `BLOCKED`，不得只用字符串白名单代替。
- 部署还必须取得可靠物理实例身份；无法取得时不得用“两个 revision 不同”放行。
- 对 Datasource/EndpointPolicy 的编辑将创建新修订；采用新修订、物理身份或 scope
  必须重新审批 TransferPolicy、校验并发布新 JobVersion。
- Windows `launcher.exe` 只能向固定 Linux 容器传入经过验证的本地配置引用，不能把
  Windows 凭据、Docker Desktop 管理端口、命名管道或宿主文件系统作为数据源快捷入口。
  容器 egress 与 EndpointPolicyRevision 仍是实际边界；Windows Defender Firewall 只作
  宿主补偿控制，不能替代容器内默认拒绝策略。
- 默认 Web 入口只绑定 `127.0.0.1:17860`。API、Worker、PostgreSQL 和 DataX 不映射
  Windows 宿主端口，避免本地工作站网络接口扩大传输授权面。
