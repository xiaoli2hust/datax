# ADR-0008：干净目标恢复与原子运行代际

- 状态：Accepted
- 日期：2026-08-01
- 决策者：仓库所有者授权的工程候选实现
- 关联：`docs/contracts/system-backup.v1.md`、`docs/contracts/runtime-generation.v1.schema.json`、`REC-HOST-001`

## 背景

当前 Windows Compose 把运行数据固定到 `des-postgres-data`、`des-log-data`、
`des-workspace-data`，运行 secret 固定放在宿主 `secrets/`。双包恢复 helper 已能认证、
配对并解包到空 staging，但 Docker named volume 不提供 rename 或 compare-and-swap；如果
Launcher 依次覆盖数据库卷、日志卷、workspace、secret 和 installation-id，任意掉电都
可能留下无法证明属于同一备份代际的混合集合。

V1 的首要恢复结果是：在另一台干净 Windows 11 x64 电脑上，从一对经过认证的
DATA/SECRETS 包恢复一个自洽的本地工作站。覆盖一个已有安装会同时引入旧卷保留、在线
停写、回滚选择和误删风险，不应与最小灾难恢复路径混在同一版本。

## 决策

1. V1 系统恢复只接受干净目标：不存在已提交运行代际、旧式 `installation-id`、任何
   `des-*` 产品卷或产品容器。已有安装调用 restore 固定失败关闭；覆盖恢复和原地升级继续
   属于后续 ADR，不复用本流程。
2. 每次首次初始化或恢复形成一个不可变运行代际。代际包含：
   - 一个 16-byte 随机、编码为 32 位小写十六进制的 `generation_id`；
   - 备份内原始 `installation_id`；
   - 该代际独立的宿主 secret 目录；
   - PostgreSQL、脱敏日志、workspace 三个随机命名 Docker volume；
   - 来源 `FRESH / LEGACY / RESTORE` 与可选 restore journal ID。
3. `%LOCALAPPDATA%\DataXEnterpriseStudio\runtime-generation.json` 是唯一活动代际指针。
   其结构由 `runtime-generation.v1.schema.json` 约束，并包含域分离 RFC 8785 摘要。Launcher
   只在同目录创建受 ACL 保护的新文件、刷盘并以“不覆盖已有指针”的原子 rename 提交。
   V1 restore 目标必须干净，因此提交不需要替换旧指针。
4. Compose 的三个逻辑 volume key 保持不变，但实际 `name` 必须由已验证的活动代际注入；
   `DES_SECRET_DIR` 和 `DES_INSTALLATION_ID` 也来自同一指针。不得分别读取多个“当前”文件
   后自行拼装运行集合。
5. 现有工程候选安装允许一次性迁移为 `LEGACY` 代际：只有固定三个卷、固定 secret 集和
   旧 installation-id 已全部通过现有身份检查时，才原子创建指针；不移动、不复制、不
   重命名旧对象。任何部分状态继续失败关闭。
6. 恢复提交前，Launcher 必须在只包含临时 PostgreSQL 与验证 helper 的 `--internal`
   隔离网络中完成新空卷初始化、参数数组形式的 `pg_restore --exit-on-error
   --single-transaction --no-owner --no-privileges`、迁移/约束/审计链/日志/KEK-Envelope/
   发布证据复核，并把日志复制到新日志卷；workspace 必须为空。
   schema head `20260802_0022` 的标准 DATA dump 固定排除整个
   `des_phase_a_qualification` 私有 schema（包括三张表、schema 内触发器、私有 ledger guard functions、
   私有 0021/0022 `SECURITY DEFINER` issuer/consumer entrypoints 和 schema metadata），且不会携带无登录
   ledger roles；保护 public `executions` trigger 的 `public.des_phase_a_execution_mode_guard()` 必须随 dump
   保留，仍由无登录 ledger owner 持有且向普通调用者撤销执行权。dump 会保留
   `alembic_version=20260802_0022`。只排除 schema 仍不足以处理 0022 public Execution/log 残留：当前
   Launcher 在 `pg_dump` 前后（PostgreSQL 停止前）固定重验无 `PHASE_A_HARNESS` Execution；存在/检查失败
   或非 `t` 输出为 `BACKUP_PHASE_A_PRIVATE_EXECUTION_PRESENT`、psql 完成但非零为
   `BACKUP_PHASE_A_PRIVATE_EXECUTION_CHECK_FAILED`，其他命令错误也失败关闭；
   受保护 Phase-A backup/restore 是未实现的独立能力。因此，在受保护 restore bootstrap 创建新的空 ledger、
   不随备份恢复的 issuance epoch，并仅允许该 epoch 后重新验证 P/QH、原子消费新 nonce 与签发新
   PAG 之前，本条的真实 `pg_restore`、迁移和应用启动必须保持 `BLOCKED`；本轮真实 PostgreSQL 15 E2 的
   空数据库 schema-exclusion `pg_restore` 探针通过，也不得解释为可完成恢复。
7. 提交前任一失败只能清理由受双恢复秘密认证 journal 精确记录、且没有容器引用的当前
   staging 对象。活动指针提交后不得自动删除包、journal、secret 或卷；首次正式启动和
   reconcile 通过后，恢复才可记录为完成。
8. 中断恢复只允许继续同一包对、同一两把恢复秘密和同一 journal，或执行 journal 授权的
   清理。不得猜测代际、采用名称前缀扫描后批量删除，或生成替代 KEK/数据库密码。
9. 固定应用数据根下只要存在 `system-restore` 状态，普通 `start` 和 `backup` 就必须在
   secret、installation-id、卷初始化或备份读取前失败关闭。不得因 journal 尚未提交、
   损坏或不可读就回退为全新安装；继续恢复或 journal 授权清理是独立受控路径。

## 后果

- 活动 installation-id、secret 和三个卷由单一指针共同选择，避免多对象“半切换”。
- 恢复不会覆盖已有工作站；操作者必须使用干净 Windows 目标机，这牺牲便利性以换取可
  证明的 V1 安全边界。
- Compose、Launcher、restore journal、威胁模型、部署文档和 Windows E4 验收必须同步
  支持运行代际。
- ADR 被完整实现并通过真实 Windows 演练前，`launcher.exe restore` 仍必须失败关闭，
  不得仅凭 schema、指针类或单元测试宣称系统可恢复。

## 工程候选实施状态（2026-08-01）

- 已接入：严格 Schema/Rust 校验、域分离状态摘要、Compose volume-name hooks；完整旧式
  三卷、固定 secret 集和 installation-id 通过原有身份检查后，Launcher 可用 ACL 受控
  pending 文件和 Windows `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 无覆盖提交 `LEGACY`
  指针。所有 Compose 调用从该指针整组取得 secret 路径、installation-id 和三个卷名，
  并清除宿主同名环境变量。Launcher restore 入口还会先证明目标没有旧身份、代际、运行
  secret、产品容器或产品卷，再用固定无网络 helper 将双包认证到 ACL staging；成功仍以
  `RESTORE_STAGED_COMMIT_BLOCKED` 结束。
- 仍关闭：创建 `FRESH` 随机对象集合、从 journal 创建并验证 `RESTORE` 随机对象集合、
  隔离 `pg_restore`、证据重算、恢复提交后的首次 reconcile 和真实 Windows E4 演练。
