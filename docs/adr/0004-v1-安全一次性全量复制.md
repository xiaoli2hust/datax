# ADR-0004：V1 采用安全的一次性离线全量复制

- 状态：Accepted
- 日期：2026-07-30

## 背景

V1 固定使用全表 Reader 和 `insert-only` Writer。如果允许绕过恢复门禁向非空目标创建新 Execution，失败、取消或 `LOST` 后的新一轮写入会产生重复记录、唯一键冲突或无法解释的数据混合；如果源表在运行期间持续变化，又没有数据库级一致性快照，就无法证明目标对应哪个确定时点。DataX 退出码 `0` 只能证明进程按自身规则结束，不能证明目标数据与源数据一致。

因此，“可重复离线同步”不是当前技术能力可以诚实承诺的产品结果。V1 必须先收敛为一个可验证、可恢复且不会奖励重复写入的最小数据合同。

## 决策

### 1. 产品语义

V1 对用户只承诺“安全的一次性离线全量复制”：

- 一次 Execution 从一张静默源表读取当前全部行，并向一张预创建、为空且可核验的目标表执行一次 `insert-only` 写入。
- 不支持非空目标追加、同一目标并发写入、周期性或可重复同步，也不支持从运行前检查开始到独立 oracle 完成仍持续写入的动态源表。
- `SyncJob`、`rerun` 等既有机器标识可暂时保留兼容性；页面、帮助、指标和验收文案统一使用“复制任务”和“恢复后再次执行”，不能借旧标识扩大产品承诺。

### 2. 固定传输策略

JobSpec V1 固定以下策略，不提供用户可改枚举：

| 字段 | 固定值 | 含义 |
|---|---|---|
| `source_consistency_mode` | `OPERATOR_QUIESCED` | Operator 确认源表从运行前检查开始到独立 oracle 完成都不再发生写入 |
| `target_precondition` | `EMPTY_AND_VERIFIABLE` | 目标表预创建、可由服务端只读核验且启动 DataX 前实测为零行 |
| `write_semantics` | `INSERT_ONLY_ONCE` | 对已准备目标只允许一次追加写入 |
| `duplicate_policy` | `REJECT_NONEMPTY_TARGET` | 目标非空时拒绝执行，不提供“忽略风险继续” |
| `partial_write_policy` | `MANUAL_REMEDIATE` | 平台不清理业务表；由 Operator/DBA 完成必要外部处置（无需清理时记录理由）并接受独立复检 |
| `dirty_data_limit` | `record_count=0, percentage=0` | 任一脏记录都使执行不能成为业务成功；非零容忍属于 POST-V1 |

任务校验与发布只验证目标表存在、安全画像合格且具备可核验能力；不得把发布时点的空表
查询冻结为运行证据，也不得因发布时目标非空就混淆发布与运行前门禁。运行请求只提交
`source_quiescence_confirmation` 与 `target_exclusivity_confirmation`；后者固定
`statement_version='1.0'` 和有限 `valid_until`，承诺从 Worker 最后空表实测到 oracle
目标一致性快照读完不存在平台外 DML/DDL，并明确平台锁不能替代该运维前提。目标空表
不是客户端声明，Worker 必须在每次启动 DataX 前生成本次 Execution 服务端实测的
`target_empty_evidence`。两类确认、空表/一致性快照证据、
DatasourceRevision/EndpointPolicyRevision、PhysicalEndpointIdentity/TargetNamespace、
TransferPolicy `scope_hash`、实际 CredentialSecretEnvelope、连接证据与固定复制策略都
进入 Execution 运行快照和审计。

Execution 对目标声明持久化 `ACTIVE/REVOKED/EXPIRED`、撤回时间与原因。Operator/Admin
一旦获知 DBA 撤回、变更冻结失效或平台外 DML/DDL，必须调用专用撤回/破坏报告接口；API
原子保存 `REVOKED` 并写 `TARGET_EXCLUSIVITY_REVOKED` 审计。未领取执行取消并释放
`RESERVED`，已领取执行停止并进入恢复门禁，已开始 oracle 则形成
`INCONCLUSIVE/TARGET_EXCLUSIVITY_BROKEN`。到达 `valid_until` 按
`EXPIRED/VALIDITY_WINDOW_EXPIRED` fail closed。终态 Execution 不随墙上时钟继续改写；
撤回终态历史返回冲突。平台未收到报告并不构成对所有瞬时、未报告或已回滚外部写的技术
证明，独立 oracle 只能判断实际读取到的数据结果。

同一 `TargetNamespace`（由不可变 PhysicalEndpointIdentity、引擎真实标识符规范化的
catalog/database、schema、table 和 normalization version 派生）在系统范围内只允许一个
未释放预留/活动/恢复锁；Datasource、revision、hostname 或 IP 别名不能绕过。API 创建
`QUEUED` Execution 时必须在同一事务创建 `TargetCopyLock=RESERVED`；Worker 领取时原子
转换为受 fence 保护的 `ACTIVE`，未领取取消释放预留，任何已领取非唯一成功转换为
`RECOVERY_REQUIRED`。

### 3. 结果状态与独立核验

Execution 同时使用三个独立维度：

- `process_state`：`QUEUED / STARTING / RUNNING / VERIFYING / SUCCEEDED / FAILED / TIMED_OUT / CANCEL_REQUESTED / CANCELED / LOST`。
- `data_effect`：`NONE / POSSIBLE / CONFIRMED / UNKNOWN`，只描述目标端影响，不证明内容正确；
  `CONFIRMED` 表示影响已被可靠测得，测得行数可以为 0。
- `verification_state`：`NOT_STARTED / VERIFYING / PASSED / FAILED / INCONCLUSIVE`。

DataX 退出码 `0` 后，Worker 必须将执行推进到 `VERIFYING` 并调用独立 oracle。oracle
不复用 DataX 自报写入数或产品自身汇总逻辑；它按机器契约定义的规范化规则比较静默源表
与目标表的行数和内容摘要，并在目标端同一个一致性读事务中同时计算目标行数与多重集
摘要，保存快照标识和起止时间。oracle 从未启动时 `verification_state=NOT_STARTED`；
只有 oracle 已启动却无法形成可靠结论时才是 `INCONCLUSIVE`。

只有 oracle 得到 `PASSED`，且目标声明仍为 `ACTIVE`、未撤回未过期、
`target_result.snapshot_finished_at <= target_exclusivity.valid_until`，Worker 才能写：

`process_state=SUCCEEDED`、`data_effect=CONFIRMED`、`verification_state=PASSED`。

oracle 得到 `FAILED` 或 `INCONCLUSIVE` 时，`process_state=FAILED`。进程失败、超时、取消或 `LOST` 时，除非可靠证据证明没有写入，否则 `data_effect` 必须为 `POSSIBLE` 或 `UNKNOWN`。

### 4. 恢复门禁

V1 不自动重试。Execution 一旦被 Worker 领取，对其 `FAILED / TIMED_OUT / CANCELED / LOST`
结果，恢复后再次执行必须满足全部条件；未领取的 `QUEUED` 取消由 reconciler 收敛为
`CANCELED/NONE/NOT_STARTED`，不创建 Attempt/fence/恢复门禁，并把已有 `RESERVED`
预留转为 `RELEASED`：

1. 原 Execution、日志、三维结果和审计保持不可变。
2. Operator/DBA 在平台外完成必要处置；平台不提供 `TRUNCATE`、`DELETE` 或自动建表。
3. Operator 通过恢复接口提交 `remediation_confirmation`，说明处置方式、是否清理及理由、确认时间和非敏感备注；API 只创建独立 `RecoveryProbe(QUEUED)`。
4. Worker 通过独立 RecoveryProbe/ProbeAttempt 的 lease 与 fence 持有目标互斥权，重新实测目标为空，保存证据并签发 `RecoveryGate=VERIFIED`；客户端确认或 ExecutionAttempt 本身都不能通过门禁。
5. 恢复后再次执行请求引用 `recovery_gate_id`，并重新提交
   `source_quiescence_confirmation` 与新的 `statement_version='1.0'`、有限
   `valid_until` 的 `target_exclusivity_confirmation`。
6. Worker 启动 DataX 前仍需生成本次 Execution 的新 `target_empty_evidence`。
7. 目标没有其他未释放目标锁，发布版本、DatasourceRevision、方向授权与
   `TransferPolicy` 仍有效。

任何一项不满足都返回稳定错误并保持 `BLOCKED`，不能只靠 UI 警告放行。

领取事务提交前失败必须整体回滚，Execution 保持从未领取的 `QUEUED`，不产生
Attempt/fence，也不把已有 `RESERVED` 预留转换为 `ACTIVE`；后续领取只是首次有效领取，
该 Execution 的预留保持不变。领取事务一旦提交，任何非唯一成功结果都不得自动回到
`QUEUED`、复用 Attempt 或跳过恢复门禁。

## 后果

- Windows 11 x64 交付必须由 `launcher.exe` 编排固定摘要 Linux 容器；DataX 与 oracle
  不得在 Windows 宿主直接运行。宿主睡眠、关机、Docker Desktop/WSL2 停止都视为单节点
  中断，恢复后必须先由 Worker/reconciler 对账 Execution、RecoveryProbe、目标锁和 fence，
  再允许新复制。
- `Setup.exe` 是否安装成功、容器是否启动和浏览器是否能打开都不能证明一次性复制成功；
  仍须在干净 Windows 11 x64 VM 内完成四方向真实 DataX 与独立 oracle 验收。
- V1 的产品名称可以保留，但范围必须持续标明“一次性复制、非周期同步、非 HA”。
- 首页只统计经独立 oracle 核验的复制成功率和 `verified_records`；DataX 自报写入数只作为诊断，不进入成功 KPI。
- Operator 必须协调源端从运行前检查开始到独立 oracle 完成的静默窗口；如果业务无法停写，应选择后续快照、增量或 CDC 产品，而不是使用 V1 冒充一致复制。
- Operator/DBA 必须协调目标端外部独占窗口；平台锁只能阻止平台自身的并发执行，不能
  证明第三方工具、触发器或数据库用户没有写入。声明版本、有限有效期、撤回/报告和
  oracle 让已知破坏 fail closed，但不能消除未报告或已回滚外部写的剩余风险。
- 故障恢复可能需要外部 DBA 操作，因此 UI 必须提供持久风险说明、处置确认和独立 RecoveryProbe 空表复检证据。
- 未来支持动态源表、非空目标、覆盖、upsert、周期运行或自动恢复时，必须以新 ADR 替代本决策，并同步设计幂等、快照、迁移、授权、威胁模型和真实验收。

## 被拒绝的替代方案

- **仅弹窗提醒后允许非空目标继续执行**：不能形成服务端安全边界，会把可预见的重复写入转嫁给用户。
- **把 DataX 退出码 `0` 定义为成功**：只能证明进程结果，不能证明数据结果。
- **失败后绕过恢复门禁创建新 Execution**：部分写入未知时会扩大污染。
- **V1 自动清空目标表**：超出已接受的无 DDL/无任意 SQL/不修改业务表边界，且引入不可逆删除风险。
- **宣称源表全量读取等于一致性快照**：没有数据库级快照合同，无法在源表持续变化时证明结果时点。

## 迁移与回滚

在尚无已验收产品数据的文档基线阶段，机器契约可直接增加固定策略和三维状态。若已有试验数据，旧 Execution 必须迁移为 `verification_state=NOT_STARTED`，且不得回填为已核验成功。

回滚本 ADR 意味着放弃 V1 的数据正确性承诺，不能只回退文案或字段；必须通过新的 Accepted ADR 明确替代语义和迁移方案。

Windows 安装器升级或回滚不得回滚 PostgreSQL 数据卷、审计锚点、KEK keyring 或恢复
门禁事实。卸载默认保留 Docker named volumes（`des-postgres-data`、`des-log-data`、
`des-workspace-data`）与 `%LOCALAPPDATA%\DataXEnterpriseStudio\backups`；程序版本
回滚后只有数据库迁移兼容检查和 Runtime/插件摘要检查通过才可重新启动。
