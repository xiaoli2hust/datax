# ADR-0014：数据源外部操作短事务与准入边界

- 状态：Accepted
- 日期：2026-08-02
- 决策者：仓库所有者
- 关联：`docs/03_技术架构设计.md`、`docs/05_API接口与前后端契约.md`、
  `docs/09_测试与验收标准.md`、`docs/10_部署运维与安全方案.md`、
  `docs/security/THREAT_MODEL.md`、`FP-P1-026`、`ASR-013`

## 背景

“仅 Web loopback”并不使外部数据库操作成本有界。数据源连接测试和 Schema 读取会执行
DNS、egress lease、TLS/JDBC 或数据库协议连接，以及可能跨多张表的查询。若这些调用发生在
产品 PostgreSQL 的事务内，并且事务持有 Organization、Project、Datasource、Job 或策略行锁，
一个获授权但缓慢的外部端点即可阻塞同一组织的取消、紧急凭据撤销、目标外部独占撤回和其他
控制面操作。

源码审查确认下列五个入口都有该风险，且它们共同属于 Credential Service 的外部数据库
操作面：

1. `create_datasource()` 的新连接探针；
2. `update_datasource()` 中任何 `requires_probe` 的更新；
3. `test_datasource()`；
4. `list_columns()`，即 `GET /datasources/{datasource_id}/schema/tables`；
5. `validate_job()` 中两端的 Schema 采集。

`POST /projects/{project_id}/transfer-policies` 与会变更 source、target 或 `requested_scope` 的
`PATCH /transfer-policies/{transfer_policy_id}` 不是第六、第七个 Credential Service 入口，却会各自
委托上述 `list_columns()` 两次以固定两端真实 scope。因此它们是同一外部操作面的双数据源复合
调用者：必须在任一端外部 I/O 前原子取得 source/target permit，并在两端 probe 间复用同一总
deadline；不得因第二端 429 让第一端已经产生外部 I/O 或审计。

当前候选源码已把上述五个直接入口及双数据源复合调用者迁移到 A/B/C，并加入单 API 进程内
admission、严格 current-credential barrier、总 deadline 和回归测试。该事实只构成 E1 源码/契约证据：真实
PostgreSQL 锁并发已有受控阻塞 probe 的单个 E2 证明，但取消/撤回/revoke/更新全竞态、真
MySQL/PostgreSQL E3 和 Windows E4 尚未取证。因此 `ASR-013` 与 `FP-P1-026` 保持
`IN_PROGRESS`；本 ADR 不能被解读为“连接测试限速漏洞已关闭”的声明。

V1 固定单台 Windows 工作站、一个 API 进程。这个限制允许使用进程内 admission，但不允许
把它误写成多进程、横向扩容或 HA 的共享保护。

## 决策

### 1. 五个直接入口及双数据源复合调用者采用 A/B/C 三阶段边界

所有五个直接入口及其双数据源复合调用者必须使用同一组不可变、非 ORM、不可序列化到响应/日志的
operation snapshot，而不是只修公开的 `test_datasource()` 或 metadata 路由。

**A — 短事务中的授权和快照。** 在认证后、任何 DNS 或数据库连接前，短暂按既有锁序读取并
授权。快照至少绑定 Organization 的状态/row version、调用者 User 的状态/row version、organization/project/datasource、Datasource 当前状态、当前
DatasourceRevision ID/config hash/PhysicalEndpointIdentity、EndpointPolicy 及其当前 revision
ID/policy hash、current CredentialSecret 与 active Envelope 的 ID/version、调用者成员身份和
所需 UsageGrant 与当前 AuthSession（未撤销、未到期、属于同一 principal）。metadata 还绑定
usage、筛选和 cursor scope；任务校验还绑定项目/Job 状态和 row version、Job draft/spec hash
（或等价版本）、源/目标两端、TransferPolicy ID/scope hash、TargetNamespace 与运行时证明。
运行时证明不是只有 Runtime/JAR 三个 hash：还必须冻结 Worker 与 SystemControl 一致的
`host_boot_id`、`reconcile_epoch`、`reconciled_at` 所派生的 proof generation；同一制品在重启或
重新对账后也不得接受旧 B 结果。Developer 的 UsageGrant 同样冻结其 `row_version`，每次撤销或
重新授予必须换代，即使最终状态再次为 `ACTIVE`。

A 阶段不得调用 resolver、egress guard、connector、外部 KMS 或任何外部数据库；它提交后
立即释放所有产品数据库行锁。operation snapshot 不包含明文密码、完整连接串或可被 API
响应/审计序列化的 secret material。

**B — barrier 后无产品数据库锁的外部工作。** 对已有凭据的操作，连接前必须以一个新的极短
credential/status barrier 重新读取并锁定当前 datasource/secret/envelope/policy，确认其仍与
A 快照一致、仍 ACTIVE，复制最小的临时解密材料后立即提交。该 barrier 自身是短产品数据库
事务；只有它提交、所有产品锁释放后，DNS resolve/rebinding、egress lease、解密和 connector
probe/schema snapshot 才可发生。新建数据源没有 current credential，使用已冻结的候选请求密码并在
C 阶段复核，而不得伪称经过 current-credential barrier。
Worker 的 immutable-bound `RETIRED` secret 解密语义不能被直接拿来放宽交互式操作的
“current ACTIVE credential”要求。

每个外部操作必须有总 deadline；双数据源任务校验和传输策略 scope discovery 复用一个 shared
deadline。连接、MySQL TCP 后的握手读写、每条查询（包括单张 Schema
探针内部的每一条 catalog SQL）只可使用当前剩余预算，Schema 分页也必须在每张表前检查
deadline。单条 query timeout 不能作为“最多 200 张表”整体操作的时限证明。明文只用可清零的
临时缓冲，并在 `finally` 中尽力清零。

当前候选实现已对 DNS、egress、连接、MySQL handshake、数据库 statement timeout 和 Schema
内部 SQL 传递剩余预算；但同步 psycopg 在网络黑洞下的 client read/fetch 尚无已验证的强制中断
机制。因此它只能在 I/O 返回后 fail closed，**尚不能被表述为端到端“30 秒一定返回”的证明**。
在引入并验证可界定的 client-side cancel/close 或隔离进程边界前，此 transport-blackhole 缺口是
`ASR-013` 的发布阻塞，而不是可忽略的 E3 缺证。

在状态 barrier 与实际 socket 之间不存在可与外部数据库原子提交的锁。实现必须在连接紧前
再次做 DNS rebinding/egress 校验，并在 C 阶段拒绝过期结果；不得承诺一次已经开始的网络包会
在策略或凭据瞬时撤回后被神奇撤回。如需这种强保证，须另立 ADR 引入可撤销的集中 egress
lease/proxy。

**C — 短事务中的复核和最终副作用。** 外部结果返回后，再按相同锁序重新授权并比较 A 的全部
安全相关绑定。任一 AuthSession、指针、状态、授权、UsageGrant、policy、secret/envelope、
Job/Project 状态或 row version、Job spec、TransferPolicy scope、TargetNamespace 或 runtime
proof 漂移，都返回稳定的 `409 DATASOURCE_OPERATION_STALE`（可重试），且不得返回 Schema
内容、写 EndpointConnectionEvidence、覆盖 `last_test_*` 或写成功/失败审计。只有复核成功才
允许持久化 connection evidence、测试状态、审计和 metadata 响应。

当 C 由 Credential Service 控制时，进入关键锁/读写步骤前必须按共享 deadline 的**当前剩余值**
刷新 PostgreSQL transaction-local `lock_timeout` 与 `statement_timeout`；任务校验的 terminal path
必须在提交前执行 `configure → flush → check`，使晚到的 validation/evidence/audit 写入回滚。它只约束
已明确插桩的单条产品数据库语句，不能把逐语句计时、terminal check 到实际 COMMIT 的极小窗口，或
同步客户端 transport blackhole 伪装成端到端 hard cap；这些仍属于 `ASR-013` 的关闭条件。

凡同一事务同时需要 `SystemControl` 与组织事实，固定锁序为
`SystemControl → Organization → Project → Job → Datasource → revision/policy/credential/grant`。
已完成的 Execution idempotency replay 使用独立、只读的短事务；它不同时持有 SystemControl，
并且必须将 record 的 `resource_id` 与请求的 Job 重新绑定，不能因路由模板共享 scope 泄露另一 Job
的历史 Execution。相同原则适用于所有模板化路由的 idempotency：创建必须把 durable
Datasource/Job 重新绑定到请求 Project，发布必须绑定 Job，取消、独占撤回与 remediation 必须精确
绑定 Execution，rerun 必须验证新 Execution 的 `rerun_of_execution_id`。scope、request hash、
resource 与已保存 response 任一不一致都返回 `409 IDEMPOTENCY_CONFLICT`。

因此，旧密码/端点的失败也不能覆盖新配置的测试状态；Developer 在读取期间失去精确 grant
也不能得到旧 metadata。cursor 必须仍绑定 A 阶段的 revision/scope，旧 cursor 保留明确的
scope-mismatch/stale 失败语义，不能被放宽为第一页成功。

### 2. 创建、更新和任务校验的专门约束

- 创建在 B 前只捕获 project、active policy revision 和 canonical request hash；不得把
  `response=None` 的 idempotency reservation 跨外部 I/O 持久化。C 阶段重新复核后才 claim/
  complete idempotency 并创建 datasource/revision/secret，以免 crash 留下永久
  `IDEMPOTENCY_IN_PROGRESS`。允许并发相同 idempotency key 重复无副作用探针，但最终只能
  创建一个业务对象。
- 有探针的更新必须绑定原 datasource 的 ETag/security pointers、候选 revision canonical hash
  和候选 policy；C 阶段不一致即返回冲突，绝不能把旧探针成功用于后来改变的 endpoint 或
  password。纯描述性、无外部 I/O 的更新可保持短事务。
- 任务校验必须为 source/target 分别捕获 snapshot，在无锁 B 阶段采集两端 schema facts，C
  阶段重新验证 AuthSession、项目/Job 状态、两端 datasource、grant、TransferPolicy scope、
  TargetNamespace 和 runtime proof。将 validation material 接受为当前 `SyncJob.validation_report`
  与 `status` 的写入，以及对应 evidence/audit，必须与 C 的复核处在同一短事务中；校验不得创建
   或修改 `JobVersion`，也不得在两次独立提交之间接受已过期 material。PUBLISHED/ARCHIVED Job
   必须在 A 阶段、任何外部 I/O 前拒绝。
- 传输策略创建和会重算 scope 的 PATCH 必须先捕获两端 revision/context，再一次性取得两个
  datasource key；两个 `list_columns()` 仅可复用该 live lease 和同一 shared deadline。若未取得
  permit，429 在两端 resolver、connector、解密、audit 和新的幂等状态之前返回；若任一端在 B/C
  中失败，不能创建或修改策略。
- egress guard/lease/attestation 抛出的错误属于平台安全依赖，必须保留稳定 code 并返回 503，不能
  重标为用户数据库凭据或 metadata 错误。只有显式可用性 code 集合可人工重试；若错误在共享预算
  已耗尽后才被观察到，C 复核通过时总 deadline 的 503 结果优先。

### 3. 准入语义

数据源外部操作 admission 是单 API 进程内、非阻塞、不可等待的资源控制：原子取得全进程、每
organization 和每 datasource 的在途配额；同一 datasource 和同一 organization 均最多一个在途
操作。创建在已认证的 completed-idempotency replay 读取后、候选外部工作前取得空 datasource-key
permit；已有 datasource 的 test、metadata、带 probe 的 PATCH、任务校验以及传输策略 scope probe，必须先完成只读的
A 阶段资源身份/授权验证并释放产品锁，再按稳定排序取得真实 datasource key。这样用户提供的
不存在 UUID 或无权资源永远不能进入 retained admission state；纯描述性或 DISABLED-only PATCH
及不触发 scope probe 的传输策略修改不属于 external lane。任务校验和传输策略 scope probe 必须一次性取得 source/target 两个 datasource key，取得失败即整体
拒绝，不能部分持有后等待。实现还必须对 `TEST` 施加 datasource 级最小间隔/token bucket，并为
所有外部操作配置有目标硬上限的总 deadline；当前同步 PostgreSQL transport 的 network-blackhole
中断实现仍为发布阻塞，不能把配置值误称为已证明的端到端 hard cap。

拒绝统一为 `429 DATASOURCE_OPERATION_ADMISSION_LIMITED`、`Retry-After`、`X-Request-Id`
和 `Cache-Control: no-store`。429 不调用 resolver/connector/解密，不写 audit 或幂等状态，
并在成功、业务错误、超时和异常路径都释放 permit；已完成的创建幂等 replay 是无外部 I/O 的只读
返回，允许在 admission 之前直接返回。不得在认证前按邮箱、IP、密码或 User-Agent 分桶，也不得
使用持久数据库行锁来实现 admission。

默认容量、interval 和 deadline 必须在 Settings/OpenAPI/部署说明中明确且有硬上限；未来增加
Uvicorn workers、Compose API scale、旁路入口或 HA 前，必须以新 ADR 定义共享、围栏的
admission，当前进程内计数不得被宣传为多实例保护。

## 分阶段实施与验证

1. 已建立 snapshot DTO、strict current-credential barrier、总 deadline、admission、409/429/503
   Problem 契约和 E1 测试夹具；仍不宣称漏洞关闭。
2. 已迁移 `test_datasource()` 与 `list_columns()` 到 A/B/C，并加入 stale/no-disclosure/no-audit
   回归。
3. 已迁移 `create_datasource()` 与 `update_datasource()`，保持幂等、ETag、secret rotation 与
   失败关闭语义。
4. 已迁移任务校验，并将 C 复核与当前 Job validation state/evidence/audit 接受原子化。
5. 只有五个直接入口及双数据源复合调用者均完成，并通过下列证据后，才可把 ASR-013 标为已关闭：
   - 单元/契约：任何 AuthSession、security pointer、grant、secret/envelope、policy、Job/project
     state、TargetNamespace、runtime proof 或 Job/transfer scope 漂移均为 409，且无陈旧
     evidence/audit/响应；429 不触发外部副作用，deadline 503 不持久化 B 结果，permit 始终释放；
   - 真实 PostgreSQL 并发：connector 在 B 阶段阻塞时，取消、目标独占撤回、secret revoke、
     datasource/job/policy 更新不等待 organization 锁；使用时间界限或 `pg_locks` 证明；
   - 真 MySQL/PostgreSQL E3：总 deadline（含 transport blackhole 的 client-side 强制中断）、DNS/egress、metadata 分页、失败/恢复与限速在
     固定 Runtime 中可复现。SQLite 或 mock 不能证明 PostgreSQL 锁行为，也不能作为 E3。

## 后果与限制

- A/B/C 用乐观复核替代跨网络的悲观组织锁，正常控制面不再被单个慢端点串行化；代价是配置
  变化期间调用方得到明确的可重试 stale 响应，而非使用旧结果静默成功。
- admission 限制的是昂贵外部操作，不是身份认证或授权替代；A/C 仍必须分别执行服务端授权。
- API 角色的 `idle_in_transaction_session_timeout` 可作为意外事务的附加防线，但不能替代本
  ADR：它既不能保证外部 I/O 公平，也不能安全地关联旧探针结果与新 revision。
- 候选实现、契约和 E1 测试不会改变真实 PostgreSQL/E3/Windows E4 的缺口。本 ADR 仍保持
  `ASR-013=IN_PROGRESS`、发布 `BLOCKED` 与 Windows E4/E3 未验证状态，直到真实外部证据随
  实现一并交付。
