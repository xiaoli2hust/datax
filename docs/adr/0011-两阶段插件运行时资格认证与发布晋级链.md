## 背景

当前普通产品路径正确地采用 production deny-all：没有受信 Windows E4 证明时，普通
Execution 创建、恢复后再次执行、Worker 领取和 Worker 启动均拒绝。这条失败关闭链不能
删除，也不能把测试注入、设置项、环境变量或自申报 JSON 接到生产路径。

但真实 E3/E4 需要候选实际运行，因而出现资格自举环。更隐蔽的问题是，如果把事后生成的
E4/资格 JSON 写进 Worker 镜像，Worker digest 已改变；如果让资格文件绑定最终 Setup 或
release manifest、而最终 Setup/manifest 又包含该资格文件，则产生递归哈希。任何一侧用
“重新计算一次哈希”掩盖循环，都会失去“证据对应同一候选”的含义。

ADR-0009 已规定普通用户执行还必须把最终 Windows E4 状态与同一 F 的有效 PR 绑定，
ADR-0010 已规定公开发布还必须有独立 Windows harness 与 hosted OIDC attestation。二者
尚未定义：

1. 如何在不放开普通用户路径的前提下，让受保护 harness 对不可变 Runtime 进行真实取证；
2. 如何把资格结论放入最终离线 Windows 包，而不改变被资格结论绑定的 Runtime payload；
3. 如何区分“可以在受控候选中进行最终验证”与“已获公开发布批准”。

## 决策

### 1. 固定区分七类对象和四个结论

| 名称 | 作用 | 是否可给普通用户 | 是否等于公开发布批准 |
|---|---|---:|---:|
| P：不可变发布 payload | API/Worker/Web/egress/PostgreSQL 五镜像、Worker Runtime、插件、锁、SBOM/许可和构建身份的可复核集合 | 否，尚未包装/晋级 | 否 |
| QH：Harness Qualification | 只给受保护 Windows harness 的短期、一次性、签名运行许可；仅用于私有 payload qualification，不是 E4 | 否 | 否 |
| PAG：Phase-A Qualification Grant | 受保护私有控制面把一个已验证、一次性消费 QH nonce 的资格收窄为一个精确 P、harness、Reader/Writer pair 的授权记录 | 否 | 否 |
| PEA：Phase-A Execution Authorization | 0022 private ledger 把既有 PAG 收窄为**一条**精确 Execution 的 append-only 授权；issuer authorize / consumer read 只用于未来 Phase-A 私有四检查点，不能由普通路径读取、修改、领取或提交 | 否 | 否 |
| QR：Release Qualification | 对精确 P 的 detached、签名“普通模式资格”授权，供私有最终候选进行无 QH/PAG/PEA 的正常模式验证 | 只能随私有候选受控使用 | 否 |
| F：最终安装包集合 | Setup、Launcher、release manifest、QR、Compose/资源和固定镜像锁 | 公开前只可由 Release/QA 持有 | 否 |
| PR：公开发布晋级记录 | 对 F、完整验收和 hosted OIDC provenance 的最终发布裁决 | 是，作为已发布版本 | 是 |

QH、QR、PR 的语义不得互换：

- QH 只回答“这个受保护 harness 是否可为一次指定 P 运行真实取证”；Phase A 的 payload
  qualification 明确不是 Windows E4，QH 永远不是插件认证状态、普通用户能力或发布许可。
- PAG 只回答“受保护私有 Phase-A 控制面是否可为一个已验证 QH、精确 harness 和一个
  Reader/Writer pair 创建一次 qualification attempt”；它不是 QH 的替代、不是测试结果，
  也不得改变普通 API/Worker 的 deny-all、插件状态、`ordinary_user_executable` 或发布许可。
- PEA 只回答“某一个已存在的 `PHASE_A_HARNESS` Execution 是否已由 0022 protected issuer 将既有
  ACTIVE PAG 与其不可变 JobVersion/Datasource/Policy/TargetNamespace facts 原子绑定”。它是
  append-only record，`grant_id`/`execution_id` 各自唯一，不存独立 state，只能由 PAG `ACTIVE`、
  QH 时间窗和 consumer read 的全量 current-fact 联结派生有效性。它不是对 PAG 的可变补丁、
  不是普通 Execution capability、也不绕过角色、凭据、静默源、目标独占、egress、oracle 或四检查点。
  每个未来 private rerun 都必须有新的 Execution 和新的 PEA。
- QR 只回答“这个精确 P 是否已取得足以在受控最终候选中进行正常模式 E4 的资格”；它不
  表示 Setup 已通过最终 E4，也不表示 GitHub release 已批准。
- PR 才回答“精确 F 已通过最终 Windows 发布门禁，且候选根已由独立 hosted attestor
  证明来源”；没有 PR 时不得公开上传、标记 stable/release 或对用户分发 F。

ADR-0009 中的 `WINDOWS_E4_CERTIFIED` 只能在 Phase B 对精确最终 F 完成无 QH/PAG/PEA 的正常模式
Windows E4 后，由受信 reader 依据该证据派生；QH、PAG、PEA 和 QR 都不能产生这个状态。该状态证明
一个插件有与 F/P 绑定的最终 E4 证据，却不替代 F 的公开发布批准。普通用户只能获得同时
具有该状态和同一 F 有效 PR 的发布制品；私有候选因 QR 获得的普通模式测试资格专供
Release/QA 完成 Phase B，不能作为对外宣称或普通用户能力。

当前候选的 `plugin-manifest.v2` 已增加 `evidence.release_promotion_ref`，并将普通用户
可执行性改为同时要求 Phase-B E4 与该引用，而不是由 E4 直接推断。该引用目前仍只是
不透明字符串：当前代码只校验存在性、格式和 Reader/Writer 配对一致性，尚无受信 reader，
也没有带签名、可独立验证的候选根/最终 `F` 绑定。它在 production deny-all 的当前状态下
没有放开任何能力，且不能单独实现本 ADR 的“同一 F 有效 PR”公开放行语义。后续必须以同一
纵向切片原子引入结构化签名发布晋级契约及受信 reader，并同步更新公开能力契约、OpenAPI、
服务端模型、四检查点和负向测试；不得仅靠“E4 为真”或“引用字段非空”推断公开发布。

### 2. P 必须先固定，并以 payload root 消除递归

先构建不含 QH、PAG、QR、最终 release manifest 和最终 Setup/Launcher 的 P。未来的
release-payload.v1 契约至少必须 canonical 地记录：

- 仓库、受保护 source ref、精确 commit、产品版本、release candidate、目标 Windows
  x64 与 Linux amd64 平台；
- 五个镜像的 repository@sha256、特别是 Worker image digest；
- DataX/JDK 版本、runtime-manifest、运行时目录树和每个插件 JAR 的路径/摘要；
- 每个插件的上游来源、参数/边界契约版本、依赖/SBOM/许可证和再分发审查摘要；
- 与 P 同时生成的构建身份文件、镜像锁、源码/镜像 SBOM 和许可清单摘要。

payload_root_sha256 的计算必须固定为：

    SHA-256(UTF8("DES-RELEASE-PAYLOAD-v1\n") || RFC8785(payload_without_root))

P 不得包含 QH、PAG、QR、QH/QR 的签名、最终 release manifest、最终 Setup、最终 Launcher，
也不得通过“稍后回填”改变 P 的任一 digest。任何 API/Worker 代码、内置公钥、Runtime、
插件或镜像锁变化都会形成新的 P，并使旧 QH/QR 失效。

### 3. Phase A：受保护 qualification harness 只为真实取证打开最小通道

1. Release 构建先产生并独立验证 P/payload root，仍不允许普通 API/UI 运行。
2. Harness Qualification Authority（HQA）仅在受保护环境中为这一个 P 签发 QH。QH 至少
   绑定 payload root、commit、release candidate、全部镜像 digest、Worker Runtime/插件
   摘要、固定 harness 身份/环境、一次性 nonce、签发时间、最长 24 小时有效期和
   purpose=QUALIFICATION_HARNESS。
   为避免 QH 被误作任意插件启动开关，受保护私有控制面还必须在**先独立验证 P 与 QH 后**
   才建立 Phase-A Qualification Grant（PAG）。PAG 只能在 protected issuer/durable ledger
   中创建、读取、撤回或到期，原始 QH nonce 单独原子消费，且至少固定：`grant_id`；P 的
   `payload_root_sha256`、完整 P binding 的 `payload_binding_sha256` 与 identity binding；
   精确 harness identity、环境 manifest SHA-256 与 harness version；QH 的
   `issuer_key_id`、`qualification_id`、`document_sha256` 和 `nonce_sha256`（即 nonce hash）；一个
   Reader/Writer plugin 名称及其 JAR SHA-256；`issued_at`、`not_before`、`valid_until`
   和 `state`。`payload_binding_sha256` 固定为 `SHA-256(RFC8785(QH.payload_binding))`，
   `document_sha256` 固定为包含 `signature` 的 canonical signed QH document 的 SHA-256，
   `nonce_sha256` 固定为 `SHA-256(UTF8(QH.nonce))`；三者均不得附加域前缀，PAG 不得保存或
   记录原始 nonce。消费者必须逐项比较 PAG、已验证 P 与已验证 QH，且只接受 `ACTIVE`
   状态；原始 QH nonce 由独立 durable nonce ledger 原子消费，grant ledger 只允许
   `ACTIVE -> REVOKED|EXPIRED` 的原子单调转换，grant 有效窗口必须完全落在 QH 有效窗口内。
   PAG 只是在受保护私有 Phase-A 内的授权
   事实，不是 E3/E4、Plugin Manifest、QR、最终 F 或公开发布结论。

   J0b.1 的 `phase-a-execution-authorization.v1` 现在精确描述 0022 的 PEA consumer read
   record。0022 protected issuer 在受保护、可审计的事务中，只能对一个已存在、尚未领取、
   `authorization_mode=PHASE_A_HARNESS`、仍 pending 的 Execution 和一个仍 `ACTIVE` 的 PAG
   创建 PEA，并强制 `UNIQUE(grant_id)` 与 `UNIQUE(execution_id)`。PEA 冻结
   `authorization_id/grant_id/execution_id/project_id`、JobVersion 的 ID/`version_artifact_hash/spec_hash`
   与 runtime pair、两侧 DatasourceRevision 和 EndpointPolicyRevision 的 ID+hash、TransferPolicy
   `scope_hash/row_version`、TargetNamespace physical identity，以及 P/runtime/harness/QH 的交叉
   检查摘要和**仅 nonce SHA-256**。它不得持有原始 nonce、凭据、连接信息、表名、DataX 配置、命令
   或结果，且不存 PEA `state`。consumer read 必须逐项重读并比较 PAG、Execution、JobVersion、
   revision、policy、namespace 与其他当前事实；只在 PAG `ACTIVE`、QH 有效且全部一致时返回。
   “其他当前事实”至少包括：Project `ACTIVE`、Job `PUBLISHED`、两侧 Datasource 与 EndpointPolicy 的
   `ACTIVE`/current revision、Organization/Project/physical identity/TargetNamespace 的 scope+engine、
   active TransferPolicy 的 revision/physical scope/hash/row version、未撤回的目标独占以及
   engine→Reader/Writer 配对。任一 parent/current/scope/engine/pair 漂移必须返回无授权。
   0022 实现数据库唯一性、append-only、原子性和 read revalidation；仍没有 private create/rerun/
   claim/start 四检查点或 harness 调用链，不能把 PEA 当 DataX start 授权。PAG 撤回/到期或任一
   binding 漂移都必须使后续私有检查失败关闭。
   `20260802_0023` 只补入 PEA 存在 + PAG/QH active-window 检查的、未接线的 global lock/fence
   primitive：它不会替 consumer read 的全量 current-fact revalidation，也不能把 PEA 变成 DataX
   start 授权。未来真实 runner 仍须在每一硬检查点调用完整 PEA/PAG/QH/current-fact 复核。
3. QH 的签名采用带域分隔的 RFC8785 canonical payload；签名验证只从 P 中固定的 HQA
   公钥 keyring 按 key_id 选择公钥，不接受 envelope 自带或环境变量提供的公钥。
4. QH、PAG 与 PEA 只能经单独的受保护 private source/override 进入精确 harness 的 qualification
   控制路径。标准 compose.yaml、Setup、Launcher、公开 candidate artifact、备份/诊断包、
   普通 API/UI、环境变量和普通用户配置中不得含 QH、PAG 或 PEA；标准启动若发现这些资源、
   override 或意外 qualification source 必须失败关闭。标准系统备份与诊断必须固定排除完整
   `des_phase_a_qualification` schema；普通 restore 不得复制、恢复或重新激活任何 Phase-A
   nonce/grant/PEA authority。当前 dump 保留 `alembic_version=20260802_0023` 却排除该 schema，故真实
   restore/bootstrap/start 继续 `BLOCKED`。未来若继续资格化，必须由独立受保护 issuer 在新
   restore epoch 后重新验证 P/QH 并重新签发；当前没有 runtime issuer 或受保护凭据配置，因此这
   不是现有 restore/reissue 路径。
5. 在 J0b 完整私有运行通道落地后，QH/PAG 只可配合精确 PEA 允许 harness 的精确候选运行
   真实 API/Worker/DataX 路径以收集 E3 和私有 Windows harness/payload qualification（明确不是
   E4）证据。PEA 必须在私有 Execution 创建、恢复后再次执行、Worker 领取、Worker 启动四个
   检查点逐项重读；任一缺失、重复、撤回、过期或 binding 漂移均失败关闭。PAG 还必须限制为所选的
   一个 Reader/Writer pair，并且不改变公开
   plugin-manifest.v2 中的普通用户状态，
   ordinary_user_executable 仍不得因 QH/PAG 变为 true，也不得把 QH、PAG 或 TEST_INJECTION
   序列化为 E3/E4 事实。
6. protected harness 必须固定 checkout、测试集合、路径和期望 oracle，不能接受待测
   manifest 提供的命令、测试名或结果。它执行真实 MySQL 8/PostgreSQL 15、独立 oracle、
   Windows 11 x64/Docker Desktop/WSL2 行为并保留失败证据。
7. Release/QA 独立复核 Phase A 证据后，Release Qualification Authority（RQA）才可为
   P 签发 QR；HQA 不得签发 QR。

QH 是一个受限 capability，不是 boolean 开关。特别禁止 DES_ALLOW_E4 一类设置、把
ExplicitTestPluginCertificationSource 暴露到 settings/环境变量、或用测试数据源替代
HQA/RQA 签名。

### 3.1 J0b.1 当前硬禁用状态与私有 Worker/runner 启用前门禁

当前落地的是 E1 数据库/契约基础和受限 PostgreSQL 15 E2：0023 已让私有 SQL primitive 复用全局
`TargetCopyLock`、`ExecutionAttempt` 与 `Execution.fence_epoch`，以 NOLOGIN
`datax_phase_a_runner` 的六个 `SECURITY DEFINER` entrypoint 提供 reserve/claim/heartbeat/
recovery/release/read。它既没有 runner 登录 provisioning，也没有任何产品调用者。
**当前不存在可运行的私有 Phase-A Worker 或 runner，且必须保持硬禁用。** 即使某条
`PHASE_A_HARNESS` Execution 已由受限 issuer 写入 PEA，标准 API、Worker、recovery/reconciler、公开
日志和维护路径也不能创建、读取、修改、领取、启动、对账或展示它；标准 Compose/Launcher/Settings
没有 issuer/consumer/runner 凭据或 private override。PEA read record 不是启动许可，当前不能产生
DataX E3、Windows E4、QR 或发布结论。

未来受保护 Worker/runner 的单独纵向切片在**全部**下列硬门禁落地并经负向验证前，不得改变该状态：

1. **私有执行锁与 fencing（仅数据库前置原语已完成，门禁未关闭）。** 0023 已用**同一**
   `TargetCopyLock` partial-unique namespace index 约束 `STANDARD` 与 `PHASE_A_HARNESS`，并在
   private `RESERVED -> ACTIVE -> RECOVERY_REQUIRED -> RELEASED` 生命周期中写入单调
   `Execution.fence_epoch`/`ExecutionAttempt`、worker/host-boot/cgroup identity。PAG 撤回/到期使
   heartbeat 失败关闭，`RECOVERY_REQUIRED` 不自动释放、重试或重新领取；API/Worker/egress RLS
   仍看不到 private lock/attempt，普通创建只得到通用 `TARGET_ACTIVE_EXECUTION`。这只是 SQL
   primitive：没有 protected runner、进程树/Popen、崩溃受保护对账、完整 PEA/current-fact/confirmation
   revalidation 或 audit checkpoint，故不能代替私有 claim/start 门禁，也不改变硬禁用。
2. **私有确认检查点。** 在私有 create/rerun、claim、Popen 前和 oracle/终态前重读 PEA/PAG/QH/current
   facts，并把 V1 的源静默确认、目标外部独占确认及其撤回/过期事实纳入失败关闭判断；不能借用普通
   Execution 的旧确认、忽略 window 或以 API 请求体重新声明。
3. **私有审计检查点。** 对 authorization、lock acquisition、每个 revalidation、runner start/stop、
   取消、oracle 和终态写入追加受保护、可关联 execution/fence 的审计事实；不记录 raw nonce、凭据、
   DSN、完整 DataX 配置或私有原序日志。没有这些 checkpoint，不得声称可追溯 Phase-A 取证。
4. **凭据、日志与维护隔离。** 受保护 runner 必须取得独立、最小、可撤销的专用凭据；普通 Compose、
   Launcher、API、Worker、恢复、取消、rerun、诊断和公开日志路由不得获得或处理它们。私有日志存放、
   脱敏、读取和保留策略必须随 runner 一起设计；现有普通日志路径不能作为私有 runner 输出。
5. **备份隔离。** 标准 backup 已在 `pg_dump` 前后（PostgreSQL 停止前）拒绝任何
   `PHASE_A_HARNESS` public Execution；未来 protected backup/restore 必须有独立原子契约，不能绕过该
   gate、筛表或筛日志目录。每项失败均保持普通备份失败关闭。

完成这些门禁只让受保护 Phase A 具备开始真实 E3 取证的资格，**仍不等于** E3 已通过、更不等于
Windows E4、普通用户能力或公开发布。

### 4. QR 是 detached 签名授权，不是可自证的配置文件

QR 的未来契约必须至少包括 authorization_id、schema_version、purpose、
issuer_key_id、issued_at、not_before、valid_until、payload_root_sha256、candidate/commit、
镜像/Runtime/插件绑定、Phase A E3/私有 Windows harness/payload qualification（非 E4）
证据描述及其哈希、完整依赖/
许可证复核结论和逐插件资格行。其签名输入必须固定为：

    Ed25519.Sign(
      RQA_private_key,
      UTF8("DES-RELEASE-QUALIFICATION-v1\n") || RFC8785(payload_without_signature)
    )

RQA 公钥必须在 P 的受保护信任策略中固定，按 key_id 从 allowlist 选择；QR 不能携带一把
可被自身信任的公钥。RQA 私钥必须独立于 Authenticode 代码签名私钥、GitHub OIDC token
和 HQA 私钥，并只能在受保护 release authority/HSM 或等价不可导出机制中使用。

未来受保护的 Phase B qualification reader 只能在以下全部成立时从 QR 导出**私有
Phase B 测试资格**：

1. canonical 格式、域分隔签名、key_id、purpose、签发/生效/到期和撤销策略均有效；
2. QR 的 P root 与当前 API/Worker build identity、镜像锁、Worker digest、Runtime tree、
   插件 JAR 哈希、插件依赖/许可证记录逐项一致；
3. 当前请求的 Reader/Writer/版本恰在 QR 的资格行内，且对应证据描述完整；
4. QR 只读资源来自被 Launcher/manifest 哈希约束的安装包路径，而不是可由普通用户配置
   指定的任意路径；
5. QR 不得单独派生 `WINDOWS_E4_CERTIFIED` 或普通用户可执行性；任一输入缺失、未知 key、
   签名错误、purpose 错误、过期、候选/commit/镜像/插件错配或证据不完整时，API、rerun、
   Worker claim/start 四个普通用户检查点全部恢复 deny-all。

该 reader 不得在产品运行时调用 GitHub、gh CLI、网络证明服务或下载新证据。离线产品只能
验证随受控制品携带的 RQA 签名和自身已经固定的 P 身份；密钥妥协后的撤销/轮换必须通过
新的受信制品和新的 QR 处理，不能假称离线旧安装获得即时全局撤销。

### 5. Phase B：先形成 F，再以精确 F 的正常模式证据派生 E4 状态和发布晋级

取得 QR 后才构建最终 F：

1. 最终 release manifest 仅绑定 payload_root_sha256、QR 文件哈希/签发者标识、固定
   Compose/镜像锁、资源和安装版本；签名 Launcher 编译期绑定该 manifest 的哈希，并在
   启动时验证 QR 资源。
2. QR 不绑定最终 release manifest、Setup 或 Launcher 的哈希；P 也不包含 QR。由此
   避免 QR ↔ manifest ↔ Setup 或 QR ↔ Worker image 的自引用环。
3. F 在干净 Windows 11 x64 上以标准 Compose、标准 Launcher、无 QH/PAG/PEA override 的正常
   模式执行最终 E2E-WIN、四方向 DataX、安装/重启/睡眠/恢复/卸载等验证。只有这组精确
   F 的 Phase B E4 证据才可为与 P/F 绑定的插件派生 `WINDOWS_E4_CERTIFIED`；QR 只使
   精确 P 的插件可供受控候选进行正常模式测试，不能改变 F 仍是私有候选的事实。
4. 最终候选根 v2（或由后续 Accepted ADR 指定的等价新契约）必须同时绑定 F 中实际
   Setup/Launcher/release manifest/QR/P、最终 acceptance manifest、Phase B Windows
   证据、场景 catalog、环境、SBOM/许可证和所有文件哈希。
5. GitHub hosted attestor 重新验证最终候选根和文件集后，以固定 workflow、commit、
   OIDC issuer、hosted runner 和 deny-self-hosted-runners 条件签发 provenance。随后
   发布 validator 重新计算哈希并聚合 P0/P1、Discovery、签名、E3/E4 与场景结果，才可
   形成 PR 并创建公开发布。没有这条同一 F 的 PR，`WINDOWS_E4_CERTIFIED` 也不得变成
   普通用户可执行性或公开生产发布。

现有 candidate-root.v1 必须继续只表达 BLOCKED/release_approved=false，不能通过修改
其枚举或填充字段偷渡 PASS。Phase B 所需的 candidate-root.v2、release-payload、QH/QR
schema、reader、validator 和 workflow 均尚未实现。

### 6. 信任角色、可替代性和不可替代性

| 信任角色 | 可做的事 | 不可替代/不可做的事 |
|---|---|---|
| HQA | 对 P 签发短期 QH | 不能签发 QR、不能批准公开发布 |
| 受保护 Windows harness | 运行 Phase A/Phase B 真实行为测试 | 不能自行声明可信、不能签候选根 |
| RQA | 依据独立复核的 Phase A 证据签发 QR | 不能替代 Authenticode、Windows 行为或 OIDC provenance |
| Authenticode 签名服务 | 签名 Setup/Launcher 并提供可信时间戳 | 不能证明 DataX 或独立 oracle 通过 |
| hosted candidate-root attestor | 证明候选根由固定 GitHub workflow/commit 产生且未被替换 | 不能证明 Windows 基线、真实数据库或物理行为 |
| Release/QA 复核者 | 审核证据、P0/P1 和发布清单 | 不能用人工勾选覆盖缺失的签名/证据 |

真实 Windows 11 x64、Docker Desktop/WSL2、真实数据库、受保护 runner、HQA/RQA 私钥、
Authenticode 证书/时间戳、GitHub protected environment 和 hosted OIDC attestation 都是
外部 TCB。它们不存在或未真实运行时，结果必须为 BLOCKED/NOT_RUN，不能由本 ADR、
单元测试、结构化 JSON 或 EXE 文件存在替代。

## 后果

- 保留 production deny-all，且为真实 E3/E4 提供一条最小、可审计、不能公开复用的
  qualification 通道。
- 将“payload 资格”“最终包验证”“公开发布批准”拆开，避免把 QR 或 final manifest
  塞回 Worker image/Setup 造成自举循环。
- Windows 本地产品仍不需要 Linux 服务器、GitHub runner 或在线 attestation 服务；这些
  仅是构建/发布 TCB。
- 需要新增签名 authority、固定公钥策略、私有候选分发控制、受保护 Windows harness 和
  hosted attestation，实施成本显著增加，但这些控制不能由文档或 CI 绿灯伪造。

## 当前实施状态

当前仓库已有 `release-payload.v1`、`harness-qualification.v1`、
`phase-a-qualification-grant.v1` 与 J0b.1 的
`phase-a-execution-authorization.v1` Schema，以及 P/QH parser + private Phase-A
payload/runtime/job binding + durable nonce/grant/PEA persistence 的 E1 进行中基础件。
`datax_studio.release_qualification` 拒绝非 UTF-8/JCS、重复键、超深 JSON、超 6 位小数秒和
非有限数；重算 P root 并要求调用方独立钉住该 root；只从已验证 P 的 HQA keyring 按 key ID
验证域分隔 QH。J0a 的 `issue_phase_a_grant` 只在 P、QH、当前 runtime 和不可变 JobVersion
pair 全部匹配后，把固定字段交给调用方提供的私有原子 recorder；它没有 Settings/env 可配置的
nonce callback。

`20260802_0021` 要求 PostgreSQL superuser 执行，创建无登录的 `datax_phase_a_ledger_owner`、
`datax_phase_a_issuer`、`datax_phase_a_consumer`。迁移将私有 schema、nonce/grant 表和既有 guard
functions 交给 ledger owner；不授予任何成员关系或直接 DML。issuer 仅获 issue/revoke、consumer
仅获 read 的精确执行权；每个 entrypoint 都是 `SECURITY DEFINER`，固定
`search_path=pg_catalog,pg_temp` 并以 `session_user` 再检 caller。issue 在同一个数据库事务中写
`(issuer_key_id, nonce)` 的一次性消费事实与不可变 PAG；read 只返回仍 current 的 `ACTIVE` grant，
并在读前令到期 grant 单调转为 `EXPIRED`。private adapter 只能接收未来受保护 harness 显式注入的
专用 Engine，读取后重建并复检非秘密 binding；它不接受请求体、Settings 或环境变量的 grant/DSN。
若任一私有角色名或任何相关成员关系预先存在，0021 在创建/转移 ledger 对象前失败关闭，绝不尝试
“清洗”该 principal；ledger owner 的默认 ACL 同时撤销其未来新建函数的全局 `PUBLIC EXECUTE`。这两项
规则只减少数据库角色/函数旁路面，不构成 harness 或 HQA/RQA 信任。

J0a grant 刻意没有 `execution_id` linkage。`20260802_0022` 以独立 PEA 补充它：私有
`phase_a_execution_authorizations` 表 append-only，对 `grant_id`/`execution_id` 各自唯一；它复制
非秘密 execution/job/version/revision/policy/namespace/P/runtime/harness/QH facts 和**仅 nonce SHA-256**。
issuer `des_authorize_phase_a_execution` 对锁定、pending、`PHASE_A_HARNESS` Execution 和有效 PAG
原子写入 PEA，并把该 private execution 保持为 `BLOCKED`、原因
`PHASE_A_PRIVATE_WORKER_NOT_IMPLEMENTED`（不转换为 queue-eligible）；consumer
`des_read_active_phase_a_execution_authorization` 只有在 PAG `ACTIVE`、QH 时间窗及全部 current facts
仍相等时才返回记录。PEA 不存独立 state。0022 还使普通 API 创建、普通 Worker claim、normal
recovery/reconciler 与 logs path 显式只处理 `STANDARD`，不能读取、修改、领取、推进或暴露 PEA/private row。
0022 还在 `datax_api/datax_worker/datax_egress_guard` 的直接数据库连接上启用 parent-linked RLS：
`executions` 及 attempt/lock/event/cancel/log/recovery/evidence/work-termination descendants 仅在 parent 为
`STANDARD` 时可见/可写，不能通过后代表绕过 Python query filter。无登录 ledger owner 仅在其受限
`SECURITY DEFINER` 函数中可读取 protected parent。该 RLS 已在本轮真实 PostgreSQL 15 E2 由
API/Worker direct-DB 负向验证（脚本退出 `0`，pytest `30 passed`）。保护 public `executions` trigger 的

`20260802_0023` 再创建独立 NOLOGIN `datax_phase_a_runner`，但没有为它配置产品可用 login、
Engine 或任何 Compose/Settings/Launcher 接线。它只获六个固定 `SECURITY DEFINER` lock/fence
