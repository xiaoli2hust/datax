## 1. 审查的第一性原理

一个数据复制产品只有同时回答以下问题，才能称为“完成”：

1. **价值是否真实**：目标用户是否真有这个问题，是否愿意承担本产品的
   源静默、空目标和外部独占操作前提。
2. **复制结果是否真实**：DataX 退出码、页面成功提示和产品自报统计都不是
   数据正确性；只有独立 oracle 可以做最终判定。
3. **失败是否安全**：取消、失租、睡眠、断电、恢复中断和部分写入不能被收敛为
   假成功，也不能在不知情时向目标继续追加。
4. **安全边界是否真正强制**：数据库权限、容器网络和 Worker fence 必须由不同
   边界强制，不能只依赖应用层约定。
5. **证据是否能证伪**：验收系统必须校验证据内容及其与需求、测试、候选版本、
   环境和 Execution 的绑定；“任意文件有正确哈希”不能构成 PASS。
6. **交付物是否与承诺一致**：目标是 Windows 可安装产品，不是一个独立 DataX
   命令行文件，也不是只在 macOS/Linux 上可编译的 EXE 骨架。
7. **“支持”是否可验收**：上游源码存在、插件能被编译、运行时已打包、产品
   已开放、真实 E2E 已通过是五个不同状态。

## 3. 状态和关闭规则

| 状态 | 含义 |
|---|---|
| `OPEN_CONFIRMED` | 已由代码/契约对照确认，尚无足以关闭的实现与证据 |
| `IN_PROGRESS` | 有明确修复 PR，但关闭条件尚未全部通过 |
| `ACCEPTED_PLAN` | 产品/架构方向已由 Accepted ADR 裁决，但实现与取证仍未完成 |
| `BLOCKED_DECISION` | 必须由仓库所有者决定产品/许可/外部依赖边界 |
| `BLOCKED_EXTERNAL` | 需要当前开发机不具备的真实 Windows、数据库、签名或组织系统 |
| `NOT_RUN` | 已有验收设计，但没有可复现执行证据 |
| `CLOSED` | 责任契约、实现、负向测试、必需 E3/E4 和证据绑定全部通过 |

不得因为已开始编码就将状态改为 `CLOSED`。单元测试只能关闭 E1 要求；数据
复制、Windows 安装/恢复分别仍需 E3/E4。每个修复 PR 必须回写本文状态、
证据路径、关联需求/测试 ID 和未验证项。

下列“当前证据”保留 2026-08-01 审查时用来确认根因的代码/契约事实；后续候选
修复不删除根因记录，而是更新“状态”并在关联 PR/证据中证明关闭条件。

## 4. P0 问题台账

### FP-P0-001：验收证据未做语义绑定

| 字段 | 内容 |
|---|---|
| 第一性原理影响 | 发布系统可能把“任意被哈希文件 + 自申报 PASS/E4”当成真实验收，属于假成功门禁风险 |
| 当前证据 | 已有外部 expected candidate/commit 参数、environment/oracle/Windows JSON 解析、绑定、oracle 重放拒绝和实际 Setup/Launcher 文件哈希候选；BLOCKED candidate-root/attestation validator 基础已绑定完整文件集、最终 manifest 1.1 和固定 GitHub workflow 身份，但尚未接入发布 workflow，也没有受保护 Windows harness、真实 attestation bundle、干净 VM 场景或完整 E3/E4 外部信任链 |
| 责任边界 | Release/QA 主责；Backend/oracle 提供可验证身份；Security 复核反伪造边界 |
| 影响契约 | `acceptance-manifest.v1.schema.json`、`verification-oracle.v1.schema.json`、environment manifest 契约、`09_`、`12_` |
| 状态 | `IN_PROGRESS`；已有 oracle/environment 结构、跨字段语义、身份绑定、oracle 重放拒绝及只能表达 `BLOCKED` 的候选根/托管 attestor 验证基础；独立负向复核仍证明通用文本证据可形成非发布结构 PASS，且真实 workflow attestation、受保护 Windows harness 与场景 profile 未完成，未关闭 |

关闭条件：

- Oracle artifact 必须先通过 JSON Schema 和独立跨字段语义 validator，再允许 E3/E4 PASS。
- Manifest 必须把每个证据绑定到 `requirement_id + test_id + execution_id +
  environment_id + environment_manifest_sha256 + candidate commit/release digest`。
- Environment manifest 必须有 schema 并被解析校验，不能只校验文件哈希。
- Catalog 必须把每个测试的必需 scenario、方向、模式、失败注入和最小
  Execution/oracle 数量固化为机器 profile；不能用一个成功断言满足“四方向、正常/空源/
  脏行、安装/重启/恢复”等复合验收语义。
- 公开发布必须验证受信 Windows harness/候选根 attestation（绑定仓库、workflow、run、
  commit、最终 release manifest 和真实制品）；在该信任根实现前，`--require-pass` 必须
  无条件失败关闭，自报 `clean_vm=true`、`VALID` 或调用者传入的 expected commit 都不是证明。
- 加入“普通文本伪装 oracle”、“PASSED oracle 来自另一 Execution/环境/候选版本”、
  “候选代码在取证后改变”负向测试。
- 只有受保护 Windows harness/candidate attestation validator 实现且上述校验全部通过后，
  `--require-pass` 才能返回成功；当前必须无条件返回
  `TRUSTED_RELEASE_ATTESTATION_NOT_IMPLEMENTED`。
- `--require-pass` 的 expected commit/release candidate 必须来自受保护 checkout/tag 上下文，
  不能从待验证 manifest 自身读取；oracle artifact/execution 不得跨 entry 重放。
- Windows E4 必须由受保护 runner 实际读取 Setup/Launcher、调用系统 Authenticode 验证、
  执行干净 VM harness 并保存不可替代证据；结构化 JSON、自声明 `VALID` 和文件哈希不能
  单独关闭本问题。
- 非发布校验即使得到结构 `gate_result=PASS`，也必须报告 `release_approved=false`，不得
  用于发布或把 FP-P0-001 标记为关闭。

| 责任边界 | Execution state machine/Recovery/Worker reconciler |

提交后进程崩溃和 lease-LOST；再以真实 PostgreSQL 进程终止/并发 E3 证明不存在可观察间隙。

## 7. DataX “完整”的四层口径

未来状态页、README、发布页和验收报告必须分别使用以下口径，不得只写
“已支持 DataX”：

| 层级 | 定义 | 当前状态 | 能声明什么 |
|---|---|---|---|
| 上游源码镜像 | 指定 tag/commit 的完整源码树、NOTICE/许可与源文件哈希清单已入库 | 已导入 `datax_v202309` / `9a1f887...`，1,346 个上游文件；其中根 POM 的 72 个 Reader/Writer 已生成 `SOURCE_PRESENT` inventory | 只能声明源码镜像完整且可追溯；不能把 Reader/Writer inventory 当成 Transformer/模板/SQL 等全部功能盘点 |
| 发布 Runtime | 经可重现构建、锁定依赖/驱动/哈希并实际装入 Worker 镜像的插件 | 当前打包四个业务插件 `mysqlreader/mysqlwriter/postgresqlreader/postgresqlwriter`，另有不向用户开放的内部自检插件 `streamreader/streamwriter` | 只能声明四个业务插件和两个内部自检插件已进入候选 Runtime，不能据此声明产品认证通过 |
| 产品开放能力 | JobSpec/OpenAPI/UI 允许选择且有参数白名单、权限、secret 和网络控制 | V1 只设计 MySQL 8/PostgreSQL 15 一次性单表复制 | 只能声明契约预期能力，不能声明 E3 已通过 |
| 产品认证能力 | 真实外部系统、固定 Runtime、产品全链路和独立 oracle 达到要求证据等级 | 四方向均 `NOT_RUN/BLOCKED` | 目前不能声明任何 Reader/Writer 组合已通过产品认证 |

### 7.1 “DataX 所有功能”的已接受实施口径

仓库所有者已通过 [ADR-0009](adr/0009-DataX完整上游与认证能力分级.md) 接受
“完整上游随包与能力分级认证”的长期目标。该决策明确 V1 仍先闭合 MySQL/PostgreSQL
四插件；每个其他插件只能沿 `SOURCE_PRESENT → BUILD_VERIFIED → PACKAGED → CONTRACTED →
E3_CERTIFIED → WINDOWS_E4_CERTIFIED` 单向推进，未到最后一级不得出现在普通用户的可执行选择器
中。“所有功能”至少可能包括：

- 上游全部 Reader/Writer 插件；
- 自由 `querySql/preSql/postSql`、Transformer 和用户自定义 DataX JSON；
- 依赖 Oracle/SQL Server/HDFS/OSS/ODPS/MongoDB 等外部系统和部分专有驱动；
- 上游已过时、实验性或许可形态不同的模块。

这些能力会改变数据外传、任意 SQL、凭据、网络出口、许可和 oracle 边界。ADR-0009
允许建立 inventory 和逐族认证，但任意 SQL、脚本 Transformer、上传插件等高风险能力仍需
各自的新 ADR，并同步 PRD/威胁模型/OpenAPI/Plugin Manifest/测试/部署；不得通过
“已在源码树中”直接开放。

已接受的交付顺序分为两个里程碑：

1. **可稳定交付的 V1**：先将现有 MySQL/PostgreSQL 安全一次性复制闭环做到
   P0/P1=0、E3/E4 PASS，交付签名 Windows Setup。
2. **分批认证的 DataX 扩展版**：从完整上游模块清单生成机器可读认证
   catalog，每个插件单独记录构建、驱动/许可、参数白名单、secret、出口、类型、
   oracle、真实外部环境和 Windows E4 状态。

插件 inventory 和分级契约可以立即开始，但在必需外部环境、可合法再分发驱动或安全
oracle 不可用时，对应插件状态必须为 `BLOCKED`；被永久阻断的模块必须在“完整
DataX 功能”声明中显式列出。不承诺一次性假实现“100% 上游功能”。

## 10. 立即开发顺序和 PR 切片

开发只能按可独立审查、回滚和验证的纵向切片推进：

1. **PR-A：验收基础**——修复 catalog 单元格解析、oracle/environment 语义校验和候选
   绑定，只修证据系统。
2. **PR-B：恢复 journal 全局门禁**——普通 Start/Backup/初始化受阻，覆盖崩溃和
   负向测试。
3. **PR-C：运行代际统一**——实现 `FRESH/RESTORE` 对象与所有 Launcher 消费者，不同时
   开放覆盖升级。
4. **PR-D：核验取消与终态原子性**——增加批次取消、终态门禁和真实大表测试
   入口。
5. **PR-E：数据库职责权限**——用可回滚迁移缩小 API/Worker 权限并添加越权负例。
6. **PR-F：容器出口边界**——收紧 control/migrate/web/postgres 网络并完成组件级外联证据。
7. **PR-G：权限契约统一**——先修 PRD/OpenAPI/Schema，再改 Backend/UI 与四角色测试。
8. **PR-H：FQDN/TLS 真实执行**——完成 selected-IP + 原主机身份方案和真实驱动
   E3。
9. **PR-I：前端可计算验收**——先进入 UI 验收 catalog，再加行为/浏览器/可访问性/
   覆盖率。
10. **PR-J：真实 E3 与恢复**——按 MySQL→PostgreSQL 黄金路径、其余三方向、异机
    restore 分开提交证据。
11. **PR-K：Windows 发布候选**——只在前述门禁达标后签名、打包并运行 E4。

每个 PR 只处理一个目的，不得在同一 PR 中同时“修恢复 + 增插件 + 改 UI + 发布”。
当前 GitHub `#1` 是用于同步和独立审查全量工程候选的集成 Draft，包含历史上多个纵向
切片，不能以当前形态合并；后续进入可合并阶段前，必须按上表拆成可独立审查、回滚和
验证的 PR，或由仓库所有者通过新的 Accepted ADR 明确改变该治理规则。集成 Draft 通过
CI 只说明组合候选未发现对应自动化回归，不豁免任何切片证据与发布门禁。

## 11. 本文的完成定义

本文建立后，它只表示“已知问题有权威台账和可执行顺序”，不表示问题已修复。

  门禁通过。

  每个对外开放能力均有真实环境和所需 E3/E4 证据。

DataX 所有功能”或“生产就绪”等表述。
