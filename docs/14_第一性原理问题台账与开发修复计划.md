## 1. 审查的第一性原理

一个数据复制产品只有同时回答以下问题，才能称为“完成”：

1. **价值是否真实**：目标用户是否真有这个问题，是否愿意承担本产品的
   源静默、空目标和外部独占操作前提。
2. **复制结果是否真实**：DataX 退出码、页面成功提示和产品自报统计都不是
   数据正确性；只有独立 oracle 可以做最终判定。
3. **失败是否安全**：取消、失租、睡眠、断电、恢复中断和部分写入不能被收敛为
   假成功，也不能在不知情时向目标继续追加。
4. **安全边界是否真正强制**：数据库权限、容器网络和 Worker fence 必须由不同
   边界强制，不能只依赖应用层约定。
5. **证据是否能证伪**：验收系统必须校验证据内容及其与需求、测试、候选版本、
   环境和 Execution 的绑定；“任意文件有正确哈希”不能构成 PASS。
6. **交付物是否与承诺一致**：目标是 Windows 可安装产品，不是一个独立 DataX
   命令行文件，也不是只在 macOS/Linux 上可编译的 EXE 骨架。
7. **“支持”是否可验收**：上游源码存在、插件能被编译、运行时已打包、产品
   已开放、真实 E2E 已通过是五个不同状态。

### 2.2 2026-08-02 对抗式审查增量

本轮从“用户拿到 Windows 安装包后能否启动、执行、止损、取证和更新”反向审查正式
Compose、Launcher、Worker、凭据撤销、插件认证和发布流水线。结论不是新增的发布
批准：当前 release gate 仍失败关闭；但确认了以下必须在解锁前关闭的实现缺口：

1. Worker 缺少控制面完整性 HMAC secret，正式 Compose 会在建立 dispatcher 前 crash-loop；
   当前切片已补齐最小只读挂载、Launcher 校验和静态闭包测试，仍须完成真实 Compose/
   Windows 验证。
2. 已领取 Execution 的目标独占撤回/过期和紧急凭据撤销已补入持久终止事实、Worker
   控制边界和 Probe fail-closed 收敛；heartbeat 不会在安全终止后续租、空闲队列会扫描
   自然到期，current secret 紧急撤销也会收敛无绑定队列，lease-LOST Probe 会重新打开
   可提交的 Gate，且 retired secret 可在后来发现泄露时单向升级。当前只完成 E1 控制面/
   进程/Probe 测试，真实 DataX 长任务、PostgreSQL 并发与 Windows E3/E4 尚未证明实际
   停止边界。
3. 生产插件认证固定 deny-all，且 E3/E4 证据需要候选先运行而普通路径先要求 E4，形成
   qualification 自举环。ADR-0011 已接受 P→QH→PAG→QR→最终 F→hosted promotion 的
   两阶段设计：Phase A 的 QH/PAG 只产生受保护私有、单 pair 的非 E4 qualification，J0b 的
   PEA 是 PAG→每条私有 Execution 的内部绑定，Phase B 的精确 F 才能派生 E4 状态，普通用户
   另须同一 F 的有效 PR。P/QH/QR Schema 与失败关闭 parser、PAG/PEA Schema 及 private Phase-A
   payload/runtime/job binding + durable nonce/grant/PEA persistence 是 E1、进行中基础件；
   `20260802_0021/0022` 新增无登录 ledger owner / issuer / consumer、精确 `SECURITY DEFINER`
   函数和未接入标准路径的 private Engine adapter。0022 有 PEA 表、issuer authorize/consumer read 数据库边界和
   普通 API/Worker/Recovery/日志仅处理 `STANDARD`。0024 仅由 issuer-only 受保护事务把 private Execution、
   PEA 与 public `TargetCopyLock=RESERVED` 一起创建；成功仍固定为
   `QUEUED/BLOCKED/PHASE_A_PRIVATE_WORKER_NOT_IMPLEMENTED`，任一失败完整回滚。它仍无 private rerun、API/Worker/Compose override、
   受保护 harness、manifest-hash-pinned QR reader 或真实证据，不能以测试注入、设置项、
   自报状态、grant JSON 或 PEA JSON 解锁。
4. 自托管 Windows 签名 Runner 的私钥清理、工具链来源和候选身份尚不能建立
   source-to-binary 信任；同一三段版本也没有不可变候选唯一性。本轮将签名 job 固定到
   `datax-release-signing` group 与精确 Windows labels，取消 Cargo/NSIS/rustc/signtool
   的 PATH 自动发现，并在导入 PFX 前检查 clean checkout、本机固定盘/非重解析工具路径及
   Cargo wrapper/flags/target/home 环境覆盖，Cargo 强制使用显式 rustc；这只消除 PATH 选择和
   显而易见的污染，不证明工具身份或阻止 TOCTOU。远端仍没有
   `windows-candidate-signing` Environment 或该受控 runner；缺失名称会被 GitHub 隐式创建
   且无保护规则，尚未配置真实审批/分支策略、工具 hash/ACL 或不可导出签名能力。
5. “DataX 所有功能”只有长期分级方向，尚无冻结的机器 target-set、许可例外和
   `target-set = certified-set + explicitly-unsupported` 的可计算完成定义。
6. Launcher 原先会继承用户 Docker CLI config/context 和 credential helper，且部分
   `up` 后安全检查失败可能保留不健康栈。当前 Launcher 对 ambient `DOCKER_HOST`/
   `DOCKER_CONTEXT` 直接拒绝，缺失时创建并每次回读受控匿名 config；受控子进程才剥离
   Docker/Compose/认证环境、注入固定 local pipe，并在不删卷的前提下收敛不健康栈。这些均
   只有 Rust E1，未取得真实 Windows ACL、Docker Desktop 或 cleanup 行为的 E4。
7. egress guard 曾把 nftables 每次原子替换重新分配的 `handle` 纳入 ruleset hash，造成
   相同 base-deny 规则也会周期性报告 `EGRESS_ATTESTATION_DIVERGED`。当前只排除
   `handle`/`expires` 并保留 timeout/真实规则语义；空策略本机 E2 已通过，含 active
   selected-IP lease 的完整生命周期仍待 E3/E4。
8. 共享 API/Worker netns 内任意不能读取 Docker secret 的普通调用者原可直接请求
   `POST /v1/leases`，对当前 ACTIVE policy 内 IP+port 制造租约与资源耗尽。当前 guard 在
   body/策略/controller 前要求唯一 `X-DataX-Egress-Lease-Capability`；Launcher 生成并
   Compose 只挂载给 guard/API/Worker，缺失/错误/重复统一 401。该修复只有 E1/E2，且同 UID
   Worker/DataX RCE 仍可读取 Worker 挂载，不得伪装为 sandbox。
9. Worker 原先让控制、凭据与心跳分别保留默认连接池，旧进程代际会耗尽
   `datax_worker` 角色上限。当前共享一个 4 条、无 overflow、5 秒超时的 pool，初始化
   SQLAlchemy 失败保持进程存活并停止 admission；角色上限为 12，且 PostgreSQL 在 30 秒
   空闲/15 秒空闲事务后回收异常残留。真实临时 PostgreSQL 已验证 role/GUC 和回收，隔离
   Compose 已验证正常重启会释放当前会话；这仍不是 Windows E4、真实 DataX E3 或无限恢复。
10. 本轮复审还确认：NSIS 仅比较路径字符串会沿既有 junction/reparse point 写入或删除；
    Launcher 仅按 Compose project label 认定归属，可能对外来同标签容器执行 lifecycle/cleanup；
    WSL 默认版本和 `%LOCALAPPDATA%` 磁盘检查不能证明 Docker 实际后端可用；`/S` 无人值守
    安装没有明确合同。远端 GitHub 同时存在 Dependabot security updates `disabled`、Actions
    policy 不强制 SHA pinning、0 approval/CODEOWNERS review 和 hosted E1 非 required check。
    这些问题分别列为 `FP-P1-021..023` 与 `FP-P2-002..004`，不得因源码 E1 或现有 12 个
    required checks 而视作关闭。
11. 数据源创建/更新探针、连接测试、Schema metadata 与任务校验曾在持有组织级控制锁时
    调用 DNS/egress/外部数据库，且没有独立 admission；慢端点可阻塞取消、撤回和凭据紧急
    终止，旧结果还可能跨修订、凭据或 grant 漂移被提交。候选源码现已按 ADR-0014 迁移 A/B/C
    与进程内 admission；隔离 PostgreSQL 仅有受控阻塞 probe + `FOR UPDATE NOWAIT` 的单个 E2
    不持锁场景，完整真实 PostgreSQL 并发矩阵和真 MySQL/PostgreSQL E3 证据尚不存在，
    `FP-P1-026`/`ASR-013` 保持 `IN_PROGRESS`。

这些问题的具体状态、关闭条件和影响范围在下列 `FP-P0-004/005`、`FP-P1-012..026` 中
维护。它们不会被绿色单元测试、候选 root 或 EXE 文件存在自动关闭。

## 3. 状态和关闭规则

| 状态 | 含义 |
|---|---|
| `OPEN_CONFIRMED` | 已由代码/契约对照确认，尚无足以关闭的实现与证据 |
| `IN_PROGRESS` | 有明确修复 PR，但关闭条件尚未全部通过 |
| `ACCEPTED_PLAN` | 产品/架构方向已由 Accepted ADR 裁决，但实现与取证仍未完成 |
| `BLOCKED_DECISION` | 必须由仓库所有者决定产品/许可/外部依赖边界 |
| `BLOCKED_EXTERNAL` | 需要当前开发机不具备的真实 Windows、数据库、签名或组织系统 |
| `NOT_RUN` | 已有验收设计，但没有可复现执行证据 |
| `CLOSED` | 责任契约、实现、负向测试、必需 E3/E4 和证据绑定全部通过 |

不得因为已开始编码就将状态改为 `CLOSED`。单元测试只能关闭 E1 要求；数据
复制、Windows 安装/恢复分别仍需 E3/E4。每个修复 PR 必须回写本文状态、
证据路径、关联需求/测试 ID 和未验证项。

下列“当前证据”保留 2026-08-01 审查时用来确认根因的代码/契约事实；后续候选
修复不删除根因记录，而是更新“状态”并在关联 PR/证据中证明关闭条件。

### 7.1 “DataX 所有功能”的已接受实施口径

仓库所有者已通过 [ADR-0009](adr/0009-DataX完整上游与认证能力分级.md) 接受
“完整上游随包与能力分级认证”的长期目标。该决策明确 V1 仍先闭合 MySQL/PostgreSQL
四插件；每个其他插件只能沿 `SOURCE_PRESENT → BUILD_VERIFIED → PACKAGED → CONTRACTED →
E3_CERTIFIED → WINDOWS_E4_CERTIFIED` 单向推进；未到最后一级或没有同一精确最终 F 的有效 PR
均不得出现在普通用户的可执行选择器中。“所有功能”至少可能包括：

- 上游全部 Reader/Writer 插件；
- 自由 `querySql/preSql/postSql`、Transformer 和用户自定义 DataX JSON；
- 依赖 Oracle/SQL Server/HDFS/OSS/ODPS/MongoDB 等外部系统和部分专有驱动；
- 上游已过时、实验性或许可形态不同的模块。

这些能力会改变数据外传、任意 SQL、凭据、网络出口、许可和 oracle 边界。ADR-0009
允许建立 inventory 和逐族认证，但任意 SQL、脚本 Transformer、上传插件等高风险能力仍需
各自的新 ADR，并同步 PRD/威胁模型/OpenAPI/Plugin Manifest/测试/部署；不得通过
“已在源码树中”直接开放。

已接受的交付顺序分为两个里程碑：

1. **可稳定交付的 V1**：先将现有 MySQL/PostgreSQL 安全一次性复制闭环做到
   P0/P1=0、E3/E4 PASS，交付签名 Windows Setup。
2. **分批认证的 DataX 扩展版**：从完整上游模块清单生成机器可读认证
   catalog，每个插件单独记录构建、驱动/许可、参数白名单、secret、出口、类型、
   oracle、真实外部环境和 Windows E4 状态。

插件 inventory 和分级契约可以立即开始，但在必需外部环境、可合法再分发驱动或安全
oracle 不可用时，对应插件状态必须为 `BLOCKED`；被永久阻断的模块必须在“完整
DataX 功能”声明中显式列出。不承诺一次性假实现“100% 上游功能”。

## 11. 本文的完成定义

本文建立后，它只表示“已知问题有权威台账和可执行顺序”，不表示问题已修复。
