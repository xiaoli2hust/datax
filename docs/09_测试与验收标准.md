# DataX Enterprise Studio V1 测试与验收标准

> 文档状态：V1 发布门禁
>
> 适用架构：Vue 3 + FastAPI 模块化单体 + 独立 Worker + PostgreSQL 15 + Redis 7 + DataX `datax_v202309` / JDK 8
>
> 部署边界：单组织、多项目、单节点、非 HA

## 1. 验收原则

V1 是否完成，以可重复执行的验收证据为准，不以代码文件数量、页面截图或开发者口头说明为准。

必须遵守：

1. Mock、Stub、Fake、静态 JSON、伪造日志和模拟 DataX 进程只能证明单元或集成层行为，不能称为真实 DataX 闭环。
2. “代码已实现”“自动化测试通过”“Docker 服务启动”“浏览器页面可操作”“真实 DataX 数据同步成功”是五种不同证据，必须分别报告。
3. 未执行的测试标记为 `NOT_RUN`，因环境缺失无法执行的测试标记为 `BLOCKED`；不得写成“预计通过”。
4. 测试失败不得通过放宽断言、删除用例、改成 Mock 或隐藏错误来获得通过。
5. 验收报告必须记录命令、环境、版本、时间、结果和证据位置，任何人按文档应能复现。
6. 真实凭据和业务数据不得进入测试报告、截图、日志、录像或版本库。

## 2. V1 冻结范围

### 2.1 必须交付

- 单组织、多项目。
- 角色：Admin、Developer、Operator、Viewer。
- MySQL 8 和 PostgreSQL 15 数据源管理、连接测试和 Schema 读取。
- MySQL 8、PostgreSQL 15 均可作为 Reader 和 Writer。
- 完整表同步或选列同步。
- 源列到目标列的一一直接映射，不支持表达式或转换脚本。
- 目标表必须预先存在，平台不创建或修改目标表结构。
- insert-only。
- 性能参数只开放 `channel`，默认 1，范围 `1..16`。
- 脏数据阈值可配置绝对条数和比例，任一阈值越界即失败。
- 任务草稿、确定性校验、发布不可变 `JobVersion` 和归档。
- 仅用户手工触发执行。
- 运行取消、超时和人工重跑；人工重跑必须创建新的 Execution。
- DataX `datax_v202309` 的真实执行、状态、脱敏日志和执行记录。
- PostgreSQL 作为平台主数据存储，Redis 用于运行协调，独立 Worker 执行 DataX。
- 操作审计、项目隔离和凭据保护。
- 单节点部署、健康检查、迁移、重启恢复和运行说明。

### 2.2 明确不验收

- AI/Agent。
- DAG 和工作流编排。
- 定时调度、补数调度和日历。
- 告警通知。
- 插件市场和自定义插件。
- CDC、流式同步和实时同步。
- 自由 SQL、`where` 自由表达式、`preSql`、`postSql`。
- 字段表达式、常量列、脚本转换和自动建表。
- update、upsert、replace、truncate、delete。
- 多组织、多租户计费、集群和 HA。

如果实现出现以上排除项，不计入 V1 完成度，也不能替代任一必交付项。

## 5. 测试分层

### 5.1 单元测试

必须覆盖：

- RBAC 和项目范围判断。
- Pydantic/领域模型校验。
- 数据源类型和连接参数白名单。
- MySQL/PostgreSQL 类型兼容矩阵。
- 完整表与选列映射。
- 同 datasource、同 schema、同 table 自同步阻断。
- V1 禁止项规则。
- `channel` 和脏数据条数/比例阈值边界。
- 草稿、校验、发布、不可变 JobVersion 和归档规则。
- DataX JSON 生成与脱敏预览。
- 执行状态转换和 DataX 退出码映射。
- 取消、超时、`LOST` 对账和人工重跑。
- 幂等键和重复运行保护。
- 日志脱敏。
- 凭据加解密边界。

单元测试可 Mock 外部系统，但报告必须标记为单元证据。

### 5.2 API 与工具契约测试

必须验证：

- OpenAPI 与实现一致。
- 请求、响应、分页、错误码和空值语义。
- 401、403、404 与跨项目对象访问。
- 乐观锁或等价并发更新保护。
- 幂等请求的相同响应和冲突响应。
- DataX Reader/Writer 配置 JSON Schema。
- Backend 与 Worker 的任务消息版本、兼容性和重复消费。
- 日志流或轮询接口的游标、截断和结束语义。
- JobDraft 乐观锁、发布 JobVersion 及不可变约束。
- 取消请求幂等、终态重复取消和人工重跑关联。

契约测试不得依赖前端是否隐藏按钮。

### 5.3 集成测试

使用真实 PostgreSQL、Redis 和 Worker，覆盖：

- 数据库迁移、事务、唯一约束和级联规则。
- `OPS-FRESH`：空用户库执行一次性 `bootstrap-admin` 成功；非空库重复执行拒绝；临时密码不进入进程参数、环境、日志或审计。
- Redis 暂时不可用及恢复。
- API 创建执行记录，Worker 领取，状态回写。
- 取消请求、进程组终止、墙钟超时、租约过期和启动对账。
- 真实 MySQL/PostgreSQL 元数据连接和 Schema 读取。
- 审计写入与业务事务的一致性。
- 私有临时目录、权限和清理。

该层可使用受控的假 DataX 进程注入退出码来覆盖难构造的异常，但必须标记为“集成测试，不是真实 DataX E2E”。

### 5.4 真实 DataX E2E

必须使用：

- DataX `datax_v202309` 真实发行物。
- MySQL 8 真实实例。
- PostgreSQL 15 真实实例。
- 真实 Backend、PostgreSQL、Redis 和独立 Worker。
- 由产品 API/UI 创建的真实数据源、任务和运行记录。

禁止用 Mock API、预制成功日志、直接手工运行 `datax.py` 后补写数据库状态，或绕过产品 API 创建任务。

### 5.5 浏览器 E2E

至少覆盖：

- Admin 完成用户/项目授权。
- 用户修改本人密码后其他会话按契约失效。
- 项目首页指标按当前项目和时间范围正确下钻。
- Developer 创建数据源、连接测试、读取表和创建任务。
- Developer 校验并发布不可变 JobVersion，修改草稿不改变历史版本。
- Operator 手工触发、取消、人工重跑并查看状态与日志。
- Viewer 只读查看且无修改/运行能力。
- 项目成员查看本项目审计；Admin 可查看全组织审计。
- 连接失败、目标表不存在、无权限、运行失败等错误反馈。
- 刷新和重新登录后状态保持。

浏览器测试应同时保留自动化结果与关键页面截图。只有截图没有断言不算浏览器 E2E。

## 6. 真实 DataX E2E 矩阵

下列四种方向都必须通过，证明两类数据库均能作为 Reader 与 Writer：

| E2E ID | Reader | Writer | 完整表 | 选列 | 最低证据 |
| --- | --- | --- | --- | --- | --- |
| E2E-DX-001 | MySQL 8 | MySQL 8 | 必测 | 必测 | E3 |
| E2E-DX-002 | MySQL 8 | PostgreSQL 15 | 必测 | 必测 | E3 |
| E2E-DX-003 | PostgreSQL 15 | MySQL 8 | 必测 | 必测 | E3 |
| E2E-DX-004 | PostgreSQL 15 | PostgreSQL 15 | 必测 | 必测 | E3 |

每种方向至少包含：

1. 源表 10,000 行确定性夹具。
2. 独立的预创建目标表；常规完整表/选列正确性用例测试前为空，insert-only 保护用例按 6.1 预置哨兵行。
3. 主键/整数、定长与变长文本、Unicode、空字符串、NULL、布尔等价值、日期时间、定点小数。
4. 完整表任务。
5. 至少排除两个源字段的选列任务。
6. 草稿通过确定性校验并发布不可变 JobVersion。
7. 运行前保存脱敏 JSON 快照和任务版本哈希。
8. 运行后验证源/目标行数、列集合和逐行规范化哈希。
9. 验证 DataX 退出码、平台状态、统计摘要和日志一致。

跨数据库类型只使用已经确认兼容的公共类型集合。数据库特有类型进入显式不兼容用例，平台必须在保存或运行前阻止，而不是静默截断或错误转换。

### 6.1 insert-only 验证

- 目标表预先写入一行哨兵数据，执行后该行必须仍存在且未被修改。
- 生成的 DataX JSON 中 `writeMode` 必须为 insert 语义。
- JSON 中不得出现 `preSql`、`postSql`、truncate、replace、update 或 upsert 配置。
- 平台不得创建、删除或修改目标表。
- V1 不承诺业务去重。对同一任务再次手工运行可能追加重复数据，UI 和 README 必须明确提示；测试使用隔离目标表避免把重复运行误判为幂等数据写入。

### 6.2 失败矩阵

| 失败 ID | 场景 | 预期 |
| --- | --- | --- |
| E2E-F-001 | 源凭据错误 | 连接测试/运行失败，凭据不出现在响应和日志 |
| E2E-F-002 | 目标不可达 | 执行失败，有稳定错误分类，无假成功 |
| E2E-F-003 | 目标表不存在 | 保存或预检拒绝，不调用 DataX |
| E2E-F-004 | 目标列缺失/类型不兼容 | 确定性校验拒绝 |
| E2E-F-005 | 注入 `preSql/postSql` 或自由 SQL | API 返回策略拒绝并写审计 |
| E2E-F-006 | DataX 返回非零退出码 | Execution 为失败，保留脱敏 stderr |
| E2E-F-007 | 相同幂等键重复提交 | 只产生一个 DataX 执行 |
| E2E-F-008 | Worker 运行中被终止且进程不可确认 | 最终进入 `LOST`，不自动重跑 |
| E2E-F-009 | Operator 在 `QUEUED/STARTING/RUNNING` 取消 | 经 `CANCEL_REQUESTED` 进入 `CANCELED`，进程组终止且临时文件清理 |
| E2E-F-010 | 运行超过 JobVersion 的 timeout | 进入 `TIMED_OUT`，进程组终止且日志保留 |
| E2E-F-011 | 对失败/超时/丢失执行人工重跑 | 创建新的 Execution 并关联原执行，不复用原 execution ID |
| E2E-F-012 | 源和目标为同一 datasource、同一 schema、同一 table | 确定性校验拒绝，不生成 JobVersion，不调用 DataX |

## 8. 安全测试

### 8.1 身份、权限和项目隔离

- 缺失、过期、伪造、签名错误的身份凭据。
- 四角色对每个受保护接口的正反向矩阵。
- 使用其他项目的 datasource/job/execution/log/audit ID 访问。
- 分页、搜索、导出和日志通道中的跨项目数据泄漏。
- 前端隐藏按钮后直接调用 API。

### 8.2 输入和执行安全

- SQL 注入、命令注入、路径穿越、日志注入和存储型 XSS。
- 数据源 host/port 被用于未授权内网探测或 SSRF。
- 表名、Schema 名和列名的特殊字符、超长值和编码混淆。
- 禁止字段通过大小写、嵌套 JSON、重复键或未知参数绕过。
- DataX 进程必须使用参数数组启动，禁止 `shell=True` 或字符串拼接命令。
- Runtime JSON 只能位于 Worker 私有临时目录，最小文件权限，完成后清理。
- DataX 进程使用非特权账号，并有 CPU、内存、进程数和运行超时限制。

### 8.3 敏感数据

对以下位置执行自动扫描：

- Git 历史和工作区。
- API 响应。
- Backend/Worker/DataX 日志。
- 审计记录。
- 测试报告和截图。
- PostgreSQL 普通业务字段。
- Redis 消息。
- 临时 DataX JSON。

除受控、短生命周期的 Worker 运行文件外，任何位置出现明文密码、Token 或完整连接串均为发布阻塞。

### 8.4 依赖和供应链

- DataX `datax_v202309` 来源、校验和及许可证记录。
- 前后端锁文件一致且可重复安装。
- 容器镜像使用固定 tag/digest。
- 生成 SBOM。
- 依赖、镜像和源代码安全扫描。
- V1 发布时 Critical/High 漏洞必须为 0；风险接受不能替代该发布门禁。

## 9. 正确性与数据质量

真实同步通过条件：

- 源/目标期望行数完全一致。
- 完整表测试的列集合完全一致。
- 选列测试只写入所选目标列，其他目标列保持数据库默认值或 NULL 的预期状态。
- 对公共类型进行逐行规范化哈希比对，差异数为 0。
- Unicode、NULL、空字符串、时区策略和 Decimal 精度符合已记录契约。
- 平台报告的成功/失败状态与 DataX 退出码一致。
- 不允许静默截断、静默丢列或把失败解析为成功。

测试夹具必须固定随机种子并版本化；执行报告记录夹具版本和哈希。

## 10. 性能测试

### 10.1 参考环境

发布报告必须记录：

- CPU 架构与核心数。
- 内存。
- 操作系统和容器运行时。
- Backend/Worker/DataX/数据库版本。
- 数据库是否同机、网络延迟。
- Worker 并发配置。
- 测试脚本版本和数据夹具版本。

默认单节点参考环境为 8 vCPU、16 GiB RAM、200 GB 可用 SSD。性能结果离开该环境不能直接比较。

### 10.2 门槛

在 20 个并发 API 用户、持续 5 分钟、无外部数据库故障时：

- 普通列表/详情 API：p95 ≤ 800 ms。
- 普通创建/修改 API：p95 ≤ 1,500 ms。
- 手工运行请求持久化并返回 execution ID：p95 ≤ 2,000 ms。
- 非预期 5xx 比例 < 1%。
- Worker 领取已提交执行：p95 ≤ 2 秒。
- DataX 输出日志后，UI/API 可见延迟：p95 ≤ 3 秒。
- DataX 退出后，平台最终状态可见延迟：p95 ≤ 3 秒。

浏览器在本地参考网络、冷缓存下：

- 登录后核心页面可交互时间 ≤ 3 秒。
- 页面切换后主要数据或明确加载态 ≤ 1 秒出现。

DataX 吞吐测试：

- 对四种 Reader/Writer 方向至少各执行一次 1,000,000 行公共类型数据同步。
- 数据正确性必须 100% 通过，进程不得 OOM，平台不得丢失状态或日志。
- 吞吐量、CPU 峰值、内存峰值、DataX channel 和批次参数必须记录。
- 第一版结果形成版本基线；后续同环境回归吞吐下降超过 20% 或资源峰值上升超过 20% 时阻塞发布，除非有书面解释和批准。

V1 单 Worker 默认最大并行 Execution 为 1。部署可调高，但调高后必须重新完成资源和稳定性验收。测试应提交 2 个运行，证明第二个执行保持 `QUEUED` 且不会启动额外 DataX 进程。

## 11. 恢复与故障注入

V1 是单节点非 HA，不要求无中断切换，但必须保证状态可解释、可恢复且不自动造成重复插入。

必须验证：

| 恢复 ID | 故障 | 通过条件 |
| --- | --- | --- |
| REC-DB-001 | PostgreSQL 短暂不可用 | API 健康状态变为异常；恢复后可重新服务，无数据静默丢失 |
| REC-REDIS-001 | Redis 短暂不可用 | 新执行不假成功；恢复后依据 PostgreSQL 权威记录重新协调 |
| REC-BE-001 | Backend 重启 | 已保存配置和执行记录保持；重新登录后可查询 |
| REC-WORKER-001 | Worker 在排队期间重启 | 执行不丢失，恢复后只领取一次 |
| REC-WORKER-002 | Worker 在运行期间被终止且进程不可确认 | 执行最终进入 `LOST`，不无限保持 `RUNNING`，不自动重跑 |
| REC-DATAX-001 | DataX 进程非零退出 | 完整记录失败状态、脱敏 stderr 和退出码 |
| REC-HOST-001 | 整套 Compose 重启 | 数据库迁移状态、配置、任务和历史执行仍存在 |
| REC-CANCEL-001 | Worker 处理中收到取消请求 | 先温和终止进程组，宽限期后强制终止，最终进入 `CANCELED` |
| REC-TIMEOUT-001 | DataX 超过墙钟超时 | 进程组被终止，最终进入 `TIMED_OUT`，日志与审计完整 |

由于 insert-only 可能产生重复数据，V1 禁止在 Worker 丢失后自动重跑不确定状态的执行。必须由 Operator 查看失败证据后手工决定是否新建一次执行。

备份恢复至少验证一次：

1. 备份 PostgreSQL。
2. 在隔离环境恢复。
3. 验证用户、项目、数据源密文、任务版本、执行和审计记录。
4. 验证恢复环境不能在缺少原密钥时错误显示凭据已可用。

恢复演练必须记录实际 RPO/RTO，并达到 RPO ≤ 24 小时、RTO ≤ 4 小时；超出即为未通过。

## 12. 证据分级

| 级别 | 含义 | 可证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| E0 | 代码/配置静态存在 | 文件和实现意图 | 可运行或正确 |
| E1 | 单元、契约、Mock/Fake 测试 | 局部逻辑和接口契约 | 真实依赖或 DataX |
| E2 | 真实平台依赖集成，但 DataX 可模拟 | PostgreSQL/Redis/Worker 协作 | 真实数据同步 |
| E3 | 真实 DataX + 真实 MySQL/PostgreSQL + 产品 API/UI | 本地真实业务闭环 | 打包部署和重启运维 |
| E4 | 从干净环境部署、浏览器验收、重启/恢复 | 可交付运行与恢复 | HA 或生产规模 |

规则：

- V1 功能闭环最低要求 E3。
- 安装部署、重启和恢复最低要求 E4。
- Mock DataX 即使全部自动化通过，也只能是 E1/E2。
- 截图只能作为辅助证据，不能单独提升等级。
- 打包成功不等于服务启动成功；服务启动成功不等于 DataX E2E 成功。

每个候选版本必须输出：

- `environment-manifest`：系统、架构、依赖和镜像 digest。
- DataX `datax_v202309` 来源、版本输出和文件校验和。
- 数据库迁移 fresh install 与 upgrade 日志。
- 单元、契约、集成、浏览器和 E2E 的机器可读报告。
- 覆盖率报告。
- 四方向 DataX E2E 的任务 ID、execution ID、脱敏 JSON、退出码、行数和哈希结果。
- 失败矩阵测试结果。
- RBAC 与跨项目安全测试结果。
- secret scan、SAST、SCA、镜像扫描、SBOM 和许可证报告。
- 性能原始数据与摘要。
- 重启、故障注入和备份恢复报告。
- 核心页面截图或录像。

建议提供机器可读的 `acceptance-manifest.json`，逐条关联需求 ID、测试 ID、证据等级、结果和文件哈希。

## 14. 缺陷等级与发布门禁

| 等级 | 定义 | 发布要求 |
| --- | --- | --- |
| P0 | 数据损坏、越权、凭据泄漏、远程执行、假成功、无法启动 | 必须为 0 |
| P1 | V1 主流程不可用、真实 E2E 失败、状态错误、无法恢复 | 必须为 0 |
| P2 | 有可接受替代路径的非核心问题 | 必须记录负责人和修复版本 |
| P3 | 轻微 UI/文案问题 | 可进入已知限制 |

任何 `BLOCKED` 的 P0/P1 需求视为未完成，不得因为“环境原因”自动豁免。

## 15. V1 Definition of Done

只有同时满足以下全部条件，才能声明 V1 完成：

1. 第 2 节范围内功能全部实现，排除项未被暗中引入。
2. 第 7 节需求追踪矩阵无缺行，所有 P0/P1 需求状态为 PASS。
3. 四种 Reader/Writer 方向的完整表和选列真实 DataX E2E 全部达到 E3。
4. 目标表不存在、字段不兼容、同表自同步、channel/脏数据阈值、禁止配置、错误凭据、DataX 失败、重复提交、取消、超时、`LOST` 对账和人工重跑测试全部通过。
5. Backend 和前端整体行覆盖率不低于 80%，权限、策略、JSON 生成、凭据和执行状态核心模块不低于 90%；覆盖率不能替代行为测试。
6. 四角色和跨项目矩阵全部通过，无服务端越权。
7. 明文凭据泄漏数为 0，Critical/High 安全缺陷为 0。
8. 第 10 节性能门槛通过并保存原始结果。
9. 第 11 节重启、故障注入和备份恢复达到 E4，且 RPO ≤ 24 小时、RTO ≤ 4 小时。
10. 从干净环境按 README 可完成安装、迁移、安全创建首个 Admin、启动、健康检查和首个真实同步。
11. 浏览器完成 Developer 配置/校验/发布、Operator 运行/取消/人工重跑、Viewer 只读的主流程，错误态和无权限态可见。
12. README、API 文档、环境变量、部署、备份恢复、故障处理和已知限制与实现一致。
13. 发布证据包完整，所有未完成或阻塞项如实列出。

AI/Agent 不属于 V1 DoD。V2 Agent 的评测和发布门槛见 `07_Agents工程化方案.md`，不得用 AI 演示替代 V1 的真实 DataX 验收。
