## 1. 验收原则

V1 是否完成，以可重复执行的验收证据为准，不以代码文件数量、页面截图或开发者口头说明为准。

必须遵守：

1. Mock、Stub、Fake、静态 JSON、伪造日志和模拟 DataX 进程只能证明单元或集成层行为，不能称为真实 DataX 闭环。
2. “代码已实现”“自动化测试通过”“Docker 服务启动”“浏览器页面可操作”“真实 DataX 复制经独立核验通过”是五种不同证据，必须分别报告。
3. 未执行的测试标记为 `NOT_RUN`，因环境缺失无法执行的测试标记为 `BLOCKED`；不得写成“预计通过”。
4. 测试失败不得通过放宽断言、删除用例、改成 Mock 或隐藏错误来获得通过。
5. 验收报告必须记录命令、环境、版本、时间、结果和证据位置，任何人按文档应能复现。
6. 真实凭据和业务数据不得进入测试报告、截图、日志、录像或版本库。
7. Windows 发布必须在干净 Windows 11 x64 VM 重新验收；macOS/Linux 构建、容器包存在、
   EXE 文件存在或非 Windows E2E 不能证明 Windows 安装、启动、安全边界与恢复达到 E4。

## 2. V1 冻结范围

### 2.1 必须交付

- 单组织、多项目。
- 角色：Admin、Developer、Operator、Viewer。
- MySQL 8 和 PostgreSQL 15 数据源管理、连接测试和 Schema 读取。
- MySQL 8、PostgreSQL 15 均可作为 Reader 和 Writer。
- 安全的一次性离线全量复制：完整表或选列。
- 源列到目标列的一一直接映射，不支持表达式或转换脚本。
- 操作员确认源表从运行前检查开始到独立 oracle 完成始终静默；Operator/DBA 另行提交
  `statement_version='1.0'`、带有限 `valid_until` 的目标外部独占声明，承诺从 Worker
  最后一次目标空表观察到 oracle 目标一致性读事务完成期间无平台外 DML/DDL。声明具有
  `ACTIVE/REVOKED/EXPIRED` 生命周期；两项人工确认都不能冒充数据库级快照或平台技术锁，
  未收到撤回/破坏报告也不能证明任意瞬时、未报告或已回滚的外部写从未发生。
- 目标表必须预先存在、可只读核验且由 Worker 在目标活动锁下实测为空；平台不创建、清空或修改目标表结构。
- `insert-only-once`；非空目标拒绝，失败后完成必要外部处置并如实声明，再经平台空表复检才可恢复后再次执行；无需清理时不得虚假声称已清理。
- 性能参数只开放 `channel`，默认 1，范围 `1..16`。
- V1 脏数据阈值固定 `record_count=0`、`percentage=0`，UI/API 不提供正数容忍；任一脏行都不能业务成功。正数阈值属于 POST-V1。
- 任务草稿、确定性校验、发布不可变 `JobVersion` 和归档。
- 仅用户手工触发执行。
- 运行取消、超时和恢复后再次执行；再次执行必须创建新的 Execution。
- DataX `datax_v202309` 的真实执行、状态、脱敏日志和执行记录。
- PostgreSQL 同时作为业务事实源和权威任务队列，独立 Worker 执行 DataX；V1 不依赖 Redis。
- 操作审计、项目隔离和凭据保护。
- 已签名 `Setup.exe`/`launcher.exe` 的 Windows 11 x64 单工作站交付；Docker Desktop +
  WSL2 前置检测但不静默安装/代接受许可；固定 Linux DataX 容器；仅 Web 绑定
  `127.0.0.1:17860`，API/Worker/PostgreSQL 无宿主端口。
- 健康检查、迁移、Windows/WSL/Docker/睡眠恢复、备份恢复、卸载保留数据和运行说明。

### 2.2 明确不验收

- AI/Agent。
- DAG 和工作流编排。
- 定时调度、补数调度和日历。
- 告警通知。
- 插件市场和自定义插件。
- CDC、流式同步和实时同步。
- 自由 SQL、`where` 自由表达式、`preSql`、`postSql`。
- 字段表达式、常量列、脚本转换和自动建表。
- update、upsert、replace、truncate、delete。
- 多组织、多租户计费、集群和 HA。

如果实现出现以上排除项，不计入 V1 完成度，也不能替代任一必交付项。

## 5. 测试分层

### 5.1 单元测试

必须覆盖：

- RBAC 和项目范围判断。
- Pydantic/领域模型校验。
- 数据源类型和连接参数白名单。
- MySQL/PostgreSQL 类型兼容矩阵。
- 完整表与选列映射。
- 同一物理表经 Datasource/revision/hostname/IP 别名的自复制阻断。
- V1 禁止项规则。
- `channel` 边界；V1 脏数据条数/比例只接受 `0/0`，任一正数或负数都被 Schema/API 拒绝。
- 草稿、校验、发布、不可变 JobVersion 和归档规则。
- DataX JSON 生成与脱敏预览。
- `process_state / data_effect / verification_state` 三类状态；`data_effect=CONFIRMED` 只表示目标影响已测得且可为 0 行，不代表内容正确；空源成功为 `SUCCEEDED/CONFIRMED/PASSED`。
- Oracle 未启动时 `verification_state=NOT_STARTED`，即使 DataX 异常退出；已启动但无法形成结论时才为 `INCONCLUSIVE`。
- 目标空表预检、Operator/DBA 目标排他声明的版本/有效期/状态转换、撤回或破坏报告、
  `TARGET_EXCLUSIVITY_CONFIRMED/TARGET_EXCLUSIVITY_REVOKED` 审计、单一一致性读事务快照、
  同目标活动锁、fence epoch、取消、超时、`LOST` 对账和恢复门禁。
- 幂等键与显式二次运行拒绝；失败后未提交如实处置确认或未通过空表复检不得恢复后再次执行。
- oracle-v1 的 NULL、Unicode、Decimal、时区、重复行多重集和稳定排序规范化。
- 日志脱敏。
- 凭据加解密边界。

单元测试可 Mock 外部系统，但报告必须标记为单元证据。

### 5.2 API 与工具契约测试

必须验证：

- OpenAPI 与实现一致。
- 请求、响应、分页、错误码和空值语义。
- 401、403、404 与跨项目对象访问。
- 乐观锁或等价并发更新保护。
- 幂等请求的相同响应和冲突响应。
- DataX Reader/Writer 配置 JSON Schema。
- Backend 与 Worker 的任务消息版本、兼容性和重复消费。
- 日志流或轮询接口的游标、截断和结束语义。
- JobDraft 乐观锁、发布 JobVersion 及不可变约束。
- 取消请求幂等、终态重复取消和恢复后再次执行关联。
- 项目可读 `DatasourceRedactedSummary` 不含真实 host/port/database/schema/username；
  只有 AdminDetail 与 Admin-only revision 路由包含非秘密连接定位。
- EndpointPolicyRevision、PhysicalEndpointIdentity、TargetNamespace、TransferPolicy 精确
  创建请求的两侧 catalog/database/schema/table/selection_mode/显式列，`ALL_COLUMNS`
  预展开、规范化 `scope_json/scope_hash`、`expected_scope_hash` 提交/审批、防旧审批复用，
  mapping 子集校验，以及 CredentialSecret 状态与 Envelope 摘要的正反例。
- JobVersion/Execution 暴露不可变 DatasourceRevision/EndpointPolicyRevision、
  TargetNamespace、安全 secret/Envelope 版本身份、连接证据 ID、resolved config hash 和
  脱敏 runtime snapshot。
- 连接证据必须区分实际 socket peer 与出口强制目的地址：平台直接持有 socket 的阶段为
  `OBSERVED` 且 `peer_ip=selected_ip`；DataX 阶段在进程启动前形成两端
  `ENFORCED_NOT_OBSERVED + peer_ip=null` 证据，并证明精确 selected-IP 租约有效。测试必须
  拒绝把 selected_ip 复制成伪造 peer，且证明 JVM 访问其他解析地址时由内核规则失败关闭。
- RecoveryProbe/Attempt 使用独立 fence；ExecutionAttempt 不能关闭恢复门禁。
- LogGap 与 `raw_received/redacted_received/stored/dropped` 四类计数的形状、缺口和跨字段
  守恒校验。
- `verification-oracle.v1` 与 `acceptance-manifest.v1` 正反例。
- 目标独占声明的创建快照、`ACTIVE/REVOKED/EXPIRED` 条件形状和
  `POST /executions/{execution_id}/target-exclusivity/revoke` 的权限、幂等、终态冲突与
  审计契约；语义 validator 强制 `confirmed_at < valid_until` 和
  `target_result.snapshot_finished_at <= valid_until`。

契约测试不得依赖前端是否隐藏按钮。

### 5.3 集成测试

使用真实 PostgreSQL 和 Worker，覆盖：

- 数据库迁移、事务、唯一约束和级联规则。
- `OPS-FRESH`：空用户库经 Launcher GUI 一次性引导调用固定容器
  `bootstrap-admin` helper 成功；非空库重复执行拒绝；临时密码只经标准输入，不进入
  浏览器/API、进程参数、环境、日志或审计。
- `OPS-ADMIN-RECOVERY`：仅在有效 Admin 数量为 0 时，容器内
  `datax-studio-recover-admin` 才能通过标准输入为一名 LOCKED Admin 设置临时密码、
  撤销旧会话并写 `SYSTEM_RECOVER_ADMIN`；存在有效 Admin、目标为 DISABLED/非 Admin、
  从 Web 调用或密码出现在参数、环境、输出、审计时均失败。
- 临时密码登录与 `/auth/me` 显式返回 `must_change_password=true`，且业务路由统一拒绝；
  refresh/logout/me/change-password 保持可用，改密后门禁立即解除。
- 在隔离 PostgreSQL 15 中并发提交相同 actor/scope/key：一个事务持锁时另一个请求稳定
  返回 `IDEMPOTENCY_IN_PROGRESS`，不等待唯一键错误；过期记录在同一锁内安全替换。
- 在隔离 PostgreSQL 15 中并发 refresh 与 Admin reset-password，设置有限
  `lock_timeout/statement_timeout` 并重复运行；两条路径均按统一行锁顺序结束，不出现
  deadlock 或 lock timeout，refresh 只允许成功轮换或因 reset 撤销而安全返回认证失败。
- RBAC 拒绝、本人旧密码错误和重复邮箱必须以独立事务写 `DENIED` 审计；审计不得保存
  密码或原始 User-Agent。若失败审计自身不可用，必须保留原 API 错误，不得显示成功、
  改写业务错误或回显审计内部异常。
- API 创建执行记录，Worker 通过 PostgreSQL `FOR UPDATE SKIP LOCKED` 单次领取、状态回写；`LISTEN/NOTIFY` 丢失时轮询兜底。
- API 创建 Execution 的同一事务原子写入 `QUEUED + TargetCopyLock=RESERVED`；
  `TargetNamespace` 部分唯一索引覆盖 `RESERVED/ACTIVE/RECOVERY_REQUIRED`，同目标第二个
  不同幂等键请求必须在 API 返回 `409 TARGET_ACTIVE_EXECUTION`，不得创建第二个 QUEUED。
- 领取事务在提交前故障时整体回滚：Execution 保持未领取的 `QUEUED` 与原 `RESERVED`
  预留，且无 Attempt/fence/secret Envelope 固定事实；提交后故障不得回 QUEUED、复用
  Attempt 或自动重新入队。
- 取消请求、进程组终止、墙钟超时、租约过期和启动对账。
- 真实 MySQL/PostgreSQL 元数据连接和 Schema 读取。
- EndpointPolicy/DNS/出口复检、用途授权、TransferPolicy 审批与执行前双检。
- 审计写入与业务事务的一致性。
- 私有临时目录、权限和清理。
- Worker 连接预算：控制、凭据和心跳必须复用一个 `pool_size=4`、无 overflow、5 秒获取超时
  的 Engine；首次 dispatcher 初始化遇到 `SQLAlchemyError` 时进程保持存活、admission 失败关闭
  并重试，不能 crash-loop。真实 PostgreSQL 必须验证 `datax_worker` 的 12 条角色上限以及
  30 秒空闲/15 秒空闲事务服务端回收；受控正常重启不得累积会话，异常终止后的残留只可在该
  有界窗口内阻断，不得伪装为无限恢复能力。

该层可使用受控的假 DataX 进程注入退出码来覆盖难构造的异常，但必须标记为“集成测试，不是真实 DataX E2E”。

#### 可重复运行的 PostgreSQL E2 子集（开发门禁）

`scripts/test-postgres-e2.sh` 只用于可重复的开发期 E2 子集：它会在随机的
`127.0.0.1` 端口启动一个带 `tmpfs` 数据目录的临时 PostgreSQL 15 容器，运行全部迁移，并对
最新 Worker 会话回收迁移执行一次真实 downgrade/re-upgrade，再执行数据库运行角色（含
Worker 角色会话回收）、egress-guard 读模型、审计 append-only、
凭据并发与认证并发测试。
脚本使用临时权限收紧的 secret 文件，结束时删除容器和临时目录；不得改用产品 Compose
的命名持久卷来执行该门禁。

此门禁的“真实”范围仅限 PostgreSQL 迁移、权限和事务并发。凭据并发测试为隔离行锁和
secret/envelope 事务，明确注入受控的 probe/attestation，因而不构成真实数据源连接、
DNS/内核 egress 或 DataX 证据。它不启动产品 Compose、API/Worker 进程、DataX 或
MySQL，不产生独立数据 oracle 结果，也不验证 Windows 安装包。结果只能登记为 E2 子集；
不得写入候选发布验收清单，不得表述为 E3 或 E4。macOS 上可运行它作为开发期数据库门禁，
但最终 Windows 交付仍必须按 E3/E4 的独立环境和证据要求验收。

### 5.4 真实 DataX E2E

必须使用：

- DataX `datax_v202309` 真实发行物。
- MySQL 8 真实实例。
- PostgreSQL 15 真实实例。
- 真实 Backend 产品 API、PostgreSQL 事实队列和独立 Worker。
- 由产品 API 创建的真实数据源、复制任务、不可变版本和运行记录。

`E3` 的固定定义是“真实数据库 + 固定 DataX Runtime + 真实产品 API/Backend/Worker +
独立 oracle”。只有被验收需求本身涉及页面、交互、可访问性或浏览器会话时，才额外要求
真实 UI/浏览器证据；纯 API/Worker/数据正确性需求不能因为没有 UI 截图被降级，也不能用
UI 点击替代产品 API 和真实数据库链路。

禁止用 Mock API、预制成功日志、直接手工运行 `datax.py` 后补写数据库状态，或绕过产品 API 创建复制任务。

### 5.5 浏览器 E2E

至少覆盖：

- Admin 完成用户/项目授权。
- 用户修改本人密码后其他会话按契约失效。
- 项目首页指标按当前项目和时间范围正确下钻。
- Admin 配置 EndpointPolicy、数据源、用途授权和 TransferPolicy；Developer 只能使用已授权数据源读取表和创建任务。
- Developer 校验并发布不可变 JobVersion，修改草稿不改变历史版本。

## 6. 真实 DataX E2E 矩阵

下列四种方向都必须通过，证明两类数据库均能作为 Reader 与 Writer：

| E2E ID | Reader | Writer | 完整表 | 选列 | 最低证据 |
| --- | --- | --- | --- | --- | --- |
| E2E-DX-001 | MySQL 8 | MySQL 8 | 必测 | 必测 | E3 |
| E2E-DX-002 | MySQL 8 | PostgreSQL 15 | 必测 | 必测 | E3 |
| E2E-DX-003 | PostgreSQL 15 | MySQL 8 | 必测 | 必测 | E3 |
| E2E-DX-004 | PostgreSQL 15 | PostgreSQL 15 | 必测 | 必测 | E3 |

每种方向至少包含：

1. 源表 10,000 行确定性夹具。
2. 独立的预创建、可只读计数核验的空目标表；预置任意哨兵行时必须在启动 DataX 前以 `TARGET_NOT_EMPTY` 阻断。
3. 主键/整数、定长与变长文本、Unicode、空字符串、NULL、布尔等价值、日期时间、定点小数。
4. 完整表任务。
5. 至少排除两个源字段的选列任务。
6. 草稿通过确定性校验并发布不可变 JobVersion。
7. 固定源/目标 DatasourceRevision、凭据安全版本、Runtime/插件摘要和 resolved config hash。
8. Operator 确认源表从运行前检查开始到独立 oracle 完成始终静默；Operator/DBA 提交
   `statement_version='1.0'`、`valid_until` 有限的目标外部独占声明。Worker 要求其仍为
   `ACTIVE`、未撤回且未过期，持有同目标活动锁、实测目标为空并保存证据后才启动 DataX；
   人工声明不替代该锁和实测，也不证明未报告的外部写没有发生。
9. DataX 退出 0 后 `process_state` 进入 `VERIFYING`；oracle 真正启动前 `verification_state` 仍为 `NOT_STARTED`，启动后才为 `VERIFYING`。独立 oracle 在一个有 ID 和起止边界的目标一致性读事务内读取目标端，并按 6.2 多重集规则验证。
10. 只有脏行数为 0、目标排他声明在目标快照完成时仍为 `ACTIVE`、未撤回未过期、
    `target_result.snapshot_finished_at <= valid_until` 且 oracle `PASSED`，才进入
    `SUCCEEDED + CONFIRMED + PASSED`。这里 `CONFIRMED` 表示目标影响已测得，空源的 0 行
    影响同样是 CONFIRMED；内容正确性只由 PASSED 表达。统计摘要和脱敏原序日志仅作运行证据。
11. MySQL Reader 和 Writer 各执行 TLS 正负例：`VERIFY_CA` 接受受信 CA、拒绝未知 CA；
    `VERIFY_FULL` 还必须接受匹配 FQDN、拒绝由同一受信 CA 签发但 SAN/CN 不匹配的证书。
    证据必须来自 Connector/J `9.7.0` 的真实握手；JDBC URL 字符串断言只能算 E1，
    不能替代 E3。Runtime manifest 必须固定两份驱动 JAR 路径与摘要，旧 `5.1.47` 或
    任意额外 MySQL 驱动均应阻断。

跨数据库类型只使用已经确认兼容的公共类型集合。数据库特有类型进入显式不兼容用例，平台必须在保存或运行前阻止，而不是静默截断或错误转换。

### 6.1 一次性 insert-only 保护

- 目标表预先写入一行哨兵数据，执行必须在启动 DataX 前被拒绝；哨兵行仍存在且未被修改。
- MySQLWriter 的 DataX JSON 必须显式包含 `writeMode=insert`。固定的
  PostgresqlWriter 上游版本不支持 `writeMode`，其 JSON 必须省略该未知参数，并通过
  固定插件默认 `INSERT` 语义、目标空表预检和独立 oracle 验证 insert-only 结果；不得
  为了形式一致向 PostgreSQLWriter 注入无效字段。
- JSON 中不得出现 `preSql`、`postSql`、truncate、replace、update 或 upsert 配置。
- 平台不得创建、删除或修改目标表。
- 同一 TargetNamespace 已有未释放 `RESERVED/ACTIVE/RECOVERY_REQUIRED` 锁时，第二个不同
  幂等键请求必须在 API 层拒绝，既不得创建第二个 `QUEUED`，也不得启动 DataX。
- 已成功复制后的目标必然非空；显式二次运行必须被 `TARGET_NOT_EMPTY` 拒绝，不能依靠 UI 警告。
- 失败、取消、超时、LOST 或核验失败后，未提交如实处置确认（需要清理时记录实际动作；
  无需清理时 `cleanup_performed=false` 并记录原因）或 RecoveryGate 未经独立
  RecoveryProbe 空表复检为 VERIFIED 时，机器 `rerun` 请求必须被拒绝。

### 6.2 独立 `oracle-v1` 规范

Oracle 不得调用产品的 DataX 摘要来判定正确性。源端保持静默、目标锁保持到核验结束，
Operator/DBA 的人工目标排他声明固定 `statement_version='1.0'` 和有限 `valid_until`，
并承诺覆盖 Worker 最后一次空表观察至目标一致性读事务结束；该声明不是技术锁。目标端
所有计数与摘要必须来自同一个只读一致性事务，并记录非秘密 `snapshot_id` 及开始/结束
边界。按 JobSpec 映射顺序把每个字段编码为长度前缀的类型标记值，对规范化行做 SHA-256，
再对 `行摘要升序 + 出现次数` 组成的多重集做 SHA-256：

```text
row_preimage =
  UTF8("DXORACLEROWv1") || 0x00 || U32_BE(field_count) ||
  EACH(U16_BE(tag_length) || ASCII(tag) || U64_BE(value_length) || value)
row_sha256 = SHA256(row_preimage)

multiset_preimage =
  UTF8("DXORACLEMULTISETv1") || 0x00 ||
  EACH_SORTED(raw_32_byte_row_sha256 || U64_BE(occurrence_count))
multiset_sha256 = SHA256(multiset_preimage)
```

类型标签固定为 `NULL / INTEGER / DECIMAL / TEXT / BOOLEAN / DATE / TIME / TIMESTAMP /
BINARY`。长度按编码后的字节数计算，整数均为无符号大端；空多重集只对
`UTF8("DXORACLEMULTISETv1") || 0x00` 求哈希。不得使用分隔字符拼接、十六进制摘要文本或
数据库自带聚合哈希代替上述前像。

- `NULL` 使用专用类型标签，与空字符串、零和字符串 `"NULL"` 不同。
- Integer 使用精确十进制、无前导正号或无意义前导零；布尔不得当成整数。
- 文本按 UTF-8 解码并规范化为 Unicode NFC；不 trim、不大小写折叠，空字符串保留。
- Decimal 使用精确十进制、无指数、移除无意义尾零，负零归一为零；禁止二进制浮点参与。
- 数据库会话时区固定 UTC；有/无时区时间均按类型兼容规则转为 UTC，时间戳编码为 RFC 3339 微秒精度 `Z`。
- Date 编码为 `YYYY-MM-DD`；Time 编码为 `HH:MM:SS.ffffff`，非 UTC offset 的 TIME
  因缺少日期而拒绝，不做含糊换算。
- 布尔编码为小写 `true/false`；二进制按 RFC 4648 Base64。
- 重复行按出现次数参与，多重集相同才通过；不依赖数据库返回顺序。
- Oracle 实际启动后，源端前置与核验后指纹不一致、目标声明已撤回/已过期/由
  Operator/DBA 报告窗口破坏、目标锁丢失、目标快照不是单一一致性事务或任一侧读取失败时
  结果为 `INCONCLUSIVE`，平台 `process_state=FAILED`，不得成功。平台不能把未报告的任意
  瞬时或已回滚外部写自动归类为已检测到的窗口破坏；独立数据差异只能证明读到的结果不同。
- Oracle 从未启动时保持 `verification_state=NOT_STARTED` 且没有 oracle 产物；DataX 先行异常退出不得伪装成 `INCONCLUSIVE`。

每次 E2E 保存符合 `verification-oracle.v1.schema.json` 的产物及 SHA-256。

Oracle 产物的 `artifact_sha256` 必填；`INCONCLUSIVE` 必须是 oracle 已启动并提供非空原因；
`PASSED` 必须固定 `source_quiescence.unchanged=true`、
`target_lock.held_through_verification=true`、`target_exclusivity.statement_version='1.0'`、
`target_exclusivity.status=ACTIVE`、`target_exclusivity.revoked_at=null`、
`target_exclusivity.valid_through_target_snapshot=true`，缺失/额外行数为 0、
`row_count_equal/multiset_sha256_equal=true` 且差异样本为空。
`FAILED` 至少有一个相等标志为 false 或差异计数大于 0。JSON Schema 无法比较两个兄弟字段，独立语义 validator
还必须强制源/目标 `row_count`、`distinct_row_digest_count`、`multiset_sha256` 相等，
目标结果的全部查询落在同一个一致性事务，`target_exclusivity.target_empty_checked_at`
等于最后空表证据，`target_exclusivity.target_snapshot_id` 等于
`target_result.snapshot_id`，并强制
`confirmed_at` ≤ `target_empty_checked_at` ≤ `target_result.snapshot_started_at` ≤
`target_result.snapshot_finished_at` ≤ `valid_until`，重算移除
`artifact_sha256` 后的 RFC 8785 制品哈希，并校验时间顺序。
`INCONCLUSIVE` 若在某侧读取或目标快照建立前失败，对应结果、差异或快照字段必须为 null，
不得用 0 行或固定 hash 伪造已完成读取；`FAILED` 表示已经完成可比较读取并得到数据差异。

### 6.3 失败与恢复矩阵

| 失败 ID | 场景 | 预期 |

## 7. 需求追踪矩阵

权威逐条映射位于 `12_需求追踪矩阵.md`。V1.2 catalog 固定为 81 个唯一需求 ID：
31 FR、22 BR、14 NFR、14 ACC，其中 80 项 `V1-MUST`、1 项 `POST-V1`。该文件必须做到一行一个需求，尤其
`PRD-BR-001..022` 不得按范围分组；每行必须包含需求优先级、至少一个不带通配符的精确
测试 ID、oracle、最低证据和证据路径字段。唯一性边界是“需求 ID + 测试 ID”对；只有
同一个可复核执行确实证明多个需求时，测试 ID 才可跨需求显式复用，并为每个需求分别
绑定 oracle 与证据。数量或集合不等于 81 时失败关闭。

候选版本必须生成符合 `acceptance-manifest.v1.schema.json` 的 `acceptance-manifest.json`。一个数组项只表示一个“需求 ID + 精确测试 ID”结果；测试 ID 禁止使用 `*`、`..` 或“对应套件”。未执行写 `NOT_RUN`，环境缺失写 `BLOCKED`，均不能满足 V1-MUST 发布门禁。

CI 必须按 Markdown 表格列精确解析权威需求目录，测试 ID 只能来自 `测试 ID` 列，不能
从 `NFR-PERF-*`、`NFR-SEC-*` 或其他单元格的文本中猜测。随后生成按
`requirement_id` 稳定排序的规范化 catalog，并把
`requirements_catalog_sha256` 写入 manifest。每个 catalog 项至少固定
`requirement_id / requirement_priority / test_id / minimum_evidence_level / evidence_requirements`；
manifest entry 必须回填相同的最低等级和结构化证据要求，独立 validator 逐项比较完整
元组；PASS 的实际证据等级必须精确等于 catalog 最低等级，不能自行抬为 E4 后绕开
`WINDOWS_E4` 结构化证据，也不能由
测试运行器自行修改。JSON Schema 还必须拒绝 `result=PASS` 但
`evidence_level != minimum_evidence_level` 的条目。随后 CI 以集合运算比较 catalog 中全部
`V1-MUST` ID 与 `entries` 中 PASS 的 V1-MUST ID，并生成
`coverage.expected_v1_must_count`、`covered_v1_must_count`、
`catalog_exact_match`、`missing_requirement_ids` 和 `duplicate_requirement_test_pairs`，拒绝未知优先级、缺失 ID、
重复“需求 ID + 测试 ID”对或计数不一致。`gate_result=PASS` 时两个数组必须为空，且 expected
与 covered 相等、`catalog_exact_match=true`；这些跨数组/跨字段条件由独立 validator
执行，不能只依赖 JSON Schema。PASS 条目还必须有至少一个哈希证据、实际执行时间和
environment ID。Catalog 标记 `VERIFICATION_ORACLE_V1` 的 E3 PASS 必须解析真实
`verification-oracle.v1` JSON，重算其 RFC 8785 hash 和跨字段语义，并把 candidate、commit、
requirement/test、environment、execution/job version 全部绑定一致；Catalog 标记
`WINDOWS_E4` 的 PASS 必须解析结构化 Windows E4 JSON，绑定同一 candidate/commit/
requirement/test/environment，验证干净 Win11 x64、签名制品、loopback 端口及逐项证据哈希。
Windows 断言数组必须包含当前 manifest entry 绑定的精确测试 ID，不能用另一个 E4 测试的
PASS 结果代替；Setup/Launcher 必须引用 evidence-root 中的实际文件并重算摘要，不能只填
裸 SHA。`--require-pass` 必须从可信 checkout/tag 编排显式接收 expected commit 和 release
candidate，缺失或不匹配即拒绝；同一 oracle artifact 或 execution ID 不能跨 entry 重放。
普通文本、截图、文件哈希和 manifest 自声明 `PASS` 不能替代上述结构化 oracle/Windows
制品；尚未进入结构化 profile 的通用证据即使内部一致，也只能作为非发布检查输入，公开
发布必须继续失败关闭。Oracle 未启动的失败项保持
`oracle=null` 并用 Execution 的 `NOT_STARTED` 状态证据，不得填 `INCONCLUSIVE`。FAIL 必须关联 defect 和
证据，BLOCKED 必须说明原因，NOT_RUN 的执行时间必须为 null。

上述 validator 只能证明结构、绑定、哈希和内部语义一致，不能证明 Windows JSON 来自可信
harness，也不能根据 `setup_signature_status=VALID` 的自声明验证 Authenticode、时间戳、
干净 VM 或物理行为。E4 仍须由受保护 Windows 11 runner 调用系统签名验证器和测试 harness
产生不可替代的外部证据；在该链路完成前门禁问题保持未关闭，`--require-pass` 无条件返回
`TRUSTED_RELEASE_ATTESTATION_NOT_IMPLEMENTED`。非发布校验即使得到结构
`gate_result=PASS`，也必须同时报告 `release_approved=false`，不得据此发布。

## 9. 正确性与数据质量

真实复制通过条件：

- 源端从运行前检查开始到独立 oracle 完成始终静默，前后指纹一致；目标活动锁覆盖复制与
  核验；Operator/DBA 排他声明为 `1.0/ACTIVE`、未撤回未过期，覆盖最后空表观察至目标
  一致性读事务结束且 `snapshot_finished_at <= valid_until`，确认/撤回审计与运行快照可追踪。
- Worker 启动 DataX 前生成目标空表证据，观测行数必须为 0。
- V1 JobSpec 脏数据阈值固定 `0/0`，真实运行脏行数必须为 0。
- 完整表测试的列集合完全一致。
- 选列测试只写入所选目标列，其他目标列保持数据库默认值或 NULL 的预期状态。
- 独立 oracle 按 6.2 对规范化行多重集比对，缺失/额外行数均为 0，重复行次数一致。
- DataX 退出 0 后 `process_state` 只进入 `VERIFYING`；oracle 启动前 `verification_state=NOT_STARTED`，启动后才进入 `VERIFYING`。Oracle PASSED 后才 `SUCCEEDED + CONFIRMED + PASSED`；CONFIRMED 仅表示影响已测得且可以为 0 行。
- 不允许静默截断、静默丢列或把失败解析为成功。
- 首页“已核验复制成功率”由独立 SQL 重算：
  `count(SUCCEEDED 且 PASSED) / count(SUCCEEDED + FAILED + TIMED_OUT + LOST)`；取消不进入
  分母，分母为 0 时为 `null`。

测试夹具必须固定随机种子并版本化；执行报告记录夹具版本和哈希。

- 非预期 5xx 比例 < 1%。
- Worker 领取已提交执行：p95 ≤ 2 秒。
- DataX 输出日志后，UI/API 可见延迟：p95 ≤ 3 秒。
- DataX 退出后，`VERIFYING` 可见延迟：p95 ≤ 3 秒；最终状态另记录 oracle 读取与比较耗时，不把外部数据库扫描时间伪装成控制面 3 秒 SLA。

浏览器在本地参考网络、冷缓存下：

- 登录后核心页面可交互时间 ≤ 3 秒。
- 页面切换后主要数据或明确加载态 ≤ 1 秒出现。

DataX 吞吐测试：

- 对四种 Reader/Writer 方向至少各执行一次 1,000,000 行公共类型数据复制。
- 数据正确性必须 100% 通过，进程不得 OOM，平台不得丢失状态或日志。
- 吞吐量、CPU 峰值、内存峰值、DataX channel 和批次参数必须记录。
- 第一版结果形成版本基线；后续同环境回归吞吐下降超过 20% 或资源峰值上升超过 20% 时阻塞发布，除非有书面解释和批准。

V1 单 Worker 默认最大并行 Execution 为 1。部署可调高，但调高后必须重新完成资源和稳定性验收。队列测试应对两个不同 TargetNamespace 提交运行，证明第二个执行保持 `QUEUED` 且不会启动额外 DataX 进程；同一 TargetNamespace 的第二个不同幂等键请求应在 API 层直接冲突，不属于容量排队。

## 11. 恢复与故障注入

V1 是单节点非 HA，不要求无中断切换，但必须保证状态可解释、可恢复且不自动造成重复插入。

必须验证：

| 恢复 ID | 故障 | 通过条件 |
| --- | --- | --- |
| REC-DB-001 | PostgreSQL 短暂不可用 | API 健康状态变为异常；恢复后可重新服务，无数据静默丢失 |
| REC-PG-NOTIFY-001 | PostgreSQL `LISTEN/NOTIFY` 提示丢失 | Worker 轮询兜底仍领取 QUEUED；无丢执行、无重复启动 |
| REC-BE-001 | Backend 重启 | 已保存配置和执行记录保持；重新登录后可查询 |
| REC-WORKER-001 | Worker 在排队期间重启 | 执行不丢失，恢复后只领取一次 |
| REC-WORKER-002 | Worker 在运行期间被终止且进程不可确认 | 执行最终进入 `LOST`，不无限保持 `RUNNING`，不自动重跑 |
| REC-DATAX-001 | DataX 进程非零退出 | 完整记录失败状态、脱敏 stderr 和退出码 |
| REC-HOST-001 | 整套 Compose 重启 | 数据库迁移状态、配置、任务和历史执行仍存在 |
| REC-WIN-RESTART-001 | Windows 11 重启 | Launcher 先完成迁移、端口和 fence/锁/进程对账再就绪；不重复执行 |
| REC-WIN-SLEEP-001 | Windows 睡眠/恢复 | 恢复期间明确不可用；旧 lease/fence 不推进，完成对账后才接收新执行 |
| REC-WIN-DOCKER-001 | Docker Desktop restart / `wsl --shutdown` | 无宿主 DataX 降级、无假健康；容器身份变化触发 LOST/恢复门禁与审计 |
| REC-CANCEL-001A | 未领取 `QUEUED+RESERVED` 收到取消请求 | reconciler 在 10 秒 SLO 内收敛，预留转 RELEASED；无 Attempt/fence/gate |
| REC-CANCEL-001B | Worker 已领取后收到取消请求 | 先温和终止进程组，宽限期后强制终止，最终进入 `CANCELED` 并保留恢复门禁 |
| REC-TIMEOUT-001 | DataX 超过墙钟超时 | 进程组被终止，最终进入 `TIMED_OUT`，日志与审计完整 |

V1 禁止在失败、取消、超时或 Worker 丢失后自动重跑。只有已经领取并形成
TargetCopyLock 从 ACTIVE 进入 RECOVERY_REQUIRED 的非成功终态进入恢复门禁：Operator/目标表所有者提交
`action/cleanup_performed/reason/confirmed_at` 处置确认；需要清理时记录实际动作，无需
清理时必须如实写 `NO_CLEANUP_REQUIRED/false` 和原因。API
创建独立 RecoveryProbe，Worker 以 probe 自身 fence 在同一 TargetNamespace 锁下复检为空
并把 RecoveryGate 写为 VERIFIED，之后才能由用户发起恢复后再次执行。未领取的 QUEUED
取消由 reconciler 收敛为 `CANCELED/NONE/NOT_STARTED`，不创建 Attempt/fence/gate，并把
创建时已有的 `RESERVED` 锁转为 `RELEASED`；UI/API
不能仅按 `CANCELED` 状态开放恢复入口。

备份恢复至少在另一台干净 Windows 11 x64 VM 验证一次。当前自动化已覆盖 DATA/SECRETS
导出、双包认证/配对、双恢复秘密认证 journal、全新空 staging、受 journal 限定的清理
和篡改/错包负例；另有 `LEGACY` 指针结构、摘要、路径/对象集合、不可覆盖提交与 Compose
变量注入的 E1 候选测试。staging 成功固定返回
`RESTORE_STAGED_COMMIT_BLOCKED`，不是完整恢复。下面第 1 项和第 2 项的文件 staging
子集已有 E1，所有真实 Windows、数据库提交与恢复验收仍为 `NOT_RUN/BLOCKED`：

- staging/journal 存在、损坏或检查失败时，普通 `start` 与 `backup` 必须在任何 secret、
  installation-id、卷初始化或备份读取前分别以稳定恢复门禁码失败；重启 Launcher 也不能
  把它识别成新装或擅自清理。

1. Launcher 在安全停写后导出配对包：`.dxdata` 只含 custom-format PostgreSQL 逻辑
   `pg_dump`、脱敏日志和固定发布元数据；`.dxkeys` 单独含四类数据库角色密码、
   JWT/HMAC 与受支持 KEK。禁止物理 volume/WAL、workspace、`job.json` 和未脱敏日志进入
   DATA 包。
2. Launcher 先拒绝任何旧身份、代际、运行 secret、产品容器或产品卷，再以固定无网络
   helper 完整认证配对包、用双秘密认证 journal 解包到受 ACL staging；随后必须
   在无旧 installation-id、活动代际、产品容器或产品卷的隔离干净 Windows 11 x64 VM、
   同一或明确兼容的已签名版本中，新建空 PostgreSQL volume、执行真实 `pg_restore`、
   重算数据库/审计链/日志/密钥证据，并以 `runtime-generation.json` 单一提交点选择三个
   卷、secret 与 installation-id；不得直接复制正在写入的卷目录。`LEGACY` 指针不能替代
   这一 `RESTORE` 提交，后半段仍
   `BLOCKED_NOT_IMPLEMENTED`。
3. 验证用户、项目、数据源密文、任务版本、执行和审计记录。
4. 验证恢复环境不能在缺少原密钥时错误显示凭据已可用。
5. 验证卸载默认保留三个 `des-*` named volumes 和导出备份，重装后可重新挂载并恢复；
   显式删除数据走单独二次确认路径。

恢复演练必须记录实际 RPO/RTO，并达到 RPO ≤ 24 小时、RTO ≤ 4 小时；超出即为未通过。

## 12. 证据分级

| 级别 | 含义 | 可证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| E0 | 代码/配置静态存在 | 文件和实现意图 | 可运行或正确 |
| E1 | 单元、契约、Mock/Fake 测试 | 局部逻辑和接口契约 | 真实依赖或 DataX |
| E2 | 真实平台依赖集成，但 DataX 可模拟 | PostgreSQL 队列/Worker 协作 | 真实数据复制 |
| E3 | 真实 MySQL/PostgreSQL + 固定 DataX + 产品 API/Backend/Worker + 独立 oracle；涉及 UI 的需求再加浏览器 | 本地真实复制闭环；以及被测 UI 需求的真实交互 | 打包部署和重启运维 |
| E4 | 从干净 Windows 11 x64 VM 验证签名 Setup/Launcher、前置依赖失败、浏览器、loopback-only、卸载保留、重启/睡眠/Docker/WSL 和备份恢复 | Windows 本地工作站可交付运行与恢复 | HA、生产规模或其他宿主平台 |

规则：

- V1 功能闭环最低要求 E3。
- 安装部署、重启和恢复最低要求 E4。
- Windows E4 只由 `E2E-WIN-001`/`E2E-WIN-002` 及其完整证据包产生；Windows runner
  构建、macOS/Linux 测试、EXE/镜像存在或人工跳过失败场景均不能提升到 E4。
- Mock DataX 即使全部自动化通过，也只能是 E1/E2。
- 截图只能作为辅助证据，不能单独提升等级。
- 打包成功不等于服务启动成功；服务启动成功不等于 DataX E2E 成功。
