## 1. 使用与发布规则

- 一行只对应一个需求 ID；禁止用 `001..004`、通配符或测试族替代逐条追踪。
- `需求级别` 只使用 `V1-MUST / POST-V1`；缺陷严重度另用 `P0/P1/P2/P3`，不得混用。
- `测试 ID` 必须精确且不含 `*`；唯一性边界是“需求 ID + 测试 ID”对。同一测试只有在
  同一个可复核执行确实同时证明多个需求时才可显式复用，每个需求仍分别生成 manifest
  条目；同一需求需要多个测试时，也拆成多个“需求 ID + 测试 ID”条目。
- `Oracle` 指独立判定规则，不得使用被测接口自己的成功字段证明自身正确。数据复制正确性固定使用 `oracle-v1`；oracle 从未启动时证据为 null 且 Execution 保持 `NOT_STARTED`，不得伪装为 `INCONCLUSIVE`。
- `证据字段` 是 acceptance manifest 中必须出现的最小产物；发布时填入真实相对路径和 SHA-256。当前 `基线` 只表示契约已定义，不表示实现或验收完成。
- 任一 `V1-MUST` 为 `FAIL / BLOCKED / NOT_RUN`，或缺少证据哈希，发布门禁均失败。
- 规范化 catalog 必须恰好包含 81 个唯一需求 ID（31 FR + 22 BR + 14 NFR + 14 ACC；
  80 V1-MUST + 1 POST-V1）；
  数量、ID 集合或“需求 ID + 测试 ID”唯一性不一致时失败关闭。
- Catalog 生成器必须按表头定位并只从 `测试 ID` 列解析测试 ID，不能从需求 ID、控制、
  Oracle 或证据描述中猜测；当前 81 个需求展开为 85 个精确“需求 + 测试”条目。

独立 CI validator 从本矩阵生成规范化需求 catalog，并把其 SHA-256 写入
`requirements_catalog_sha256`。Catalog 每项固定
`requirement_id / requirement_priority / test_id / minimum_evidence_level / evidence_requirements`；
`evidence_requirements` 根据明确的 `oracle-v1` 产物要求和 E4 Windows 最低证据生成。
validator 必须把 manifest entry 的五元组与本矩阵逐项精确比较，并拒绝
`result=PASS` 但 `evidence_level` 不精确等于 `minimum_evidence_level` 的条目；不得把 E3
自报为 E4 却不提交 Windows E4 结构化证据。随后对 catalog 的
全部 V1-MUST ID 与 manifest entries 做集合比对，生成 expected/covered 计数、缺失 ID 和
重复“需求 ID + 测试 ID”对。
`gate_result=PASS` 时缺失与重复数组必须为空、expected 与 covered 必须相等且
`catalog_exact_match=true`；JSON Schema
负责字段形状、证据等级顺序和空数组门禁，catalog 五元组相等、集合相等、计数相等和
catalog 哈希重算由独立 validator 负责。
