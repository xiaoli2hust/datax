# 部署、运维与安全方案

| 项 | V1 决策 |
|---|---|
| 拓扑 | 单节点 Docker Compose |
| 高可用 | 不支持 |
| 数据库 | PostgreSQL 15 |
| 队列/短期事件 | Redis 7 |
| 执行 | 独立 Worker 内固定 DataX Runtime |
| TLS | 入口反向代理终止 |
| 备份目标 | RPO 24 小时、RTO 4 小时 |
| 日志保留 | 执行日志 30 天、执行记录 365 天、审计 730 天，均可延长；缩短需合规批准 |

## 1. 部署边界

V1 面向企业内部试点：

- 一台 Linux 主机，推荐 8 vCPU、16 GB RAM、200 GB 可用 SSD。
- 只允许受控内网访问；数据库源/目标通过白名单开放。
- 单节点故障会导致服务不可用，运行中的任务可能进入 `LOST`。
- 通过备份恢复而非自动故障转移恢复。

生产 HA、Kubernetes、多 Worker 调度和跨地域容灾不属于 V1；没有另行设计和演练前不得宣传支持。

## 2. Compose 服务

| 服务 | 职责 | 持久化 | 就绪条件 |
|---|---|---|---|
| `web` | SPA 静态资源、同源反向代理、TLS 入口 | 无 | 静态资源可读且 API upstream 可达 |
| `api` | 认证、RBAC、项目/数据源/任务/执行 API | 无状态 | PostgreSQL 可用、迁移版本正确、主密钥可读、Redis 可用 |
| `worker` | 队列、租约、DataX 进程树、日志、状态推进 | 执行工作目录为临时；日志产物卷持久化 | Runtime 自检、数据库和 Redis 可用 |
| `postgres` | 唯一业务事实源 | 专用数据卷 | `pg_isready` 与只读探针通过 |
| `redis` | 队列、短期日志通知、协调 | AOF；仍可从 PostgreSQL 重建 | `PING`、写读探针通过 |

DataX 是 CLI Runtime，不部署为可被任意调用的网络服务。它与认证插件以只读方式进入 Worker 镜像或只读挂载，并通过 manifest 校验。

## 3. 网络分区

- `web` 是唯一对用户暴露的入口。
- `api` 仅接受 `web` 内网流量。
- `postgres`、`redis` 不映射到宿主公网。
- `worker` 不接受入站业务请求。
- `worker` 出站只允许访问获批数据源、DNS 和必要的内部服务。
- DataX 执行工作目录禁止访问 Docker Socket、宿主密钥目录和应用源码。
- 连接测试和元数据读取与正式执行使用相同网络策略，防止借接口做 SSRF/端口扫描。

生产试点必须使用网络白名单；不能只依赖应用层 JDBC URL 校验。

## 4. 配置与 Secret

仓库仅提交 `.env.example`。实际环境使用受限 Secret 文件或编排器 Secret：

| 配置 | 说明 |
|---|---|
| `APP_ENV` | `development/test/pilot`，生产式部署禁止 `development` |
| `DATABASE_URL_FILE` | PostgreSQL 连接串 Secret 文件 |
| `REDIS_URL_FILE` | Redis 连接串 Secret 文件 |
| `APP_MASTER_KEY_FILE` | 凭据 AEAD 主密钥文件 |
| `JWT_PRIVATE_KEY_FILE` / `JWT_PUBLIC_KEY_FILE` | Ed25519 签名密钥 |
| `DATAX_HOME` | 只读 Runtime 路径 |
| `DATAX_MANIFEST_PATH` | Runtime/插件摘要清单 |
| `EXECUTION_WORK_ROOT` | 每次执行独立临时目录的父路径 |
| `EXECUTION_LOG_ROOT` | 持久化日志产物目录 |

要求：

- Secret 文件权限 `0400` 或平台允许的最小权限。
- 容器以非 root 用户运行。
- 配置加载错误 fail closed；不得回退到硬编码默认密码。
- Secret 不进入命令行参数、环境转储、错误页、日志和审计详情。
- 主密钥、JWT 私钥与数据库备份分开保管。

## 5. 凭据保护

- 用户密码使用 Argon2id 哈希，不可逆。
- 数据源凭据使用带版本的 AES-256-GCM 或等价 AEAD 加密。
- 每条密文使用独立随机 nonce，并将项目、数据源 ID、密钥版本作为附加认证数据。
- API 从不返回密码；编辑数据源时空密码表示保留原凭据。
- Worker 运行前按权限解密，在独立目录生成 `0600` Job JSON。
- 进程启动后不在日志输出 Job JSON；运行终止后可靠删除临时文件。
- 密钥轮换采用“新写入使用新版本、后台重加密旧值、保留回滚窗口”的流程。

主密钥丢失会使数据源凭据不可恢复。备份恢复演练必须同时验证密钥材料，不得把密钥放入普通数据库备份。

## 6. DataX 执行隔离

每次执行：

1. Worker 获取带租约的 Execution。
2. 校验 JobVersion 哈希、Runtime manifest 和插件白名单。
3. 创建不可预测的独立工作目录。
4. 渲染最终 Job JSON，并仅在内存/临时文件中注入凭据。
5. 使用参数数组启动固定解释器与 `datax.py`；禁止 shell。
6. 设置 CPU、内存、进程数、打开文件数、磁盘和墙钟超时。
7. 捕获 stdout/stderr，先做敏感值替换再持久化。
8. 取消/超时时向进程组发送温和终止，超过宽限期再强制终止。
9. 写入最终状态、退出码、统计、日志摘要和产物哈希。
10. 清理临时凭据与工作目录；清理失败产生高优先级告警事件。

禁止用户控制可执行文件路径、工作目录、JAR 路径或 shell 参数。

## 6.1 初始 Admin 与账号恢复

V1 不提供公开注册。全新数据库迁移完成后，运维人员在 `api` 容器内执行一次性离线命令：

```text
python -m app.cli bootstrap-admin --email <admin-email>
```

临时密码通过交互式标准输入或受限文件描述符读取，禁止出现在命令行参数、环境变量、Compose 文件或日志中。

规则：

- 默认仅在用户表为空时成功。
- email 规范化后唯一，密码必须满足当前策略。
- 创建用户、组织级 Admin 授权和 `SYSTEM_BOOTSTRAP_ADMIN` 审计在一个事务内完成。
- 已存在用户时返回非零退出且不修改数据。
- 首次登录强制修改临时密码，并撤销 bootstrap 会话。
- 灾难恢复需要重置 Admin 时必须进入维护窗口，使用独立的 `recover-admin` 流程、双人审批和审计；不得删除或绕过现有授权记录。

## 7. 健康、就绪和启动顺序

- `/health/live`：进程事件循环可响应，不访问外部依赖。
- `/health/ready`：数据库迁移正确、PostgreSQL/Redis 可用、密钥文件可读。
- Worker readiness 还需 Runtime 自检和 manifest 校验。
- Web readiness 检查静态资源与 API 路由。

启动顺序：

`postgres/redis → migration job → api/worker → web`

迁移失败、Runtime 摘要不匹配或主密钥缺失时服务必须保持未就绪，禁止带病运行。

## 8. 可观测性

所有记录关联：

- `request_id`
- `actor_id`
- `project_id`
- `job_id` / `job_version_id`
- `execution_id`
- `attempt_no`
- `worker_id`

指标至少包括：

- HTTP 请求量、错误率、P50/P95/P99 延迟。
- 数据库连接池、Redis 队列长度和最老消息等待时间。
- Worker 心跳、租约、排队/运行/终态数量。
- DataX 启动耗时、运行耗时、读写记录、失败记录、字节和吞吐。
- 取消、超时、`LOST`、日志脱敏命中和清理失败数。
- 磁盘使用率、日志保留清理和备份结果。

结构化应用日志与 DataX 原始日志分开。原始日志不可被解析器改写；解析失败只影响指标，不改变基于退出码和规则得出的最终状态。

## 9. 日志和审计保留

- DataX 日志按 Execution 分块，使用单调游标、SHA-256 和长度记录。
- UI/API 默认读取脱敏日志。
- 单执行日志达到大小上限后继续保存末尾诊断窗口并标记 `truncated`；完整策略在部署配置中可调。
- 执行日志默认 30 天后清理；被事故/审计保全的记录例外。
- 审计事件默认 730 天，只允许追加和受控导出。
- 清理任务记录对象数量、范围和结果，并产生审计事件。

## 10. 备份与恢复

### 10.1 备份对象

- PostgreSQL 全量备份 + WAL/等价增量能力。
- Execution 日志产物卷及索引。
- 配置的非敏感部分、镜像 digest、迁移版本、Runtime manifest。
- 主密钥和 JWT 私钥由独立安全渠道备份。

### 10.2 周期

- 每日全量数据库备份，保留至少 14 天。
- 日志产物每日增量或快照。
- 每次发布前创建一致性备份。
- 每月至少一次恢复演练；试点上线前必须演练一次。

### 10.3 恢复验收

- 在隔离环境恢复。
- 校验迁移版本、行数、外键和审计链。
- 抽查 JobVersion 哈希、Execution 与日志产物哈希。
- 验证密钥可解密测试凭据，但不输出明文。
- 记录实际 RPO/RTO；超过 24 小时/4 小时需整改或正式豁免。

## 11. 升级与回滚

升级前：

- 停止接受新执行，等待或安全取消运行任务。
- 备份数据库、日志和密钥元数据。
- 校验新镜像、Runtime 和插件摘要。
- 在副本环境演练迁移与主链路 E2E。

升级顺序：

`备份 → 数据库兼容迁移 → api/worker → web → 冒烟与真实小数据 E2E`

回滚要求：

- 应用至少兼容一个迁移窗口。
- 破坏性迁移采用 expand/migrate/contract，不与代码一次删除旧列。
- Runtime/插件升级必须能恢复上一摘要。
- 若迁移不可逆，必须先恢复备份，不能伪称已回滚。

## 12. 事故处置

### 永久 RUNNING/心跳丢失

1. 阻止新执行领取。
2. 核对 Worker、PID/进程组和租约。
3. 清理确认的孤儿进程。
4. 将无法证明仍在运行的执行标记 `LOST`，不得标记成功。
5. 保留日志和审计，人工决定是否重跑。

### 凭据疑似泄露

1. 立即停止相关数据源执行并撤销凭据。
2. 隔离日志/产物，禁止继续传播。
3. 轮换数据源凭据和可能受影响的平台密钥。
4. 通过审计确定访问范围。
5. 修复脱敏或隔离缺陷并完成安全复盘。

### 磁盘接近满

1. 停止领取新执行。
2. 保留审计和事故相关日志。
3. 执行受控保留清理，不得直接删除数据库目录。
4. 扩容并验证文件系统、日志索引和备份。

## 13. 安全基线

- TLS 1.2+；安全 Cookie；严格 CORS；CSRF 防护按 Token 存放方式实现。
- 登录和连接测试限速；连续失败产生安全事件。
- 所有输入做长度、格式和枚举校验。
- 元数据值按纯文本展示；防止存储型 XSS 和日志伪造。
- 下载日志设置安全文件名和内容类型。
- API 错误不暴露堆栈、SQL、路径、连接串或内部网络。
- 镜像非 root、最小基础镜像、只读根文件系统（必要写目录显式挂载）。
- CI 生成 SBOM 并扫描依赖、镜像和 Secret。
- 高危/严重漏洞为发布阻断；豁免必须有范围、补偿控制、负责人和到期日。

## 14. 试点发布门禁

上线前必须确认：

- [ ] 全新主机按文档安装并通过 readiness。
- [ ] TLS、网络白名单和非 root 验证完成。
- [ ] 数据库、日志和密钥恢复演练通过。
- [ ] Runtime/插件 manifest 与实际文件一致。
- [ ] 真实 MySQL→PostgreSQL 主链路及失败/取消/恢复用例通过。
- [ ] 明文凭据扫描为 0。
- [ ] 高危/严重安全缺陷为 0。
- [ ] 基础设施监控的外部告警接收人、备份责任人和事故联系人已在私有运维配置中指定；这不代表 V1 已实现产品内通知中心。
- [ ] 已知限制明确展示为“单节点、离线批、无 HA”。

缺少任一 P0 门禁时，只能作为开发环境，不得称为已上线的企业平台。
