> 证明安全。当前 Worker 在 DataX 启动前只接受 `EXACT_IP`，并暂时拒绝尚未完成真实驱动

> 不能执行复制。该限制是 fail-closed 工程缺口，不是 V1 产品范围变更；解除前必须实现
> 独立 netns 或驱动级“selected IP 建连 + 原 FQDN 身份验证”，并完成 multi-A、DNS
> rebinding 到 control 子网和四方向真实数据库 E3。

## 1. 部署边界

V1 面向企业内部试点：

- 一台 Windows 11 x64 本地工作站，推荐 8 个逻辑 CPU、16 GiB RAM、200 GiB 可用 SSD。
- 当前仓库所在 Mac 只用于开发和自动化层验证；最终产品运行在另一台 Windows 11 x64
  电脑，必须在目标机重新完成安装、Docker Desktop/WSL2、真实 DataX、恢复和 E4 取证。
- Windows 10、Windows Server、ARM64、macOS、原生 Linux 宿主和远程共享服务器不属于
  V1 发布验收矩阵；源码开发结果不能替代 Windows 11 x64 交付验收。
- Docker Desktop、WSL2、CPU 虚拟化必须由用户或组织预先安装/启用并接受各自许可。
  `Setup.exe` 和 `launcher.exe` 只能检测并给出官方获取路径，不得静默安装、启用
  Windows 可选功能、修改固件设置或代替用户接受 Docker Desktop 许可。
- 产品自身只允许本机 `127.0.0.1:17860` loopback 入站；这里的受控网络仅指到数据库源/目标的
  出站访问，它们必须同时通过 Admin EndpointPolicy、DNS 安全解析和主机/容器级默认拒绝
  egress enforcement，绝不因此开放 LAN 入站。
- 单节点故障会导致服务不可用，运行中的任务可能进入 `LOST`。
- 发布目标通过经过验收的备份恢复而非自动故障转移恢复；当前安全导出、双包认证
  journal 和全新空 staging 已测到 E1，但新空 PostgreSQL volume、真实 `pg_restore`、
  证据重算、卷/secret 原子提交与异机演练尚未完成，所以不能承诺系统可恢复性。

生产 HA、Kubernetes、多 Worker 调度和跨地域容灾不属于 V1；没有另行设计和演练前不得宣传支持。

### 1.1 Windows 文件与数据边界

| 类别 | 默认位置 | 卸载行为 |
|---|---|---|
| 程序、Launcher、Compose 清单 | `%LOCALAPPDATA%\Programs\DataXEnterpriseStudio\` | 删除 |
| 配置引用 | `%LOCALAPPDATA%\DataXEnterpriseStudio\config\` | 保留 |
| 活动运行代际 | `%LOCALAPPDATA%\DataXEnterpriseStudio\runtime-generation.json`；受 ACL 保护、不可覆盖原子提交 | 保留；Launcher 不自动替换 |
| PostgreSQL/脱敏日志/不含秘密的 oracle 工作数据 | 活动代际选择的三个 Docker named volumes；`LEGACY` 为 `des-postgres-data`、`des-log-data`、`des-workspace-data` | 保留，不映射为 Windows 宿主路径 |
| 用户备份 | 用户为 DATA/SECRETS 分别选择的两个本地新目录；无固定默认目录 | 位于程序目录外，不由卸载器删除 |
| Launcher 诊断日志 | `%LOCALAPPDATA%\DataXEnterpriseStudio\launcher-logs\` | 保留，按保留策略清理 |

安装目录、Docker named volumes 与导出备份目录必须分离。业务数据不得用 Windows bind
mount 模拟 named volume；当前 Windows 用户拥有配置/备份目录，其他普通用户无访问权。
Launcher 拒绝符号链接/reparse point、UNC 路径、网络盘和超出已批准根目录的宿主挂载。
其他本机普通用户不得读取 secrets 或修改当前用户的程序/配置目录；但 V1 是
`%LOCALAPPDATA%` 下的按用户安装，当前 Windows 用户及本机管理员属于宿主信任边界。
Launcher 每次校验 Authenticode 信任链、被清单绑定的发布证书 DER SHA-256 允许集、
资源哈希和镜像 manifest 并在发现篡改时失败关闭，
不得把这种检测能力描述成“对当前用户不可变”或“能抵抗已攻陷宿主”。
Launcher 还必须用 OS CSPRNG 生成受 ACL 保护的安装实例标识，并要求三个 `des-*` 卷
同时存在、installation-id 与各自 role 标签完全匹配。Docker 重置、部分卷丢失、已有卷
缺少实例标识或标签不符时停止启动，不得自动创建空库掩盖数据丢失。
首次初始化必须先写 ACL 受控的 `initialization-incomplete` 日志，完整生成和校验全部
本机 secret 后才可创建 named volume，三个卷及标签全部通过后才提交旧式
`installation-id`，再以同目录、不覆盖、write-through rename 提交包含整组引用和域分离摘要的
`LEGACY` 活动指针，最后清除日志。Compose 不再分别拼装 secret、installation-id 与卷名，
必须从已验证指针整组注入。断电/崩溃恢复只允许在日志仍有效、当前没有产品或数据卷
消费者、已存在卷标签匹配且卷出现时 secret 集合已完整的状态下补齐；零卷阶段可以清理
并整组重新生成从未使用的未提交 secret。任何状态矛盾都失败关闭，不自动删除卷、容器
或可能已有的数据。

### 1.2 `Setup.exe` 合同

1. 验证 Windows 11、x64、可用磁盘和当前安装版本；显示发布者、版本、许可证与将安装的组件。
   安装根固定为当前用户 `%LOCALAPPDATA%\Programs\DataXEnterpriseStudio`：NSIS 在
   `.onInit` 中拒绝 `/D=<path>` 覆盖，并以 `CRCCheck force` 拒绝 `/NCRC` 跳过自身的
   损坏校验；不支持 `/S` 静默模式，必须以非零退出拒绝。每次 install、repair 与 uninstall
   在停止服务、写入或删除前检查固定根、`resources` 和既有发布文件没有 reparse point。
   CRC 只是损坏检测，不能替代 Authenticode 或抵抗重新制作的恶意安装器。
2. 在写入程序目录前，先从已显式初始化的安装器临时目录运行 Launcher，验证 Launcher/Setup 的
   Authenticode 信任链、被 Launcher 编译期摘要绑定的清单 1.1，并要求两者只有一个主
   签名者、实际证书 DER SHA-256 完全相同且属于清单中的 1–8 项严格排序允许集；任一
   缺失、无效或不匹配即中止。通过后才安装已签名 `launcher.exe`、只读
   Compose/manifest、卸载器和桌面/开始菜单快捷方式。
3. 同版本 repair 必须先完成上一条候选包核验，才尝试停止现有服务；随后显式解除已安装
   发布资源的只读属性，使用 `SetOverwrite on` 与 `AllowSkipFiles off` 写入。任一停止、属性
   解除或写入失败都中止，不允许把健康旧版本因无效候选包提前停止，也不允许用户跳过资源。
   卸载器从当前用户注册表记录重新绑定固定安装根，避免临时 self-copy 把 stop/delete 指向
   错误目录。NSIS 的属性检查只能拒绝稳定的 junction/symlink/reparse point；hardlink 与同用户
   检查—使用 TOCTOU 仍未由路径 API 消除，不能把这一层写成强路径完整性保证。
4. 不包含、不静默下载或安装 Docker Desktop/WSL2，不执行 `wsl --install`，不改变虚拟化、
   Windows Defender Firewall、组织策略或 Docker Desktop 许可状态。
5. 校验所有安装文件 SHA-256；当前工程候选只允许全新安装并拒绝升级。未来只有在备份、
   迁移和回滚 helper 通过 Windows 验收后才可启用升级，且禁止无明确确认的降级。
6. 安装成功只证明程序文件落盘；不宣称容器、数据库或真实复制已经通过。

上述 `/D`、`/NCRC`、`/S` 拒绝、稳定 reparse 防护、候选核验顺序、只读 repair 与卸载根绑定
目前只有源码静态回归测试（E1）。尚未在 Windows 上以真实 NSIS 编译的签名 `Setup.exe` 验证，
也未执行 junction/symlink、hardlink 或检查—使用竞争负例，不能提升为安装 E4 证据。

发布文件命名固定为 `DataX-Enterprise-Studio-Setup-<version>-x64.exe`，发布页同时提供
SHA-256、Authenticode 签名/时间戳和发布证书 DER SHA-256、SBOM、第三方许可证及固定
镜像 digest 清单。发布流水线中的允许集来自受保护 environment secret；运行时不从
用户环境变量、配置文件或注册表覆盖。允许集经清单精确哈希绑定到已签名 Launcher，
轮换时可短期列出最多 8 张证书，但 Setup 与 Launcher 在一次候选中仍必须使用同一张。
该自校验只能约束正式安装器及发现局部替换；它不能认证一个已在运行且主动删除校验逻辑
的恶意重打包 Setup。首次执行前仍必须由 Windows/组织发布工具从安装器外部核对固定发布
证书 SHA-256 和发布页文件 SHA-256；当前用户或管理员完全控制宿主属于既定信任边界。

### 1.3 `launcher.exe` 启停合同

Launcher 每次启动按顺序执行：

1. 校验自身 Authenticode 信任链、唯一主签名证书 DER SHA-256、清单内固定允许集、
   Compose 清单、镜像 manifest 和安装版本；解析路径时拒绝当前目录劫持。
2. 在任何 Docker/Compose 子进程前，在缺失时创建并每次回读校验
   `%LOCALAPPDATA%\DataXEnterpriseStudio\docker-cli-config\config.json`：目录与文件 DACL
   只允许当前用户和 `SYSTEM`，目录只能含一个字节完全等于 `{"auths":{}}` 的
   `config.json`；已存在的改写、额外文件或 ACL 不符一律失败关闭，不会被“重建”覆盖。
   Launcher 发现继承的 `DOCKER_HOST`/`DOCKER_CONTEXT` 即拒绝启动；受控子进程还显式剥离
   Docker transport/TLS/认证/credential-helper、`DOCKER_DEFAULT_PLATFORM`、custom header、
   BuildKit、上/小写代理变量，以及 Compose 的 env-file/project/profile/行为/输出覆盖变量。
   它只重新注入 Launcher 派生的镜像/secret/volume 值、匿名 config 和已经验证的固定本机
   Docker Desktop named pipe。任一固定 pipe 不能实际返回 `linux|amd64` 时以安全错误停止，
   绝不读取用户 registry 登录、credential helper 或 Docker context；Docker Desktop daemon
   的组织级代理配置是独立前置，不经 CLI 子进程环境继承。
3. 检查 Windows 11 x64、硬件虚拟化、WSL2、Docker Desktop 安装且 Engine 正在运行，
   以及 `docker compose` 版本；Docker 实际 Linux/amd64 backend 才是准入事实，注册表中
   新发行版的 DefaultVersion 只能作诊断，不能造成 Docker 正常时的假阻断。缺失项显示可操作
   说明并返回非零，不伪装成功。
4. 检查数据目录 ACL/reparse point、安装实例标识、三个 named volume 的同存同失与
   role 标签；40 GiB 只保护当前安装/用户目录，不能代表 Docker Desktop/WSL VHD 或 named
   volume 的实际数据盘。`start` 与 `backup` 都先确认五个固定 Linux/amd64 镜像本地可用；仅
   缺失镜像以 Launcher-owned 空 Docker config 按 immutable digest 拉取，缓存完整时不访问
   registry。预取完成后所有产品 `docker run` helper 与 `compose up` 都显式 `--pull=never`；缓存
   被并发 Docker 操作删除时必须失败关闭，不能在容量 admission 后重新下载。`start` 在认证活动
   代际及三卷身份后、`compose up` 前，`backup` 在创建 staging
   前，都会以固定参数数组运行带 opaque name/双标签的 release-locked Worker 容量 probe：三个
   当前 generation **local、无 options** 卷只读挂到固定 `/probe/*`、`network=none`、无 secret、
   只读根、`0:0`、`cap_drop=ALL` 后仅加 `DAC_READ_SEARCH`、`no-new-privileges`、16 PID、64 MiB、
   0.25 CPU；probe 仅执行 `statvfs` 并返回严格固定顺序的每卷可用字节。该 capability 能绕过
   普通文件读取和目录搜索权限，故它不是卷内容保密控制；无网络/secret/写挂载以及固定脚本和
   精确 Worker digest 才限制受信 probe 的实际行为。它使用 `--pull=never`，Docker 命令失败、
   协议异常或任一卷低于 200 GiB 都以稳定错误失败关闭；错误/超时/无效输出时只按重新认证
   immutable ID 清理同名 probe 容器，不将本地安装目录余量冒充 Docker 容量。容量拒绝不表示没有
   先前 side effect：受控初始化或镜像缓存可能保留，但 Compose/业务数据库尚未启动。此处的源码/
   单元回归是 E1；不同数据盘、临界容量、运行中耗尽、`0700` 权限、Docker timeout/残留/cleanup
   竞争和真实宿主行为仍需 Windows E4。完整旧式集合可一次性原子登记为 `LEGACY` 活动代际，
   部分集合、指针篡改或身份不一致均失败关闭。当前版本发现既有安装需要升级时必须因备份/迁移
   闭环未实现而拒绝，不得跳过前置条件。
5. 检查 `127.0.0.1:17860` 未被占用；不自动换端口、不终止未知进程。
6. 验证/加载五个固定 digest Linux 镜像。对既有 Compose project 执行 lifecycle、`up`、`down`
   或 cleanup 前，逐一认证 immutable container ID、唯一预期 service、精确锁定 image、正确
   project/service label 及有状态卷的 installation identity；未知、重复、镜像/挂载不符均失败关闭
   且不触碰容器。禁止将 project label 当作所有权 oracle 或使用 `--remove-orphans` 扩大清理范围。
   认证通过后才幂等执行迁移和 `docker compose up --pull never -d`；迁移完成后必须先等 `egress-guard`
   证明 healthy，再启动共享其 netns 的 API/Worker。
7. 枚举实际 Compose 端口和宿主监听：只允许 Web `127.0.0.1:17860`；发现
   `0.0.0.0`、`::` 或 API/Worker/egress-guard/PostgreSQL/DataX 宿主映射时立即停止并
   报安全错误。读取 API、Worker、守卫的 `/proc/self/ns/net`，三者不完全相同也立即停止。
   `up` 后的卷身份、实际端口、共享 netns、live、容器 secret target、lifecycle 或 readiness
   任一安全检查失败时，Launcher 只能对已认证完整产品栈执行不带 `--volumes` 的受控
   `compose down`；如果清理自身失败，返回 `STARTUP_CLEANUP_FAILED` 并同时保留主失败码与
   清理失败码，不得显示已安全停止。恢复对账仍在 draining、首次管理员流程由用户取消、或浏览器
   打开失败不属于不健康栈，服务保持可供受控重试。
8. 等待 readiness。恢复自睡眠、Windows/WSL/Docker 重启时，必须先完成队列、两类 fence、
   TargetCopyLock、RecoveryProbe 和孤儿进程对账，再开放新执行。
9. readiness 通过后才用默认浏览器打开 `http://127.0.0.1:17860`。

正式候选的五个固定镜像必须是公开可匿名读取的 digest。发布流水线在生成 Windows
候选包之前，以全新、固定空 `auths` 的临时 `DOCKER_CONFIG` 逐项执行
`linux/amd64` pull，并把结果写入 `anonymous-image-pulls.json`；Windows 候选验证器
再将该证据与最终镜像锁逐项比对。Linux build evidence 的 lock、Windows handoff 顶层
lock 与安装器内嵌 lock 必须逐字节一致；托管 attestor 还须独立下载 Linux build artifact、
验证其 `SHA256SUMS`，并使 candidate-root 递归比对该独立来源与候选内 `linux-evidence/` 的
全量文件路径、大小和 SHA-256。Windows handoff 或 candidate-root 任一处不一致均失败关闭；
该检查不证明 Windows 二进制或工具链的源码来源。Launcher 不提供、索取或保存 GHCR/Docker Hub
登录凭据；若任一镜像只能由已登录的发布 runner 拉取，发布流程必须失败。

“停止”在固定安全预检通过后执行不带 `--volumes` 的受控 `docker compose down`，保留
三个 named volume；“退出 Launcher”不等于停止容器，UI
必须明确。卸载默认先提示停止服务，只删除程序/快捷方式/注册项，保留配置、数据、备份、
密钥引用和审计。重新安装同版本或更高兼容版本后，必须可重新关联保留数据并通过迁移/
恢复检查。清除数据是独立危险操作，需要再次输入数据目录确认，不属于静默卸载。

## 2. Compose 服务

| 服务 | 职责 | 持久化 | 就绪条件 |
|---|---|---|---|
| `web` | SPA 静态资源、同源反向代理、唯一宿主入口 | 无 | 静态资源可读且 API upstream 可达 |
| `egress-guard` | 默认拒绝 nftables、ACTIVE policy 只读视图、loopback attestation、selected-IP 租约 | 无；token 只在内存 | DB view 可读、nft 原子 apply/readback、规则未漂移、证明未过期 |
| `api` | 认证、RBAC、项目/端点/数据源/任务/执行 API | 无状态 | PostgreSQL/迁移正确、KEK keyring 可读、追加式审计事件哈希链可验证 |
| `worker` | 两类 PostgreSQL 事实队列、持久公平游标、Execution/RecoveryProbe 独立围栏、reconciler 取消/对账、预检、DataX、LogGap、oracle；单个共享 Engine pool（4、无 overflow、5 秒超时） | `des-workspace-data` 仅存不含明文凭据的有界 oracle 工作区；DataX 进程工作目录、含密 Job、未脱敏 Runtime 日志/性能临时文件只进 `/tmp` tmpfs 并按 Attempt 清理；`des-log-data` 只持久化脱敏日志 | Runtime、数据库、两类 keyring、DNS/egress、水位、工作/日志卷、敏感 tmpfs 清理、两类 fence 探针及 Worker 连接预算可用 |
| `postgres` | 唯一业务事实源和任务队列 | 专用数据卷 | `pg_isready`、读写/锁/NOTIFY 探针通过 |

DataX 是 CLI Runtime，不部署为可被任意调用的网络服务。它与认证插件以只读方式进入 Worker 镜像或只读挂载，并通过 manifest 校验。

当前固定基础镜像为：`postgres` 服务和 `egress-guard` 使用固定摘要的 PostgreSQL
`15.18-alpine3.24`；API 与 Worker 的最终 Python 运行层使用固定摘要的 Python 3.12.13
`slim-trixie`（Debian 13）。发布仍只接受 `repository@sha256`，版本字符串不能替代
digest 校验。

Compose 固定 Worker 的 `/tmp` tmpfs 为 256 MiB，并限制 2 GiB 内存、2 CPU、256 PID 与
`nofile=4096/8192`；耗尽时失败关闭。Worker 的控制、凭据和心跳服务共用一个最多 4 条、无
overflow、5 秒获取超时的数据库 pool；迁移 `0016` 将 `datax_worker` 角色上限设为 12，迁移
`0017` 为该角色设定 30 秒空闲/15 秒空闲事务服务端回收；`0018` 新增审计链 watermark，
`0019` 为 `DatasourceUsageGrant` 增加单调授权代际，均不改变运行角色的权限边界。12 条只覆盖当前 Worker 加最多两代
残留会话的有界缓冲；异常压力下 admission 失败关闭并等待重试，不是无限重启或 HA 承诺。
迁移 owner、`datax_api`、`datax_worker` 使用独立密码，owner secret 只进入迁移任务；
API/Worker 运行角色无 DDL/TEMP 权限。`0013` 仍给两个运行角色相同的全表 DML，不能声称
数据库已经强制 API/Worker 的细粒度状态职责。

Compose 的唯一宿主端口映射必须等价于：

```yaml
ports:
  - "127.0.0.1:17860:8080"
```

`api`、`worker`、`egress-guard`、`postgres` 不得存在 `ports:`；只使用内部
network/expose。Docker
Socket、Windows 命名管道和宿主用户目录不得挂载进业务容器。

## 3. 网络分区

- `web` 是唯一对 Windows 宿主暴露的入口，仅绑定 `127.0.0.1:17860`。
- `web` 通过 `egress-guard:8000` 到达共享 netns 内的 API。
- `api`、`postgres`、`worker`、`egress-guard` 和 DataX 不映射任何宿主端口。
- 只有 `egress-guard` 获得 `NET_ADMIN`；API/Worker
  `network_mode: service:egress-guard` 且 `cap_drop: [ALL]`，迁移任务只加入
  `control` 网络。
- `worker` 不接受入站业务请求。
- 共享 netns 的 output hook 默认拒绝，只长期允许 Docker DNS、完整 `lo` 回环接口和
  `control` 子网；完整 `lo` 是让 guard/API 的请求与随机回包端口双向可达，不是 LAN/WAN
  出口。外部数据库只允许守卫生成的 selected-IP `/32|/128 + TCP port` 短租约。DataX
  子进程继承相同策略。
- DataX 执行工作目录禁止访问 Docker Socket、宿主密钥目录和应用源码。
- 连接测试和元数据读取与正式执行使用相同网络策略，防止借接口做 SSRF/端口扫描。
- `POST /v1/leases` 不是“只要处于共享 netns 就可信”的接口：除 JSON body 外，调用者必须
  恰好携带一个 `X-DataX-Egress-Lease-Capability`。Launcher 用 32 个 OS CSPRNG 原始字节
  生成其 64 个 ASCII 小写十六进制字符值；Compose 只读挂载给 `egress-guard`、API、Worker，
  `migrate`、`postgres`、`web` 不得获得。guard 在读取 body、策略或调用 controller 前以
  常量时间比较；缺失、重复、格式错误或不匹配一律 `401 LEASE_CREATION_AUTH_INVALID`，且值
  不得进入响应、日志、Job JSON 或 DataX 子进程环境。DataX 与 Worker 同 UID/文件系统，故该
  值不是同 UID RCE 的 sandbox；该残余风险必须在 Windows E4 报告中如实保留。

生产试点必须使用真实网络出口规则；不能只依赖应用层 JDBC URL 校验。每次连接固定不可变
EndpointPolicyRevision。对 FQDN，连接前校验全部 A/AAAA/CNAME，拒绝混合允许/禁止地址；
随后申请守卫生成 ID 和随机 bearer token 的 selected-IP 租约。守卫重新读取当前 ACTIVE
view，CIDR×port 只作准入，内核只写精确 IP+port；JDBC 二次解析到同 CIDR 内另一 IP 也
必须被拒绝；落入运行时 `control` 子网的 selected IP 即使匹配策略也不得获得租约。
逻辑租约 30 秒、5 秒续租、内核元素最多 15 秒，连接结束立即释放；撤策、
数据库失败、规则漂移或守卫死亡时失败关闭。TLS hostname 和实际 peer IP 仍须核验。
连接测试、元数据、空表预检、oracle、RecoveryProbe 与正式运行使用同一
resolver/attestation/lease 实施，但分别保存实际 policy/resolver/egress/lease 证据，
不能复用过期结果。详见
[`contracts/egress-guard.v1.md`](./contracts/egress-guard.v1.md)。

MySQL DataX 固定使用 Connector/J `9.7.0`。平台的 `VERIFY_CA` 映射为
`sslMode=VERIFY_CA`，`VERIFY_FULL` 映射为 `sslMode=VERIFY_IDENTITY`；两者不得生成相同
参数，也不得回退到旧 `useSSL/requireSSL/verifyServerCertificate` 组合。校验模式使用
镜像内固定 JRE truststore；证书链或 FQDN 身份不匹配时连接必须失败。企业私有 CA 的
受控注入尚未形成发布制品合同，当前应视为 E3/E4 待验收项，不能通过关闭验证来兼容。

V1 不创建 LAN 入站防火墙例外。Windows Defender Firewall 即使被用户关闭，loopback-only
绑定仍必须成立；发布测试从第二台主机验证端口不可达，并检查 IPv4/IPv6 监听。

`AUDIT_ANCHOR_PRIVATE_KEY_FILE`、`AUDIT_ANCHOR_KEY_VERSION`、
`AUDIT_ANCHOR_PUBLIC_KEYRING_DIR`、`AUDIT_ANCHOR_GENESIS_FINGERPRINT_FILE` 和
`AUDIT_ANCHOR_TARGET` 仅是后述发布目标的保留名称，当前配置加载器和运行时没有实现这些
能力。部署中设置这些名称不会产生外部锚点，也不得据此解除发布门禁。

要求：

- 容器内 Secret 文件权限 `0400` 或镜像允许的最小权限；Windows 宿主配置/密钥引用目录
  使用当前用户与 SYSTEM 的显式 ACL，禁止 Users/Everyone 继承写权限。
- 业务容器以非 root 用户运行。唯一受控例外是容量 probe：它以 UID `0:0` 启动，但先
  `cap_drop=ALL`，只回加 `DAC_READ_SEARCH` 以穿越 PostgreSQL `0700` 卷根；Linux 语义下该
  capability 也可绕过普通文件读权限和目录搜索权限。它没有网络、secret、可写 root filesystem
  或可写 volume，且只给精确 digest 的 Worker 以固定 `statvfs` 参数脚本运行；这降低已受信代码的
  攻击面，却不是对卷内容的内核保密隔离。若 E4 证明可在非 root 下稳定读取，必须移除该例外或经
  ADR 重新评估。
- 配置加载错误 fail closed；不得回退到硬编码默认密码。
- Secret 不进入命令行参数、环境转储、错误页、日志和审计详情。
- KEK keyring、JWT 私钥与未来数据库备份必须彼此分开保管。外部审计锚定实现后，其
  私钥、公钥 keyring 与数据库写账号也必须按第 9 节目标合同隔离；当前不存在可保管或
  可验证的审计锚定私钥/keyring。
- Windows Launcher 生成的首个数据源凭据 KEK 必须是独立 32-byte OS CSPRNG 原始密钥，
  不能与 refresh-token/idempotency HMAC key 复用；仅 API 与 Worker 获得版本化只读
  secret 挂载。
- Worker 初始化只对已登记的 `ACTIVE` KEK 做普通只读查询与本地指纹核验；缺少、状态、
  算法或指纹不匹配即拒绝建立 dispatcher，绝不插入、轮换或锁定 `kek_key_versions`。
  默认 API/bootstrap 路径仍可登记首个活动 KEK。此实现层收敛只移除了 Worker 对该表的
  启动写入前提；运行角色的 PostgreSQL 细粒度 DML grant/直接 SQL 拒绝仍须按 ADR-0013
  和写权限矩阵完成迁移与真实 PostgreSQL 反例取证。

## 5. 凭据保护

- 用户密码使用 Argon2id 哈希，不可逆。
- 数据源凭据使用每条 CredentialSecret 独立 DEK 的 AES-256-GCM；DEK 的包裹物单独保存
  为版本化 CredentialSecretEnvelope，并由版本化 KEK 通过 AES-256-KWP 包裹。实现若
  更换算法必须先更新 ADR、迁移和恢复测试。
- 每条密文使用独立随机 nonce。数据 AEAD AAD 精确绑定组织、项目、Datasource、
  CredentialSecret ID/版本、AAD schema version 与数据算法，明确不包含 KEK version、
  Envelope ID/版本或 wrapping algorithm。
- API 从不返回密码；编辑数据源时空密码表示保留原凭据。
- Worker 必须在事实领取事务内、任何 DNS/JDBC/DataX 连接前固定两端 `ACTIVE`
  CredentialSecret 和 ACTIVE Envelope；随后按权限解密，在
  `/tmp/datax-studio-sensitive` tmpfs 的独立 `0700` Attempt 目录生成 `0600` Job JSON。
  文件必须以 `O_EXCL|O_NOFOLLOW` 原子创建，禁止先连通再补记 secret 版本。
- Worker 对每一端固定 secret 的解密使用独立、全新的短事务，以 `FOR UPDATE` 加强制刷新
  状态读取后立即解密并释放数据库锁；不得把该锁持有到 DNS/JDBC/DataX 运行期，也不得让两端
  共用可能缓存旧状态的 Session。两端解密之间与每个外部 I/O 边界都重读安全终止事实；对
  可变 `bytearray` 在 Attempt 退出时尽力清零，但 Python、驱动、JVM 或子进程的不可控副本
  不能被宣称完整内存擦除。
- 未脱敏 DataX Runtime 日志/性能临时文件同样只写该 tmpfs Attempt；子进程 umask 固定
  `0077`。进程启动后不在持久日志输出 Job JSON；运行终止后删除敏感 Attempt。
- Worker 启动和每轮 Execution/RecoveryProbe admission 前，只能清理名称包含规范
  Execution/Attempt UUID、所有者/权限正确且产品标记逐字节匹配的过期目录；未知条目、
  符号链接、跨挂载或清理错误都阻断新领取，不自动删除无法证明归属的内容。
- keyring 同时保留一个 `ACTIVE` 写入 KEK 和保留期内所需的 `DECRYPT_ONLY` 旧 KEK。
- KEK 轮换顺序固定为：生成新版本并双人登记 → readiness 验证指纹 → 新写入切换新版本
  → 后台为每个 secret 插入新 Envelope、切换 ACTIVE/SUPERSEDED，只解包/重包 DEK 而不
  改写业务 ciphertext/nonce/AAD → 抽样/全量恢复探针 → 保留到所有旧备份过期 → 双人
  批准销毁。回滚只切换写入/ACTIVE Envelope，不覆盖旧 key 文件或旧 Envelope。
- Secret 生命周期为 `ACTIVE/RETIRED/REVOKED/COMPROMISED`。普通轮换必须先切换 Datasource
  current secret，再把旧 secret `RETIRED`；直接退役 current secret 返回
  `CREDENTIAL_STATUS_CONFLICT`，仅已固定的历史 secret 工作可继续。若轮换后才发现泄露，
  `RETIRED` 只能进一步升级为
  `REVOKED/COMPROMISED`，不得重新激活或降级。紧急状态原子禁用 current 指向它的
  Datasource、禁止状态提交后开始的解密与新连接，并为所有已绑定它的非终态 Execution/RecoveryProbe 建立
  每 secret 独立的终止事实；若该 secret 仍是 current，还覆盖尚未绑定 secret、但不可变引用
  该 DatasourceRevision 的排队 Execution/RecoveryProbe。Execution 在启动、DataX process tick、
  oracle 有界回调和 heartbeat 消费该事实；预检的每次 DNS/connector（含 probe 查询间隙）/
  schema/fingerprint/count 有界 I/O 和
  process helper 的 Popen 紧前同样消费；heartbeat ACK 后不再续租。RecoveryProbe 在 heartbeat
  及每个有界 DNS/连接/schema/count 查询边界消费。阻塞 JDBC 调用只能等连接/查询超时或 lease 到期后的保守
  `LOST/INCONCLUSIVE` 回退，运维界面不得声称平台已同步中断该调用。

数据库撤销和 OS 进程创建不是一个可合并的原子事务。Popen 紧前的 helper 内复检只保证
“已观察到终止时不创建新的 DataX 进程组”；实际提交到外部连接/既有进程停止的时间边界仍须
在真实 PostgreSQL 与真实 DataX E2/E3 取证，不能由本地单元测试宣称为即时停止。

任一保留期内 KEK 或所需 Envelope 丢失都会使对应凭据不可恢复。备份恢复演练必须同时
验证新旧 key/Envelope 及旧备份，keyring 不得进入普通数据库备份。密钥恢复探针与
目标处置 RecoveryProbe 是两种不同机制，均只报告哈希/成功状态，不输出明文。

## 6. DataX 执行隔离

每次执行：

1. API 创建 Execution 时已按不可变 TargetNamespace 原子创建
   `TargetCopyLock=RESERVED`。Worker 通过 PostgreSQL 持久项目服务游标公平领取；同一
   事务锁定并校验该预留、创建 Attempt、递增 `fence_epoch`、设置 active
   attempt/lease，把预留转 `ACTIVE`，并固定两端 DatasourceRevision、
   EndpointPolicyRevision、`ACTIVE` CredentialSecret 及 ACTIVE Envelope。事务提交前
   禁止任何外部连接。
2. 校验 JobVersion 哈希、两个 PhysicalEndpointIdentity/物理表 hash、方向授权、
   TransferPolicy 精确表/列 `scope_hash`、Runtime manifest、插件白名单和固定
   `dirty_data_limit=0/0`。物理源/目标 hash 相等即拒绝，不允许换
   revision/hostname 绕过。
3. 提交领取事务后，通过固定 EndpointPolicyRevision、受信 resolver/真实 egress 策略
   连接；每阶段保存全部解析结果、selected/peer IP、TTL、resolver/egress 版本和证据
   哈希。确认源静默，并确认目标外部独占声明的 `statement_version='1.0'`、
   `valid_until` 尚未到达、状态为 `ACTIVE` 且无撤回事实；校验 Schema/约束无漂移，并由
   Worker 强校验目标 `COUNT(*)=0`，保存 `target_empty_evidence` 和独占窗口起点。状态推进
   期间继续读取已持久化的撤回/过期事实；平台锁不能替代外部 DML/DDL 约束，也不能证明
   所有未报告或已回滚的外部写从未发生。
4. 清理可证明属于产品的过期敏感 tmpfs Attempt；失败即阻断领取。创建不可预测的独立
   持久工作目录和 `0700` tmpfs Attempt 目录。
5. 渲染最终 Job JSON，并仅在内存/该 tmpfs Attempt 的原子 `0600` 临时文件中注入凭据；
   未脱敏 Runtime 日志与性能临时文件也只写该 Attempt。
6. 使用参数数组启动固定解释器与 `datax.py`；禁止 shell。记录 boot ID、PID start time、
   PGID 和 cgroup/container identity。
7. 设置 CPU、内存、进程数、打开文件数、磁盘和墙钟超时。
8. 捕获 stdout/stderr，先做敏感值替换再持久化脱敏后的原序日志。
9. 取消/超时时只向身份完整匹配的进程树温和终止，超过宽限期再强制终止。
10. DataX exit 0 后进入 `VERIFYING`；独立 oracle 验证源端运行前后静默指纹不变，并在
    目标端同一一致性读事务中计算 count 与多重集摘要、记录 snapshot ID 与边界。只有目标
    声明仍为 `ACTIVE`、未撤回未过期、`target_result.snapshot_finished_at <= valid_until`
    且其余 oracle 条件都 `PASSED`，才写 `SUCCEEDED/CONFIRMED/PASSED`；声明为
    `REVOKED/EXPIRED`、时间覆盖不足、差异或已启动后不可判定进入 `FAILED`，oracle 从未
    启动则保持 `NOT_STARTED`。
11. 每次心跳、事件和状态写都匹配 active attempt、lease token hash 和 fence epoch；
    0 行更新即失租，Worker 停止写入并终止身份匹配的进程树。发现活动安全终止事实的
    heartbeat 只 ACK、绝不续租；无法从阻塞调用返回时由到期 lease/reconciler 保守收敛。
12. 清理 tmpfs 敏感 Attempt 与持久工作目录；任一清理失败产生高优先级安全事件，并在
    后续 admission 持续失败关闭。

Execution 一旦被 Worker 领取，除 `SUCCEEDED/CONFIRMED/PASSED` 外，失败、取消、超时、
失联、preflight 失败或核验未通过均使目标锁进入 `RECOVERY_REQUIRED`；即使能证明 DataX
未启动、`data_effect=NONE` 也不例外。未领取 `QUEUED` 取消由 reconciler 独立收敛，
释放 `RESERVED` 预留，不创建 Attempt/门禁。

提交 remediation confirmation 后，API 只创建 `RecoveryProbe(QUEUED)` 事实。Worker
使用独立 ProbeAttempt/lease/fence，在领取事务内固定同一 TargetNamespace、policy、
ACTIVE secret/Envelope，提交后才连接并复核 `COUNT(*)=0`。只有当前 probe fence 的
`SUCCEEDED+EMPTY` 可原子关闭 gate/lock；非空、失败、不确定、取消或 LOST 均保留门禁，
不自动重新入队。平台不执行 truncate/delete，只有门禁关闭后才允许新的 Execution。

禁止用户控制可执行文件路径、工作目录、JAR 路径或 shell 参数。

## 7. 健康、就绪和启动顺序

- `/health/live`：进程事件循环可响应，不访问外部依赖。
- `/health/ready`：管理平面关键门检查数据库迁移、PostgreSQL、API 日志卷和追加式审计
  事件哈希链。正常请求只比较每组织 watermark 和审计索引 tail，不读取整条 `event_json` 链；
  完整重放最多每 60 秒一次且受 30 秒事务/语句预算约束，新的 event 只做 suffix 重放。
  watermark 缺失、tail 漂移、过期 full proof、超时、CAS 竞争或完整性失败均
  `503/DOWN`；失败/超时的完整重放在下一次尝试窗口前固定返回
  `AUDIT_CHAIN_FULL_REPLAY_THROTTLED/DOWN`，不会连续扫描；health 结果最多缓存 1 秒，已有计算时直接
  `READINESS_CHECK_IN_PROGRESS/DOWN`，不排队耗尽 API pool。它只证明同库链的有界核验，
  不是数据库外锚点或管理员篡改防护；V1 不声明未实现的审计公钥 keyring、外部锚点或
  ACTIVE signer。
- Worker readiness 还需 Runtime/manifest、DNS/egress、日志卷/容量水位，以及
  Execution 与 RecoveryProbe 两套 fence 条件写、持久公平 cursor 和未领取取消探针。
- egress-guard health 只在 ACTIVE policy view 可读、nft apply/readback 成功、规则未漂移
  且 attestation 未过期时通过；API/Worker 还必须验证同一真实 network namespace。
- Web readiness 检查静态资源与 API 路由。
- Launcher readiness 还必须确认实际监听/Compose 映射仅有 Web
  `127.0.0.1:17860`，并确认 Docker Desktop/WSL2 Engine 与宿主磁盘水位可用。

启动顺序：

`launcher preflight → postgres → migration job → egress-guard healthy → api/worker（共享 netns） → web → reconcile → open browser`

迁移、PostgreSQL、API 日志卷或审计哈希链失败时返回 `503/DOWN`。Runtime 摘要不匹配、
所需 KEK/Envelope 缺失、secret 紧急撤销未收敛、egress enforcement 不可证明、工作区或
容量门异常时返回 `200/DEGRADED` 并停止新执行，但仍允许登录、配置和查看诊断，
禁止带病运行。

## 8. 可观测性

所有记录关联：

- `request_id`
- `actor_id`
- `project_id`
- `job_id` / `job_version_id`
- `execution_id`
- `attempt_no`
- `fence_epoch`
- `worker_id`

指标至少包括：

- HTTP 请求量、错误率、P50/P95/P99 延迟。
- 数据库连接池/锁等待、Worker pool 的 checked-out/overflow/等待超时、`datax_worker` 活跃与
  空闲会话数及服务端回收次数、两类 QUEUED 数量、最老 eligible/blocked 排队时间、持久项目
  服务序号/欠服务时间、预计 backlog、NOTIFY/轮询发现数、未领取取消收敛时长。
- Worker 心跳、Execution/RecoveryProbe lease/fence 拒绝、三轴状态、TargetNamespace
  活动锁、RecoveryProbe 结果和恢复门禁数量。
- DataX 启动耗时、运行耗时、读写记录、失败记录、字节和吞吐。
- 取消、超时、`LOST`、oracle FAILED/INCONCLUSIVE、LogGap 原因、日志
  raw/redacted/stored/dropped 字节和清理失败数。
- 磁盘 effective free、日志预算占比、绿色/黄色/红色 admission、拒绝数、保留清理和
  备份结果。
- EndpointPolicyRevision/DNS/selected-peer IP/egress/PhysicalEndpointIdentity/
  TransferPolicy scope 拒绝数、KEK/Envelope 恢复探针、secret 紧急撤销收敛。审计
  锚点/公钥 keyring 年龄与失败指标只在对应组件实现后加入，当前不能显示伪造值。

结构化应用日志与“脱敏后的原序日志”分开。原序只表示平台合并 stdout/stderr 后观察到的
sequence，未脱敏原始字节永不落盘。解析器不改写已保存正文；解析失败只影响
`summary_parse_status`，不能替代 oracle 或形成成功终态。

## 9. 日志和审计保留

- DataX 脱敏后的原序日志按 Execution/Attempt 分块，使用单调游标、SHA-256 和长度记录。
- UI/API 只读取脱敏日志，不存在未脱敏日志下载路径。
- 每块与 Execution 分别记录 `raw_received_bytes`（脱敏前仅计数）、
  `redacted_received_bytes`（脱敏后截断前）、`stored_bytes`、`dropped_bytes`，并满足
  `dropped=redacted_received-stored`；raw/redacted 差值不表示 secret 长度。
- 单行超限时保留脱敏头尾诊断窗口。
- 单执行达到默认 100 MiB 上限后保留末尾环形诊断窗口，并持续记录
  `log_truncated/first_truncated_sequence` 与四类累计计数。
- 行/执行限额、环形淘汰、读取/解码/脱敏/存储失败和 fence 丢失都必须追加 LogGap，
  记录相邻 sequence、原因、四类字节计数和证据哈希。任一 Gap 设置
  `log_incomplete=true`；限额类同时设置 `log_truncated=true`。
- API/UI/下载在任一 Gap 后必须显示“不完整日志”及原因；已丢弃字节不能通过分页恢复，
  也不得用 `has_more=false` 暗示日志完整。
- 执行日志默认 30 天后清理；被事故/审计保全的记录例外。
- 当前实现只提供数据库内追加式 `DXAUDITv1` 事件哈希链、序号连续性和 readiness
  验证；它能发现普通应用路径的删除/改写，但不能抵抗可同时修改数据库记录和链头的
  数据库管理员。当前没有数据库外 checkpoint、签名 keyring、WORM 或 24 小时锚点门禁。
- 发布前必须实现并验证以下独立能力：至少每日或每 10,000 个事件（先到者）按
  `DXAUDITCHECKPOINTv1` 精确前像用独立 Ed25519 key 签名，并写入数据库外
  WORM/对象保留目标；验证方从只读公钥 keyring 按 `anchor_key_version` 验证。
- 目标签名前像字段顺序固定为 domain、organization UUID、through sequence、chain
  head、previous checkpoint hash、`SHA-256`、`RFC8785-v1`、六位微秒 UTC 创建时间、
  key version，各文本字段以单个 LF 分隔且末字段后无 LF；精确公式以
  `04_数据库与领域模型设计.md` 为准。不得签实现私有 JSON 序列化结果。
- 目标 key 轮换必须先把包含旧/新公钥指纹的双签 `DXAUDITKEYROTATIONv1` 声明写入
  WORM，再切换 ACTIVE/VERIFY_ONLY；首个公钥匹配数据库外只读 genesis fingerprint。
  锚点失败 24 小时后的高风险操作门禁只有在该组件实际实现后才可宣称生效。
- 清理任务记录对象数量、范围和结果，并产生审计事件。

内部保留 helper：

```text
datax-studio-retention-maintenance run --json
```

- 返回码 `0`：本批次完成且没有阻断项。
- 返回码 `3`：本批次为 `PARTIAL` 或 `BLOCKED`；JSON 的 `block_reasons` 给出稳定原因。
  当前到期 AuditEvent 必然以 `AUDIT_WORM_ANCHOR_UNAVAILABLE` 保留，不能把返回码 `3`
  改写成成功。
- 返回码 `4`：数据库时间、迁移、审计链、文件边界或其他维护前提失败；不继续删除。
- helper 使用固定最短值：日志正文 30 天、Execution 组 365 天、AuditEvent 730 天、
  IdempotencyRecord 24 小时。部署配置只能延长；当前没有绕过合规审批的缩短入口。
- 日志正文删除采用同一日志卷内的隔离重命名和提交后删除；启动时只会为数据库中已经标记
  不可用的正文补删隔离文件，或为事务已回滚且仍标记可用的正文恢复原路径。无法解析的
  隔离对象保持不动并报告阻断。
- 维护不是业务 Execution，也不是 Cron/DAG；何时由 Launcher/运维窗口调用不改变 V1
  “仅手动触发复制”的边界。

> Schema/严格 Rust 校验、旧式完整集合的 `LEGACY` 指针原子提交、以及 Compose 从单一指针
> 注入 secret/installation-id/三个卷名已有工程候选；Launcher restore 入口也已加入干净
> 目标证明、固定无网络容器、双 key 标准输入和受 ACL staging，但这些不等于 `RESTORE`
> 提交已实现。
> 新空 PostgreSQL volume、真实 `pg_restore`、数据库/审计链/日志/密钥证据重算、
> 卷/secret/installation-id 原子提交、异机恢复和 RPO/RTO 仍未实现或未运行。发布、

> “系统可恢复”声明必须继续阻断。

DATA、SECRETS 与 restore staging 的无网络 helper 使用角色加安装/用户或恢复输入派生的
不透明确定性名称，并写入 role 与不透明 ID 标签；因此不同安装不会因固定名称互相碰撞。
当 Docker CLI 超时、启动、输出捕获或 helper 结果校验失败时，Launcher 只按精确名称枚举
候选，读取其不可变 container ID 与两项标签，随后只对已验证 ID 执行
`docker container rm --force <id>`。ID 消失只有在重新枚举确认名称已不存在时才视为已清理；
标签不匹配、名称重用、枚举/inspect/remove 失败均返回 `HELPER_CLEANUP_FAILED`，不删除
未验证容器或任何 named volume。这是 Rust E1 行为与单元测试结论，尚未证明 Windows Docker
Desktop 在 timeout/CLI 终止下的真实容器收敛。

当前 Launcher 还会在普通 `start/backup` 的任何初始化或备份读取前检查固定
`system-restore` 根；该根存在或状态无法安全检查时分别以 `RESTORE_IN_PROGRESS` 或
`RESTORE_STATE_CHECK_FAILED` 失败关闭，不生成替代 secret/installation-id/卷，也不把
部分恢复当成新装。这是 E1 防破坏门禁，不是恢复完成证明。

### 10.1 备份对象

- `.dxdata`：custom-format、`--compress=0 --serializable-deferrable` 的一致性
  PostgreSQL 逻辑 dump，`des-log-data` 中符合固定路径的脱敏日志，以及
  `compose.yaml/images.release.env/release-manifest.json` 三个发布元数据。
- `.dxdata` 的标准 `pg_dump` 与所有诊断包必须固定排除完整

  恢复或重新激活任一 Phase-A nonce/grant authority；当前 dump 保留 `alembic_version=0020` 却排除
  此 schema，所以真实 restore/bootstrap/start 继续 `BLOCKED`。未来若需要继续资格化，只能由独立
  受保护 issuer 在新 restore epoch 后重新验证 P/QH 并重新签发；此处不是已可运行的 restore/reissue
  流程。
- `.dxkeys`：PostgreSQL owner、egress-guard、API、Worker 四类数据库密码、JWT 密钥、
  refresh/idempotency HMAC 与全部受支持 KEK；使用与 DATA 不同的恢复秘密，并以
  `related_data_backup_id` 精确配对。
- DATA 明确排除 `des-postgres-data` 物理卷、WAL、Docker volume tar、
  `des-workspace-data`、`job.json`、未脱敏 Runtime 文件和任何运行 secret。

### 10.2 周期

- V1 只提供由操作者通过 Launcher 手工发起的系统导出，不内置 Cron、DAG 或自动备份
  调度。每日/发布前导出、14 天保留和每月恢复演练是组织外部运维政策。
- 操作者为 DATA、SECRETS 选择两个不同的本地新目录，并把两包与两把恢复秘密按分离
  保管规则复制到独立介质；本机副本不能与 Docker/WSL2 虚拟磁盘构成同一故障域。
- 试点前必须至少完成一次干净 Windows 11 x64 异机恢复演练；当前为 `NOT_RUN`。

### 10.3 恢复验收

- 已实现的 E1 前置只负责认证双包、校验发布/版本/installation-id 绑定、写受双秘密认证
  的 journal，并把内容解到全新空 staging；它不创建或切换运行卷。
- 在没有旧 installation-id、活动代际、产品容器或产品卷的干净 Windows 11 x64 VM 中
  安装同一或明确兼容的签名 Setup，创建新的三个
  带 restore-journal-id/installation-id/role 标签的随机 staging named volumes，在
  新空 PostgreSQL volume 执行真实 `pg_restore`，完成下列证据重算后原子提交三个卷、
  secret 与 installation-id 的单一 `RESTORE` 运行代际指针；不得依赖原机 WSL2 虚拟
  磁盘路径。当前只有 `LEGACY` 指针接入，该恢复提交路径仍为 `BLOCKED_NOT_IMPLEMENTED`。
- 校验迁移版本、行数、外键和审计链。
- 从数据库外签名锚点向前重放审计链，并验证 WORM 对象签名/哈希。
- 抽查 JobVersion 哈希、Execution 与日志产物哈希。
- 验证当前和仍在备份保留期内的旧 KEK/Envelope 可解密测试凭据，但不输出明文；证明
  业务 ciphertext/nonce/AAD 未因重包裹改变。
- 抽查 EndpointPolicyRevision、PhysicalEndpointIdentity/TargetNamespace、
  DatasourceRevision、target lock/recovery gate、RecoveryProbe 独立 fence、公平 cursor
  和三轴状态约束。
- 记录实际 RPO/RTO；超过 24 小时/4 小时需整改或正式豁免。
- 验证卸载旧程序后保留的数据/备份可被重装版本识别；缺少 KEK 时必须 fail closed，
  不能生成新密钥覆盖旧数据。

- 应用至少兼容一个迁移窗口。

## 12. 事故处置

### Windows、Docker Desktop 或 WSL2 中断

1. UI/Launcher 明确单节点不可用，不宣称自动切换；Docker Engine 不可用时不写假健康状态。
2. Docker 恢复后不立即开放新执行，先核对容器 identity、PostgreSQL、Execution/
   RecoveryProbe lease/fence、TargetCopyLock 和日志缺口。
3. 睡眠/休眠导致租约跨越阈值时按失联路径收敛；旧 fence 不能恢复写权限。
4. `wsl --shutdown`、Docker Desktop restart 和 Windows reboot 均保存诊断与恢复证据。
5. 数据卷损坏时停止自动重建，转入第 10 节备份恢复；不得用空库覆盖。

### 永久 RUNNING/心跳丢失

1. 阻止新执行领取。
2. 核对 Worker、active attempt、fence epoch、lease、host boot ID、PID start time 和
   cgroup/container identity。
3. 只清理身份完全匹配的孤儿进程；PID/PGID 单独匹配不足以发送信号。
4. 将无法证明仍在运行的执行标记 `LOST`，不得标记成功。
5. 把目标锁转为 `RECOVERY_REQUIRED`，保留日志和审计；提交处置确认并经平台空表复核前
   不得恢复后再次执行。

### 凭据疑似泄露

1. 在一个事务把相关 CredentialSecret 置 `COMPROMISED`（确认不再可用时
   `REVOKED`）；已 `RETIRED` 的历史版本也可单向升级到这两个紧急终态。禁用 current
   指向它的 Datasource，禁止解密/新连接，并为所有已绑定它的非终态
   Execution/RecoveryProbe 建立紧急终止事实；若是 current secret，也为不可变引用该
   DatasourceRevision、尚未绑定 secret 的排队工作建立请求，由 Worker/reconciler fail-closed
   收敛。
2. 隔离日志/产物，禁止继续传播。
3. 等待 Worker/reconciler 以各自 fence 收敛；无法确认已停止的 Execution 进入
   `LOST + RECOVERY_REQUIRED`。
4. 轮换数据源凭据和可能受影响的平台密钥；KEK 轮换新增 Envelope，不改写业务密文/AAD。
5. 通过审计确定访问范围。
6. 修复脱敏或隔离缺陷并完成安全复盘。

### 目标外部独占声明撤回或窗口已知破坏

1. Operator/Admin 一旦从 DBA、变更冻结流程或其他可信渠道获知平台外 DML/DDL 或冻结失效，
   立即调用 `POST /executions/{execution_id}/target-exclusivity/revoke`，提交
   `statement_version='1.0'`、责任类型、报告时间和原因；不要等待平台“自动发现”。
2. API 原子保存 `REVOKED` 状态并写 `TARGET_EXCLUSIVITY_REVOKED` 审计。未领取执行由
   reconciler 取消并释放 `RESERVED`；已领取执行终止进程并进入恢复门禁；已进入
   `VERIFYING` 的 oracle 记录 `INCONCLUSIVE/TARGET_EXCLUSIVITY_BROKEN`。
3. 声明自然到达 `valid_until` 时按 `EXPIRED/VALIDITY_WINDOW_EXPIRED` fail closed；目标
   快照完成时间晚于截止时间不得 `PASSED`。
4. 平台可通过独立 oracle 发现最终数据差异，但无法技术证明全部瞬时、未报告或已回滚的
   外部写入。事故报告必须如实记录发现来源、未知窗口和这一剩余风险。

### 目标部分写入或 oracle 不通过

1. 保持目标 `RECOVERY_REQUIRED` 锁，停止同表所有新执行。
2. 保存 `process_state/data_effect/verification_state`、差异和日志截断证据。
3. 由业务/数据库责任人在平台外决定回滚或清空；平台不自动执行 DML/DDL。
4. Operator/Admin 提交 remediation confirmation；系统创建独立 RecoveryProbe。Worker
   用 ProbeAttempt/fence、同一 TargetNamespace/revision/policy、运行时 DNS/egress
   连接证据复核 `COUNT(*)=0`。
5. 只有 probe `SUCCEEDED+EMPTY` 原子形成 gate `VERIFIED` 后允许创建新的 Execution；
   probe 失败/非空/LOST 保持门禁，成功复制到非空目标不可再次执行。

### 审计锚点（实现后）或 KEK 异常

1. 当前只对数据库内哈希链异常失败关闭；外部锚点组件实现后，锚点超过 24 小时未成功、
   公钥 keyring 指纹不匹配、签名失败或 signer `COMPROMISED` 时停止高风险管理操作和
   新执行，保留只读查询。
2. 任何 KEK 指纹不匹配/缺失立即使依赖该版本的服务未就绪；不得跳过解密或用新 key
   覆盖旧文件。
3. 外部锚点仍未实现；安全导出 helper 存在但恢复 helper 仍关闭，不能声称可执行该
   恢复。实现后使用独立备份与双人流程恢复，并按 `DXAUDITCHECKPOINTv1` 重建前像、
   验证外部锚点/双签轮换链和测试凭据后再恢复服务。

### 磁盘接近满

1. 按绿色/黄色/红色 admission 执行：红色停止两类事实领取，reconciler 继续取消/失租
   收敛；黄色只允许满足独立预留的 RecoveryProbe 与既有工作。
2. 保留审计和事故相关日志。
3. 执行受控保留清理，不得直接删除数据库目录。
4. 扩容并验证文件系统、日志索引和备份。

### 13.1 容量包络与队列公平性

默认 200 GiB 可用 SSD 的验收预算为：系统/镜像/Runtime 30 GiB、PostgreSQL 40 GiB、
30 天日志 60 GiB、工作区 20 GiB、安全保留 40 GiB、机动 10 GiB；备份必须外置。

包络分档：

| 维度 | 轻量控制档 | 大表复制档 |
|---|---:|---:|
| 24 小时 Execution | 200 | 20 |
| 单次源规模 | 10 万行或 512 MiB | 100 万行或 5 GiB |
| 单次服务时间预留 | 6 分钟 | 60 分钟 |
| 30 天 stored log | 平均 ≤10 MiB/次 | 硬上限 100 MiB/次 |

混合负载必须同时满足：

```text
Σ max(profile_reservation_seconds, observed_p95) over rolling 24h <= 20h
Σ log_stored_bytes within 30d <= 60GiB
daily_sustainable <= floor(60GiB / (30 × observed_average_log_bytes))
```

所以“200 次/天、每次 100 MiB 日志、保留 30 天”不是受支持组合；100 MiB 全打满时约为
20 次/天。其他默认值：活跃项目 20、JobVersion 1,000、普通 QUEUED 200、单行 1 MiB、
并发 DataX 1、轮询 5 秒。未知源统计按大表档。

`effective_free = filesystem_free - active_log_reservations - active_workspace_reservations`。
日志 `<80%` 且 effective free ≥40 GiB 为绿色；日志 80%..90% 或
30 GiB≤effective free<40 GiB 为黄色，
停止普通新执行准入、仅在预留后仍安全时服务既有事实/RecoveryProbe；日志 >90% 或
effective free <30 GiB 为红色，停止新领取并 readiness 失败。普通 QUEUED 达 200 或
预计 eligible backlog >8 小时也以 `503 CAPACITY_ADMISSION_BLOCKED` 拒绝新运行请求，
reason 仅为 `QUEUE_LIMIT/BACKLOG_LIMIT/DISK_YELLOW/DISK_RED/LOG_BUDGET`；既有事实不删除。

公平顺序来自 PostgreSQL 持久 `last_service_sequence`，统一覆盖 Execution/RecoveryProbe；
只有成功领取才推进；同项目存在 eligible Execution 时连续 RecoveryProbe 不超过 1。
容量档内 SLO：空槽事实发现 P99≤10 秒，eligible Execution 等待
P95≤2 小时/P99≤8 小时，eligible RecoveryProbe P95≤1 小时/P99≤2 小时，未领取取消
收敛 P99≤10 秒。blocked 项单独计时并展示 reason；8 小时违约停止普通新准入。超过包络
或调高并发前，重新完成数据库锁、磁盘、日志、取消、两类 fence、oracle 和公平性压测。

### 13.2 两阶段资格资源与发布运行规程（ADR-0011，P/QH/PAG 契约仅 E1 基础件）

未来的 release qualification 不是产品运行时的在线服务，也不是允许用户填写的设置项。
它是一个随私有最终候选以只读、哈希受约束资源交付的 detached 签名文件；API/Worker
只能把它与自身已固定的 payload identity 和 RQA 公钥策略一起验证。当前有 P/QH 的
Schema 与失败关闭 parser、`phase-a-qualification-grant.v1`（PAG）Schema，以及 private
Phase-A payload/runtime/job binding + durable nonce/grant persistence 的 **E1、进行中**基础件；
它不是可运行的 qualification 通道。安装包、Compose、Launcher 和运行时均没有专用 ledger
database role/function、private API/Worker/Compose override、受保护 harness、QR 或 reader 能力，
任何文档中的 P/QH/PAG/QR 描述都不能被当作可配置功能、普通运行能力或 E3/E4 结论。

本轮已记录 `scripts/test-postgres-e2.sh` 面向临时、一次性真实 PostgreSQL 15 容器的结果为
`12 passed`，其中包含 0020 migration 的 upgrade/downgrade/re-upgrade，并覆盖 runtime-role
实际登录对 closed-default 私有 schema 的 SELECT/INSERT/UPDATE/DELETE/TRUNCATE 拒绝、nonce/grant
不可变性、nonce replay 和 grant 生命周期；同一脚本还验证 nonce/grant sentinel 的固定
`--exclude-schema=des_phase_a_qualification` TOC 与临时库 restore 排除。这只构成受限 PostgreSQL E2：
它不启动产品 Compose、API/Worker、DataX、MySQL 或独立 oracle，也不验证 restore bootstrap/start，
不是 DataX E3、Windows E4、private harness 验收或发布结论；测试/脚本文件存在本身不能代替该次
`12 passed` 加 dump probe 的运行记录。进程内 provenance marker 只
能拒绝同一 Python 进程中的偶然构造或篡改，不能充当 protected issuer/consumer 信任边界；跨进程
consumer 必须从 protected durable grant lookup 重建绑定，不能接受调用方 dataclass、请求体或
marker 作为授权来源。当前 E1 PAG ledger 刻意不含 `execution_id` linkage；未来精确 execution
binding 必须由单独 protected atomic issuer/function 纵向切片提供，不能事后把 grant 改为可变。
标准系统备份与诊断必须固定排除完整 `des_phase_a_qualification` schema；普通 restore 不得复制、
恢复或重新激活任何 Phase-A nonce/grant authority。当前 dump 仍会保留 `alembic_version=0020` 而排除
该 schema，真实 restore/bootstrap/start 继续 `BLOCKED`；未来只有独立受保护 issuer 在新 restore
epoch 后重新验证 P/QH 才可重新签发，因此这不是现有 restore/reissue 路径。

运维/Release 顺序必须固定：

1. 先在隔离构建环境固定 P，记录 payload root、五镜像、Worker Runtime、插件、SBOM 和
   许可证；P 不得包含 QH、PAG、QR、最终 Setup、Launcher 或最终 manifest。
2. HQA 仅向受保护 Windows harness 提供短期、一次性 QH。该资源不得写入标准 Compose、
   安装目录、公开候选、备份、诊断包或用户配置；测试结束必须按受控清理流程销毁。
3. 受保护 private authority/ledger 只有在独立验证 P 与 QH 后，才可记录一个 PAG。PAG 必须
   固定 `grant_id`、P binding/`payload_binding_sha256`、harness binding、QH
   `issuer_key_id/qualification_id/document_sha256/nonce_sha256`、一个 Reader/Writer pair、
   `issued_at/not_before/valid_until` 和单调 state；`payload_binding_sha256` 是
   `SHA-256(RFC8785(QH.payload_binding))`，`document_sha256` 是包含 `signature` 的 canonical
   signed QH document 的 SHA-256（不是 raw nonce），`nonce_sha256`（即 nonce hash）是
   `SHA-256(UTF8(QH.nonce))`；三者均不得附加域前缀，也不得保存 raw nonce。独立 durable nonce ledger
   原子消费 nonce，grant ledger 仅允许 `ACTIVE -> REVOKED|EXPIRED`。其有效窗口必须落在
   QH 有效窗口内。
   该授权记录只留在受保护私有 authority/harness 边界，不能进入任何普通 API/Worker、Plugin
   Manifest、标准 Compose、安装包、公开候选、备份、诊断包或用户配置；它不是 E3/E4、QR、
   `WINDOWS_E4_CERTIFIED` 或公开发布批准。
4. Phase A 的真实数据库、独立 oracle 和私有 Windows harness/payload qualification（不是
   E4，也不产生 Plugin Manifest 状态）经独立复核后，RQA 才能签发 QR。RQA 私钥与
   Authenticode、HQA、GitHub OIDC 凭据相互独立，且需要受保护环境或不可导出 HSM/等价控制。
5. QR 进入私有 F 后，以标准 Launcher/Compose、无 QH/PAG override 的方式在干净 Windows
   11 x64 运行 Phase B；只有精确 F 的 Setup/Launcher 正常模式 E4 证据才可派生
   `WINDOWS_E4_CERTIFIED`。Launcher 的未来职责是校验已签名的 manifest、payload root 和
   QR 资源，而不是联系 GitHub、下载证明或自行批准资格。
6. Phase B 通过后才生成最终候选根并交给 ADR-0010 的 hosted attestor。最终 validator
   聚合签名、场景、P0/P1、Discovery、E3/E4 和 provenance 形成同一 F 的有效 PR 后才可
   创建公开 release；`WINDOWS_E4_CERTIFIED` 本身不构成公开晋级或普通用户放行。

不得把 QH 或 PAG 作为标准 Compose 的 Docker secret、用户环境变量或可编辑文件暴露；不得让
PAG 变成普通 API/Worker 的参数或状态来源，不得让 QR 绑定包含 QR 的 Setup/manifest，或把 QR
写回 Worker 镜像。当前用户/本机管理员能控制
宿主仍是既定信任边界，QR 校验只能发现制品不一致，不能把本机提升为不可篡改 TCB。
